## Live alarm-only control path (experimental; manual acceptance pending)

The same pinned checkout was checked again at `c9df5ef5d675b0d1d226828bddf6b78c28502d91`. `Content.Server/Atmos/Monitor/Systems/AirAlarmSystem.cs:170-191,194-225,334-346` registers device-list/power/UI handlers, closes interfaces on power loss and accepts device settings only for addresses in the alarm's DeviceList. `Content.Shared/DeviceNetwork/Components/DeviceListComponent.cs:17-28` provides the inherited 32-device bound. The local resolved `AirAlarmData` is consumed by the wall alarm entity and its runtime: a matching alarm, persisted list (up to 32 UUIDs), loaded-only local 16-block spherical candidate discovery, and fresh fully delivered 100 W are required for pairing or edits. The alarm menu routes settings to online associated vent/scrubber identities. This is the current production control route; direct vent/scrubber menus are absent. The alarm requires no separate data cable: upstream SS14 devices use same-grid wired DeviceNetwork, but local UUID pairing is not that network.

Departure: local alarm discovery scans only loaded candidates within its 16-block sphere and requires explicit UUID pairing; stored associations can remain visible offline. It does not implement general DeviceNetwork/address discovery, departmental access, automatic modes, alerts, directional-bound selection, or wide-network association. No separate data cable is required. The upstream empty allow-list cancels broadcasts (`DeviceListSystem.OnBeforeBroadcast`); a Network Configurator can collect device entities and apply them using Set/Add in the DeviceList UI, while map data can preconfigure lists. Opening an unconfigured alarm alone does not populate its list. Local pairing replaces that setup workflow, not SS14's wired same-grid transport.

The local alarm edits enabled state, scrubber filter/siphon and selected gases, vent external pressure bound (0–4500 kPa), and scrubber volume rate (0–0.2 m³/s). Numeric edits are kind-checked and revisioned; invalid input is rejected before client send and revalidated server-side. The scrubber cap is sourced from `GasVentScrubberComponent.TransferRate`, which clamps to `MaxTransferRate`, defaulting to `Atmospherics.MaxTransferRate = 200` L/s. Opening requires fresh full 100 W delivery; depowering invalidates the menu and closes it, matching the upstream power/UI rule. Internal pressure checks, vent intake direction, wide-net, and presets remain absent. Manual registered-human acceptance remains pending; this documentation does not claim a successful in-client test.
