## Required parity gate for future tasks

**Explicit DeviceNetwork departure:** Local resolved vent/scrubber prototypes deliberately do not declare `DeviceNetwork`; the separate alarm UUID association/menu is only the current control route and is not its substitute. The pinned SS14 endpoint prototypes declare `DeviceNetwork`, and upstream alarm control uses same-grid wired networking. General network/access semantics, automatic modes and alerts remain **NOT PARITY**, even though live local prototypes and alarm settings are implemented. Wired runtime consumers do not alone prove full composition or acceptance.

Before implementing **each new feature**, answer literally: **“Does this thing I am making have parity with SS14?”** Record (1) the pinned SS14 entity prototype ID/path, parent chain, effective component list including overrides/removals, and sourced component defaults (alongside exact system files/observed behavior); (2) the actual local resolved prototype/composed components and runtime consumers of those defaults, with evidence; (3) each departure, explicit reason, and user review; and (4) tests of resolved inheritance/defaults, tests that the real consumers use them, and required conservation, power, and ownership/lifecycle tests. Missing prototype/composition, mapping, consumer evidence, or source is **NOT PARITY**, not inferred from Java constants or visual similarity. No SS14 code is to be copied as part of this audit. The clicked-only, unchanged sealed-wall/no-AIR interaction is an explicit Minecraft-specific departure; it does not establish an SS14 Airtight equivalent.
