# Hands/inventory sprint: current handoff

**Status: playable-hands MVP implemented, not full inventory acceptance.** The owner explicitly deferred sudden-crash/power-loss durability work to prioritize normal playable body-owned hands. Do not equate automated coverage with connected-client acceptance or SS14 inventory UI/storage.

## Policy and current implementation

- Only a controlled `CHARACTER` body with prototype-declared hand capability is eligible: human has left/right hands; pig has none. Hands and wearable slots belong to the body; grid/container contents belong to a storage item, not an intrinsic body inventory. Legacy `HANDS` tokens are metadata, not live `ItemStack` ownership.
- Persistent `LIVE_HANDS` holds ordered hand slots, active hand, occupant token and real `ItemStack` with bounded codec and revision checks. Lifecycle and experimental ready paths bootstrap the attachment for eligible bodies. `HandActorAuthority` requires an exact controlled body/epoch, account-owned `CREATIVE_PARKED_INVENTORY` marker and clean isolated carrier, and revalidates authority for actions.
- Server-side whole-stack `ItemEntity` pickup and drop transfer ownership between world and body hands, with a server ray/reach/occlusion check for pickup, revision/token checks and compensation on known failure paths. The follow-up shares a small aiming tolerance for targeting and uses short safe forward drop placement with fallback. Ambiguous outcomes return `RECOVERY_REQUIRED`, potentially requiring admin intervention; they are not proof of automatic repair or crash-safe atomicity.
- Authenticated server packet query/action routes provide hand state and gated pickup/drop intents; client G pickup / H drop controls and an active-hand HUD. The follow-up makes the HUD/chat layout safer, restores a crosshair and shows decimal health and `DAMAGE`. The client only nominates a target; the server decides. No item-owned storage, inventory menu or SS14 inventory UI is implemented.
- `CreativeParkedInventory` persists account-bound exact snapshot data in the **same vanilla playerdata attachment**. The runtime parks/physically clears the actual Creative carrier before eligible body control and restores only in Creative across routine lifecycle and experimental mode transitions. Empty Creative carriers can receive an empty isolation marker. Packet and selected direct-API guards are bounded; raw inventory-list mutation and other direct paths are **not** covered by a complete barrier. Unsupported/occupied extra compartments are rejected rather than silently quarantined. The old external `CreativeQuarantineStore` journal, reconciliation classifier and playerdata disk probes remain inert/deferred, not the active park/restore path; no independent durable index or sudden power-loss guarantee is claimed.

Implemented follow-ups include a no-write denial diagnostic that stays in Creative; a narrowly scoped **OFFLINE Creative operator reconnect** recovery after that no-write denial, without granting body authority; `/ms14dev creative` from body and ghost; strict marker rollback; declared human-harness host support for vacuum damage; direct-hurt immunity for ghosts; confirmed corpse client pose; and the HUD, targeting and drop changes above. Source-verified later fixes address a `parkBody` admission bug: after successful restoration of a nonempty snapshot, it incorrectly required the Creative carrier to be empty; admission now checks the exact pre-switch snapshot (42 slots, cursor and selected hotbar slot). `PlayerCharacterHarnessEntity` now overrides `requiresCustomPersistence()` so vanilla Mob distance-despawn cannot remove the saved body. The hand HUD no longer shows a transient syncing placeholder. These changes are automated-test verified, **not connected-client retested**. An already-missing old body is not recreated; an offline saved location can still be stale if the body moved cross-chunk. Existing marker corruption can still require administrator recovery; none of these fixes guarantees recovery of an existing save. No SS14 knockback requirement is asserted here.

**Not proven:** connected-client success of the latest fixes, actual saved-body unload/reload survival, Creative return/reconnect under the failing nonempty-carrier and far-flight conditions, denial/contamination behavior across manual play, 20-player performance, comprehensive direct-API isolation, or power-loss durability.
