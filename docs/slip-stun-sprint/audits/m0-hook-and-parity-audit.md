# M0 Hook and Parity Audit

**Outcome: audit complete, implementation hooks not yet runtime proven.** This is an evidence/design report, not a claim of working slip or stun. No GameTest was run; the planned real server GameTest remains pending.

## Findings

- **Contact:** In vanilla Minecraft 1.21.1 / NeoForge, `Block#entityInside` can be reported repeatedly while an entity overlaps a block. It does not provide SS14's step-trigger entry/exit latch or speed test. The implementation needs a server-side per-target/source contact latch and exit reconciliation (including sources/targets removed or unloaded); it must not treat every overlap callback as a new slip. `EntityTickEvent.Pre` is available as a server tick/reconciliation hook. Runtime ordering, cleanup, and contact semantics still require a real GameTest.
- **Action gates:** Relevant server player packet paths are `ServerGamePacketListenerImpl.handlePlayerAction`, `handleUseItem`, `handleInteract`, and `handleMovePlayer`; corresponding game-mode actions include `ServerPlayerGameMode.useItem` and `useItemOn`. Villager `Brain` ticking and `GoalSelector.tick` are independent of these player paths. No common player-and-AI authorization hook was found. A central timed-status/action-policy owner must gate the player paths and the AI paths; if both cannot be intercepted reliably, stop at the **M2 gate** for evidence and owner decision rather than claiming common stun enforcement.
- **Pose:** `Pose.SWIMMING` is available as an implementation probe only; it is not evidence of SS14 crawling or physical knockdown parity.
- **Identity lifecycle:** `PrototypeRuntime` currently registers three families: reagents, status effects, and alerts (`src/main/java/com/juicyslew/moonstation14/ms14/prototype/PrototypeRuntime.java`). Existing `EntityJoinLevelEvent` and `PlayerEvent.Clone` paths are in `eventhooks/ModEventHooks.java`. Those are candidate integration seams, not proof that a key-only character binding persists correctly across clone, dimension changes, or reload. Use a provider-owned typed attachment containing only the `moonstation14:human` key; resolve it through the server character catalog. A Minecraft villager is a runtime host for this same local human profile, not an SS14 `MobHuman` claim. Current all-`LivingEntity` status handling is not character binding.
- **Source thresholds and capacities:** Local `PuddleBlockEntity` uses flow cutoff `20` and capacity `200000` (`block/block_entity/PuddleBlockEntity.java`); neither is SS14's slip threshold. Pinned `SharedPuddleSystem.cs:228-320` uses `LowThreshold = 0.3`, gates small puddles at `solution.Volume <= overflowVolume * 0.3`, activates slippery contribution only when it is strictly greater than that cutoff, and uses `>=` for super-slippery quantity. Keep a separately configurable local slip cutoff mapped to the pinned semantics. Do not claim the local flow cutoff or capacity is equivalent; if contact/hook design requires conflating them, stop and seek a decision.
- **Source/target data:** Existing `ReagentData.slipData` is source behavior; character `slip_data` must be a separate typed target capability grouping. The human capability adapter should represent status susceptibility, intrinsic no-slip, standing/prone eligibility, and reactive Touch group/method admission, mapped to the pinned inherited human components rather than an invented upstream serialized field. Pinned `MobPig`, `MobChicken`, and `MobCow` inherit `StunImmune`; they are not positive fixtures. Use player and villager on the shared `moonstation14:human` profile.
- **Reactive effect and split:** Pinned `PuddleSystem.cs:245-268` reacts on admitted `SlipEvent`: require reactive target and not already sliding at that event time, roll 50%, resolve current solution, split 15%, then dispatch Touch. Failed eligibility/chance/solution resolution consumes nothing. `spacelube.json` provides slip data; `polytrinicacid.json` provides acidic/touch `HealthChange`. The local shared reagent split helper is `ReagentUnits.split(Map,long)`; compare it against pinned `Solution.SplitSolution` (`Content.Shared/Chemistry/Components/Solution.cs:720-780`) with golden cases, but do not add a touch-specific splitter. The local split uses integer hundredths and deterministic residual allocation; pinned arithmetic can differ slightly. Tiny per-reagent rounding differences alone are not a blocker. Space Lube source slip data does not itself provide response fields; do not invent them. No special Touch splitter is needed.
