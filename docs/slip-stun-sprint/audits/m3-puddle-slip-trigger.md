## Implementation and parity

- `PuddleBlock.entityInside` is a repeated vanilla overlap callback, not a step-entry event. Server-side `SlipSystem` validates the level, live living target, puddle block/entity, identity and policy, then calculates the authoritative current reagent solution. The real GameTest drives `Entity.move` through a real puddle and observes the callback for both a `FakePlayer` (a `ServerPlayer` fixture, not an authenticated player) and a real Minecraft Villager, both bound to the same `moonstation14:human` policy. An unbound pig remains inert.
- The Minecraft contact adapter uses a **virtual 0.8 × 0.8 XZ source trigger** centered in the puddle block. It computes `max(overlap / target area, overlap / source area)`, and requires at least `0.3`, plus vertical intersection against the local puddle shape. This follows the pinned StepTrigger spatial ratio concept, but is not a claim of SS14 collision equivalence: entity AABBs, movement integration, and physics differ in Minecraft.
- Contact latching is bounded per server level and source-position/target pair. It is set after qualifying speed, area and eligibility checks but before intrinsic `NoSlip`, already-knocked-down handling, and cancellable attempt gates. Thus an admitted trigger that is cancelled does not retry while still inside; leaving and re-entering clears/rearms it. `TickHooks` invokes `SlipSystem.reconcileTarget` during living server entity ticks to remove out-of-bounds/source-gone/dead contact latches and reconcile sliding state; source/level validity is also pruned on later contacts. This is an adapter around repeated `entityInside`, not an upstream step-trigger implementation.
- Solution quantities use integer cents (`100` per unit). `LOW_VOLUME_CUTOFF_CENTS = 1,500`, i.e. `50 * 0.3 = 15` units. Total solution at or below 15 is inert; slippery-reagent amount must be strictly greater than 15 to enable slipping; super-slippery amount uses `>= 15`. The local puddle flow threshold `20` and capacity `200000` are separate and are not slip cutoffs.
- Aggregation follows pinned `SharedPuddleSystem`: required speed and friction are weighted over the whole mixture; launch multiplier, stun, knockdown, and super-slippery contribution use slip-data reagent volume. A reagent with no `SlipData` contributes default required speed `5.5` and default friction `1`; no slip-data-specific response contribution. Optional `SlipData` response fields missing from source data receive pinned runtime defaults: stun `0.5s`, knockdown `1.5s`, launch multiplier `1.5`. Current default source slip speed is `3.5` where used for an empty outcome. Target velocity is measured as `length * 20` blocks/second; launch applies the weighted multiplier to the full current velocity vector.
- Attempt flow requires resolved eligible character policy/status capability and standing eligibility, finite speed, a valid slippery mixture above threshold, sufficient speed and area overlap. The upstream ordering is preserved in the bounded path: knockdown restrictions, `NoSlip`, then extensible cancellable attempt gates precede `SlipEvent`; the event carries `wasSliding` observed before the new sliding response and runs before velocity scaling, stun, knockdown status, and sliding-state update. Failed gates do not apply slip effects or consume chemistry. Sliding is a volatile in-memory projection, reconciled against knockdown and cleared when knockdown is absent (including expiry), on death, or on dimension change; leaving the puddle alone does not clear sliding. It is **not durable across reload**, and durable representation needs a later owner decision if persistence is required.

## Boundaries, deviations, and remaining gates

- Minecraft AABB/contact and movement physics differ from SS14's physics/StepTrigger. The virtual trigger and max-ratio calculation are an explicit bounded adaptation; identical outcomes for arbitrary bodies/movement are not claimed.
- Sliding state is volatile across reload as described above; no persistence guarantee or physical prone/crawl behavior is claimed. Timed status/action behavior remains bounded M2 work: network packet denial on an authenticated connected player and actual Villager AI/navigation enforcement are still unproven. No owner-run end-to-end connected-player manual smoke has occurred.
- **M4 Touch is mandatory and pending, not included in this M3 result.** There is no claim yet for the 50% reactive roll, 15% current-solution split, target/reagent Touch admission, scaled effect dispatch, dose conservation, or zero-consumption reactive-gate tests. Slip listeners exist before physical/status effects, but the reactive chemistry pipeline has not been integrated. Do not mark the sprint complete or describe reactive puddle chemistry as working.
- Full physical prone/crawl is not implemented. M3 demonstrates bounded contact/slip and timed status response, not full SS14 knockdown/crawl parity. M2's network+AI limitations remain, and M5 still requires owner manual player-action smoke and any follow-up automated evidence required by acceptance.
