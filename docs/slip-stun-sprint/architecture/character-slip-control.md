# Character Slip-Control Architecture

## Ownership and data

```text
source prototype / live puddle solution ──> slip-source aggregation ──┐
                                                                      ├─> attempt gates ─> SlipEvent ─> physical/status response
target character key ─> character catalog ─> target capabilities ────┘                         └─> reactive Touch split/dispatch
```

- `PrototypeRuntime` remains catalog/reload owner. The implemented immutable typed `CharacterData` family is registered alongside reagent, status-effect, and alert families. The initial `moonstation14:human` record has explicit typed `slip_data` target capabilities. It is an adapter grouping status susceptibility, intrinsic `NoSlip`, standing/prone policy, and reactive Touch admissions—not an upstream serialized field or source reagent data. Its current separate group and method lists imply a global cross-product; arbitrary per-group method profiles are not representable yet.
- Server identity binding is a provider-owned attachment containing only a character prototype key. The server join adapter enrolls a `ServerPlayer` or Minecraft villager as `moonstation14:human`; tests use a `FakePlayer` subclass of `ServerPlayer` and a real villager, not an authenticated connected player. Missing/dangling identity is inert and diagnostic. Keys resolve against the current server catalog. Same-key policy resolution, key-only/dangling behavior, and clone event handling have GameTest coverage, but real dimension transfer and disk save/reload have not been proven. Do not treat those lifecycle guarantees as complete.
- Source prototypes and current puddle solution own slip speed, friction, launch/stun/knockdown values, and super-slippery contribution. They remain separate from target policy. Local puddle flow cutoff `20` and capacity `200000` are not slip thresholds; slip cutoff is an independently configurable setting aligned to pinned `overflowVolume * 0.3` behavior.
- `CharacterControlSystem` owns the implemented finite stun application and active `stun_action_block` policy query. A living-entity `isImmobile` projection, nine `ServerGamePacketListenerImpl` action-handler injections (after `PacketUtils.ensureRunningOnSameThread`), server-player pickup cancellation, and a Villager `customServerAiStep` cancellation are present. M2 GameTests establish status/expiry and immobility for a `FakePlayer` plus a real Villager, not actual inbound packet effects on a connected player or real AI navigation pause. Those are explicit evidence gaps; see the [M2 report](../audits/m2-timed-stun-and-action-gates.md). Full prone/crawl is not implemented; a Minecraft pose alone is not SS14 crawling.

## Slip and reactive event order

1. The bounded M3 server contact adapter deduplicates repeated `entityInside` overlap using per-target/source latch state and reconciles exit through `TickHooks`; `entityInside` alone is not an SS14 step trigger. It uses a virtual 0.8 × 0.8 XZ trigger and maximum normalized overlap ratio `0.3` plus local vertical intersection; Minecraft AABB/physics outcomes differ from SS14. Source aggregation is recomputed from the authoritative solution. See the [M3 report](../audits/m3-puddle-slip-trigger.md).
2. Resolve source and bound target policy. Apply containment/status susceptibility, standing/prone and super-slip rules, target no-slip/slow-over-slippery response, and cancellable source attempt. Failed gates have no slip effects and no solution consumption.
3. Raise the admitted `SlipEvent` **before** velocity, sliding, status, or other later physical effects. This preserves the pinned observation point for reactive handlers.
4. Reactive handling requires target Touch admission and not already sliding at that event point, then uses server RNG for pinned 50% chance. Resolve the actual current source solution; request 15% using pinned rounding by default and the shared split/mutation path. Only after successful split, dispatch admitted per-reagent Touch effects scaled to actual portions. Failed gates/chance/solution resolution consume nothing. A callback failure after removal does not imply rollback or dose replay.

   **Important pinned boundary:** SS14's `PuddleSystem.cs:245-268` splits 15% after Reactive/not-sliding/chance/solution checks and before per-reagent `ReactiveSystem` group/method filtering. Therefore a reagent group/method mismatch can still consume its proportional share while dispatching no effect; it is not an upstream zero-dose gate. Local invalid-prototype and unsupported-payload preflight are deliberate additional hardening that leaves the whole source unchanged, while ordinary callback errors after split remain non-atomic. See the [M4 audit](../audits/m4-slip-triggered-touch.md).

M3 proves contact, weighted source outcomes, latch/re-entry behavior, attempt cancellation, and pre-response event timing. M4 reactive Touch integration is now implemented and its available GameTests pass: the latest required server log reports 99/99. The M4 acceptance gate remains open because FakePlayer is immune to damage and cannot prove connected-player caustic damage; the owner-agreed manual player test remains pending. The trigger uses a 15-unit source cutoff (50 × 0.3); local puddle flow cutoff `20` and capacity `200000` remain independent. M5 bounded sliding-friction conversion and the grounded LivingEntity movement adapter are implemented; the connected-client movement/synchronization check remains pending. The sliding projection is nonpersistent and is cleared on join/clone, not rehydrated from generic knockdown; ongoing sliding can be lost across dimension transfer/reload because knockdown does not establish slip provenance. See [M5 sliding-friction architecture](sliding-friction.md) and the [manual smoke checklist](../manual-smoke-checklist.md). Refer to the [M3 audit](../audits/m3-puddle-slip-trigger.md) and [M4 audit](../audits/m4-slip-triggered-touch.md) for exact evidence and limits.

## Rollout and proof

The M1/M2 proof binds a `FakePlayer` (not an authenticated connected player) and real Minecraft Villager to the same populated profile; M2 verifies shared timed status policy, expiry, and immobility only. M3 proves bounded real puddle contact/slip/status for both actors. M4 proves deterministic Touch split/dispatch, rejected chance, sliding exclusion, source conservation, and Villager caustic damage in server GameTests, but FakePlayer immunity prevents those tests from proving real connected-player damage. Connected-player packet denial and actual AI navigation pause also remain unproven. M5's pure conversion and bounded grounded movement adapter are implemented; the LocalPlayer path, synchronized sliding marker, and client-side source aggregation have no runtime validation yet and require the owner connected-client check. Keep unbound and non-slippery controls inert. Future adapters cover animal, hostile/zombie, humanoid-race, and any nonliving sentient/AI families incrementally; the project owner owns that coverage plan and a dated review gate remains pending assignment. No live possession-transfer proof is required absent such a system. The sprint is still in progress: connected-player damage/manual smoke, connected-client M5 verification, full physical prone/crawl, and dated future character coverage review remain pending or unsupported. Do not mark full acceptance until required player damage is demonstrated.
