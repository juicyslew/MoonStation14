# APC machine UI — visual parity guide

## Source comparison (not connected-client acceptance)

Local sources: `src/main/java/com/juicyslew/moonstation14/ms14/power/ui/client/ApcScreen.java`, `src/main/java/com/juicyslew/moonstation14/ms14/power/ui/ApcMenu.java`, and the `RegisterMenuScreensEvent` registration in `src/main/java/com/juicyslew/moonstation14/MoonStation14Client.java` (`ModMenus.APC` → `ApcScreen`). Upstream reference in the local SS14 checkout: `Content.Client/Power/APC/UI/ApcMenu.xaml`, `ApcMenu.xaml.cs`, and `Content.Client/Power/APC/ApcBoundUserInterface.cs`. This is a source comparison, not a screenshot comparison or a manually observed Minecraft client run. SS14 XAML/C# is reference material, not code to import.

| Concern | Local Minecraft screen | Upstream SS14 APC UI |
| --- | --- | --- |
| Window/frame | Fixed 250×174 `AbstractContainerScreen` with hand-filled nested rectangles: outer `0xff18232a`, inset `0xff26343c`, header `0xff10191e`. Title drawn in Minecraft font. | `FancyWindow` (non-resizable), styled dark panel, spacing/grid and style-class labels; footer divider, flavor labels and logo. |
| APC image | Static 32×32 APC PNG blit at `(left+20, top+48)`; no animation or entity preview. | `SpriteView` entity preview at 64×64, scale 2, south-facing inside a dark panel; `ApcBoundUserInterface` sets the entity. |
| Breaker | Vanilla `Button` at `(left+128, top+58)`, 105×20, with ON/OFF label; no SS14 switch visual. Server response/menu snapshots reconcile local button-label prediction. Authoritative trip latch adds a red `OVERLOAD — TRIPPED` label (`0xffff5c4d`). | Styled `SwitchButton`; `ApcMenu.xaml.cs` binds pressed state and a tripped power label from UI state; bound UI checks access and can disable the switch with tooltip. |
| Power/charge | Battery 0–1000 permille snapshot appears as a 210×10 bar (dark `0xff101519`, constant green `0xff55c98b`) and white percent below. Fill width eases toward authoritative charge; percentage is authoritative. External power and load are explicitly marked unavailable. | Charge `ProgressBar` includes percentage inside, with charge-dependent red → orange → green hue; external supply has none/low/good text and status styles, and power/load/trip text uses UI state. |
| Layout/text | Vanilla Minecraft button skin and typography remain prominent despite the custom panel palette. No styled footer or reusable themed window/switch/bar kit exists for this screen. | Consistent FancyWindow, style classes, switch, progress-bar and footer language across its UI toolkit. |

The local menu/session protocol is separable from this presentation: `ApcMenu` binds a server level/device and opaque session, validates menu context and interaction range, and syncs breaker, four revision words, battery permille and trip latch via seven menu-data slots. Client button requests are correlated and reconciled with server snapshots; `MoonStation14Client` registers the screen and routes responses to the current instance. Those authority/session boundaries could support a differently styled client without changing the core device state. They do **not** constitute a generic SS14-like widget framework or prove connected-client visual/transport behavior. The static APC sprite has its own provenance in [assets-and-attribution.md](assets-and-attribution.md); no upstream footer/logo or other art is imported here.

## Bounded follow-up

If visual parity becomes a priority, first design a **small shared client-side window frame, switch and charge bar** consistent with Minecraft's UI APIs; migrate this screen to those pieces without copying upstream XAML/C# or implying unsupported load/external telemetry. A themed switch should continue to show server-authoritative state after request reconciliation, and a styled bar should keep the existing bounded charge source. Any added art needs separate provenance/license review. Compare screenshots and interaction with an actual connected client before asserting visual parity. Item-range movement testing while the vanilla screen is open remains deferred: server-side range validation does not make vanilla-screen walking possible, and no movement UI change is claimed.
