# Development workflow

For feature work, start with the [author role](roles/author.md). Runtime installation is separate. See the indexed [coordinator guide](coordinator.md), [recovery guide](recovery.md), [reviewer role](roles/reviewer.md), and [protocol schema](../development-workflow-redesign/contracts/protocol.schema.json). The source architecture and detailed design live in the source repository's WR10 packaging guide and redesign DESIGN document; those source-only documents are not installed links. One local coordinator is lifecycle authority; SQLite is state authority, artifacts are external/hash-bound, and page/JSON views are projections.

Use isolated coordinator dependencies and external configuration/database/artifact directories. Examples use wrapper metadata `{ "disabled": true, "configuration": { ... } }`; they are not configuration objects accepted by runtime loaders. Render ONLY the inner `configuration` object to a private fixture before loading. Placeholder paths/credentials/session values must be replaced only in that private fixture; never place real credentials, sessions, database inputs or private context in a worktree or package. The coordinator CLI currently exposes only `serve --config ... --port ...`; the supervisor has its own `serve --config ... --port ... --health-file ...`. Do not assume administrative reset, queue or gate commands. The package publisher/installer staging and read-only verification syntax is documented in the indexed [CLI guide](CLI.md); it does not activate the workflow.

Author completion means the entire agreed feature is ready for owner testing, with focused checks and explicit unverified limits. Coded checks precede reviews. PASS is not owner acceptance; a later owner acceptance has its own separate regression. Pending is not a verdict. ERROR normally means recovery on the same run, not a new author revision; only an owner-retired ERROR head allows a fresh, non-replacement submission, as confirmed by status. See the role-specific documents for allowed actions.
