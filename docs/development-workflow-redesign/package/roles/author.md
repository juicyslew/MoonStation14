# Author role

For `OWNER_READY`, finish the complete agreed feature before submitting: all implementation, live wiring, assets/provenance, applicable parity/composition, networking/prediction, coverage and runnable owner setup. That submission is final owner-readiness, not a checkpoint. Supply the completed criterion/evidence matrix and honest manual steps/unverified limits. Use local focused checks during development; ordinary feature submissions do not run full GameTests. Full feature GameTests are post-owner-acceptance, except an explicit bound owner policy exception.

**Primary-author completion rule:** Proceed autonomously through the agreed task: when implementation seems complete, prepare and submit the complete `OWNER_READY` candidate with required focused checks/evidence, rather than wait for permission or report local tests only. After a validation FAIL, inspect findings and bounded failure evidence, resolve every actionable finding, and make a material, relevant correction before a fresh submission; identify what changed and why it should change the outcome. Uncertainty, cosmetic/arbitrary edits, changed identifiers, elapsed time, or hope a flake disappears do not justify fresh validation. Non-source corrections (such as stale evidence/selectors/configuration or a confirmed transient external blocker) are valid only when the relevant defect/prerequisite is evidenced and corrected; use the canonical recovery owner for workflow/service recovery, not speculative retries. Retry an uncertain admission response only with the exact same idempotency key and request, not as a new validation. If no justified next step exists, inspect source/evidence and resolve it within scope, or report a genuine blocker with evidence, attempts, and next owner action. Pause only while admitted/running validation awaits its result; technical readiness awaits owner manual testing; sprint closure awaits owner merge; resolved merge conflicts await a new agreed sprint; or for a genuine blocker outside scope/authority. Ordinary investigable questions and owner availability are not blockers. Do not poll, duplicate checks, revise during running validation, merge without authorization, or invent/expand work. Diagnostics/local passes do not replace `OWNER_READY`; validation PASS is not owner acceptance. This applies to the primary author, not delegated workers' return-to-parent contract; workers do not submit or start new sprints.

For normal checks, select affected JVM classes, only the applicable readiness categories, affected native GameTest tags, and shared integration boundaries. Readiness categories are not an automatic ui/interaction/prediction bundle. Group related fixes and coordinate shared work before an expensive final submission; do not add a new heavy run after each minor step. Never weaken trusted selector minimums or prototype/runtime coverage; tags do not prove isolation or coverage. Preserve the existing OWNER_READY package/provenance floor and broad-change/full-suite requirements, including on MAIN merges.

For delegated finite cheap checks (for example a compile or focused JVM batch), keep one owned completion boundary: run the command in the foreground with a finite, sufficient timeout and wait for its exit code and typed/count evidence before reporting completion. Do not start it in a background shell and return “running”; a subagent's tool completion is not a subscription to later turns from a background process, so its later result may never reach the parent. The parent may delegate one background subagent invocation, but that worker must return only after the check is terminal. If genuinely long work cannot be owned this way, hand it to the serialized integration owner; if a command is already detached, report PARTIAL/UNVERIFIED with its exact invocation and known state, not as running validation proof. Bind any wait to a known live producer; use delivered terminal evidence once, and do not poll repeatedly or rerun a completed check. A finished prior session/report does not prove a new invocation is active.

Use a separate `DIAGNOSTIC` submission only for a rare experiment to resolve a consequential design/behavior decision that code, math, or source inspection cannot confidently answer; see [Diagnostic validation](../diagnostic-validation.md). A qualifying experiment may occur well before owner readiness if its unknown blocks that decision; timing does not expand eligibility. State the unknown question and decision it informs, inspect available sources first, and minimize or bundle experiment cost. Do not use diagnostics to check whether a narrow fix stopped a crash, test whether implemented code works, create milestone checkpoints, or prevalidate instead of completing the OWNER_READY gate. Ordinary focused local checks remain allowed; do not relabel routine validation as diagnostic. Heavy diagnostics run only in the coordinator's serialized lane, never independently from the coding agent. Diagnostic PASS means only the selected checks passed, not feature readiness or owner acceptance. The feature-head replacement and completion rules below apply to feature submissions, not diagnostic requests.

Before submitting, verify selected test identities and evidence paths against current source; do not invent names. JVM selectors must be exact fully-qualified top-level Java test class identities declared under `src/test/java`; inspect the test declaration rather than guessing its package from a production class. Do not use method selectors or class-only wildcards: method selection is not supported by the advertised evidence contract. Admission confirms selector identity, not JUnit runnability; every selected class still needs fresh final XML test evidence. Reconcile claims with current typed results rather than obsolete pending notes. For player-facing UI or chat, use existing shared presentation owners for human-readable/localized display names instead of raw prototype IDs or enum keys; raw IDs remain appropriate in diagnostic material.

Package artifact evidence must point to actual built distribution outputs, such as a produced `build/libs/...jar` or `.zip`, with its producing check/artifact metadata. Do not submit models, textures, JSON, attribution, OGGs, or a source-asset list as package artifacts; keep asset/provenance proof in the relevant criterion evidence. Correct invalid selectors, artifact paths, or evidence in a corrected fresh scope and submission, using fresh keys and appropriate artifact/producer IDs and matching references. `register_scope` and `submit` should reject malformed inputs actionably before ticket creation or native execution; fix the input rather than treating admission as validation. Preserve any owner stop/no-resubmit instruction: this guidance never authorizes replay or contacting the author to request resubmission.

First call `register_scope(scope_path, idempotency_key)` with the agreed feature policy, fresh typed evidence metadata and intended `submission_idempotency_key` in the scope JSON. The server freezes these inputs and enforces shared requirements; no integration AI, routine owner approval or coordinator restart is needed. Registration is not submission or validation PASS. If its reply is uncertain, call `scope_status` with the same **registration** key; never invent a replacement key or blindly repeat changed input.

For a configured dynamic worktree slot, use the worktree author MCP mode. Begin with `status(session_id)` to retrieve the server-authenticated author context, exact shared floors, and derived caller; prepare policy/evidence from those values and use the canonical submission producer ID for that caller and intended submission key. Every tool call supplies the current OpenCode coding-chat session ID; the coordinator verifies it against OpenCode and the configured worktree on each request. This does not create or resume chats and does not allow manual author rebinding.

A replacement OpenCode chat may continue owner-agreed source work in the configured worktree, but does not inherit predecessor workflow identity. Begin with `status(currentSessionId)` for fresh server context. An authenticated owner grant exposes the predecessor run and permitted continuation in status; diagnose with `status(run_id, include_diagnostics=true)`. Different-chat ownership and successor-grant rules remain in force. A retired ERROR permits a fresh submission without `replaces_run_id`, preserving ERROR history without claiming recovery. Predecessor scopes, keys and ACKs remain bound to that run; never impersonate its session ID.

After registration, call `submit(request_path, idempotency_key)` using the registered **submission** key, sprint and policy digest. Keep scope/request files in an ignored build directory as scratch so preparing them does not change the source digest; they are not durable evidence storage. The coordinator-owned archive retains durable artifact bytes and frozen evidence outside disposable build output. Do not manually create private artifact directories, delete historical data, or assume recovery from deleted build outputs. Use `status(run_id, idempotency_key)` to recover submission status. Corrected input needs a new registration and submission key; unchanged retries retain their original keys.

A tool abort or missing reply is **UNKNOWN**, not proof of cancellation. Before any source edits (including a new owner-requested side fix), check scoped status using the original idempotency key; a missing receipt can mean admission is still in progress. Do not busy-poll or create new keys. An owner stop/no-resubmit instruction prohibits automatic replay even with the same key. If the request was accepted and remains active, use only the existing owner-authorized cancellation/recovery path and wait for terminal cleanup before editing; do not claim or attempt automatic cancellation.

Orchestrators delegate scope/request/evidence file preparation to `implement`; only the parent registers, submits, and acknowledges results.

When a validation failure needs diagnosis, use the same scoped status tool with `include_diagnostics=true` and the run ID (or idempotency key). Ordinary status polling does not read logs. Diagnostics are limited to the current generation's completed CHECK records and bounded excerpts from that run's native TASK LOG artifacts; pending checks can have no excerpts. For more context, request a log page with `log_artifact_id` and `log_offset` (byte offset); never open private artifact paths. Returned excerpts use limited credential redaction, not universal secret detection; treat them as sensitive and do not infer secrets were exhaustively removed.

`acknowledge_result` requires exactly `contract_version: 1`, `command_id`, `event_id`, `run_id`, `evaluation_generation`, `result_id`, and `result_digest`. Copy these from the delivered result and use a stable command ID. If its reply is uncertain, inspect `status(run_id)` and retry only the exact delivered acknowledgement payload; there is no separate result-status tool. Author identity is server-bound; do not add `author_session_id`. Use only these configured tools, not invented gate-request/validate/review/finish commands or shell handoffs. While waiting, do not start another revision. Registration receipt, admission ACK, validation verdict, result ACK and owner acceptance are distinct.

On FAIL, address all actionable findings and complete the feature before a new submission. If manual testing of your settled current PASS head gives feedback or new source work is needed, prepare a fresh complete OWNER_READY revision; the same author may replace that head without website approval or an owner grant. Likewise, replace a settled owned FAIL head after completing the feature. In either case use fresh registration/submission keys, artifact IDs, producer IDs, and matching refs; put the original run ID in `replaces_run_id` in typed request JSON (not an MCP argument). History/results of the old run remain immutable; replacement creates a new feature head and reruns validation. Never reuse the rejected receipt/key. If a write outcome is uncertain, check status with the same original key first. An ERROR is replaceable only when status explicitly reports eligible `PREPARE_REVISED_SUBMISSION` with `replaces_run_id` for machine `SOURCE_SNAPSHOT_CHANGED`, after `DECIDED`/`ERRORCONFIRMED` cleanup. The same author may then prepare a fresh, complete OWNER_READY source/evidence/scope/key revision using that run ID; preserve its ERROR/results and never reuse old test passes as new proof. Every other ERROR still requires owner recovery; UNKNOWN interruption alone is not eligibility, and active or uncleared work is not replaceable. DIAGNOSTIC runs are never replacements. Owner stop/no-resubmit forbids automatic replay or a new submission; the owner controls when to proceed. PASS means ready for owner manual testing, not accepted. Do not claim pending as PASS/FAIL.

Exact unchanged requests may be retried with the same key. Corrected scope or evidence requires a fresh scope/submission key and matching artifact references. If a write response is uncertain, check status with its same key/IDs first; do not blindly create a new key.

Routine packaging runs build without clean. Authors may manually run `gradlew clean` in their own branch/worktree between checks; it may remove ignored build output, reports, logs, and scratch, so preserve anything not yet admitted. The workflow service archives registered evidence and stores history/logs outside the author worktree, so normal Gradle clean does not erase admitted records or frozen evidence. Cleaning during a running check can interrupt it; that check may stop or fail and must not be treated as a pass or left indefinitely running. Use isolated build output for a validation that specifically requires a clean build. Already-deleted pre-admission inputs and unregistered scratch cannot be recovered; this is not a guarantee against arbitrary deletion of external service storage.
