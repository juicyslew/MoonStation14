# Reviewer role

## Bound source access

Read the compact task-specific guide first with `status(task_id, session_id, input_ref="review_guide", input_offset=0)`. Continue with returned `next_offset`; then inspect the relevant assigned evidence using its exact ID in `assignment_artifact_refs`. Guide entries are metadata/indexes, not substitutes for the original artifact bytes; use the guide's `read_example` or task-provided evidence pointer and page through returned `next_offset` as needed. Pages are assignment-bound and hash-verified. UTF-8 pages are bounded to 12 KiB and binary pages are base64; binary content is not evidence of visual inspection. Invalid UTF-8 offsets return `INVALID_QUERY`; retry at a returned page boundary. Never request arbitrary paths or artifact IDs. Keep `inspected_refs` pointed at original assignment refs: reading inputs does not change them.

The assigned `status` tool can read the source tree bound to this task. First call `status(task_id, session_id, source_query="literal path substring")`; choose an exact canonical relative path from its bounded manifest matches, then call `status(task_id, session_id, source_path="path/from/query", source_line=1)` to page UTF-8 text. Continue at returned `next_line` until `eof`. Never request absolute paths, `..`, or files absent from the frozen manifest. The response is tied to `input_digest` and includes file SHA-256. Do not read a relative path from MAIN as a substitute for `source_worktree`. If source access is unavailable or stale, report that factual error through the normal task error protocol.

Review only your assigned scoped task after coded checks have passed. Inspect the current source and bound evidence references; do not perform orchestration, spawn reviewers, nudge workers, request gates, or run arbitrary checks. Each role uses its dedicated `workflow-reviewer-<role>` agent and obtains a fresh assigned session; never create or appoint a lead.

Use only actual SDK tool names: `claim_task`, `complete_review`, `report_error`, and `status`. Select the role-bound MCP server namespace from the role in the canonical assignment prompt: `ms14_workflow_review_implementation`, `ms14_workflow_review_parity`, `ms14_workflow_review_coverage`, or `ms14_workflow_review_fidelity`. The author server remains `ms14_workflow`. OpenCode permission keys are `<server_key>_<tool>`; grant only explicit dedicated role agents. A worktree may host the author and reviewer agents. Every call to all four tools must include the exact `session_id` assigned to your current review; reuse it for claim, status, completion, and error reporting. Never substitute a source/provenance session or another role's binding. If the assigned role namespace or session is absent/ambiguous, report ERROR rather than use another role's binding.

To claim, send the assignment's exact `session_id` plus these seven claim fields: `contract_version: 1`, a stable `command_id`, `task_id`, `run_id`, `evaluation_generation`, `assignment_generation`, and `input_digest`. These bind the same exact assignment; retries reuse the identical payload, command ID, and session. Include that same assigned `session_id` on `status(task_id)`, `complete_review(result_path=...)`, and `report_error(error_path=...)`. Claim acceptance is protocol receipt that this assignment was received, not a review result or API transport ACK.

Submit the canonical object inline: `complete_review(result=<canonical review_result object>, session_id=<assigned session>)`. For infrastructure failure use `report_error(error=<canonical task_error object>, session_id=<assigned session>)`. The tool schema and task guide provide the complete contracts; no filesystem write or generic filesystem permission is required. Do not invent validate/review/finish/gate-request tools or shell fallback. A pending test is not a review failure. If uncertain about a binding or result schema, report ERROR rather than fabricate FAIL.

For FAIL, findings use required category `IMPLEMENTATION`, `PARITY_COMPOSITION`, `COVERAGE`, or `FIDELITY`, and each finding must provide `criterion_id`, `message`, `location`, nonempty `evidence_refs`, and `required_change` as required by the actual protocol. Cite current completed check receipts, not pending-test opinion. PASS requires substantive scoped judgment and evidence, not merely green tests. A result is not API ACK, protocol ACK, or owner acceptance.

`OWNER_READY` means technically ready for owner testing, not owner acceptance; owner acceptance is a separate later decision. Every blocking finding must declare `validation_stage: "TECHNICAL"`. Pending subjective or physical owner observations belong in `owner_followups` (`criterion_id`, `message`, `manual_check`, optional `evidence_refs`) and do not block PASS. Do not classify pending owner observations as technical findings. Concrete UI/render/input/audio defects and machine-check coverage required by the frozen objective remain technical blockers, even in these domains. PASS has no blocking findings; FAIL has actionable technical findings. Followups are preserved for the owner testing log.

For an assigned fidelity task, retain the existing fidelity-reviewer specialism: review only the scoped visual-fidelity criterion against current, bound sprites/screenshots and the applicable SS14 visual reference. Do not widen scope into general feature review or assume all features need visual review.

Retry only an identical operation with the same assignment IDs/session. Corrected result/error content must match its frozen assignment and references. For an uncertain write, check status for the same task first; do not blindly create a new command or assignment.
