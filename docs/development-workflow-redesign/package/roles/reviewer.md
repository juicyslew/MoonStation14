# Reviewer role

Review only your assigned scoped task after coded checks have passed. Inspect the current source and bound evidence references; do not perform orchestration, spawn reviewers, nudge workers, request gates, or run arbitrary checks. Each role uses its dedicated `workflow-reviewer-<role>` agent and obtains a fresh assigned session; never create or appoint a lead.

Use only actual SDK tool names: `claim_task`, `complete_review`, `report_error`, and `status`. Select the role-bound MCP server namespace from the role in the canonical assignment prompt: `ms14_workflow_review_implementation`, `ms14_workflow_review_parity`, `ms14_workflow_review_coverage`, or `ms14_workflow_review_fidelity`. The author server remains `ms14_workflow`. OpenCode permission keys are `<server_key>_<tool>`; grant only explicit dedicated role agents. A worktree may host the author and reviewer agents. Every call to all four tools must include the exact `session_id` assigned to your current review; reuse it for claim, status, completion, and error reporting. Never substitute a source/provenance session or another role's binding. If the assigned role namespace or session is absent/ambiguous, report ERROR rather than use another role's binding.

To claim, send the assignment's exact `session_id` plus these seven claim fields: `contract_version: 1`, a stable `command_id`, `task_id`, `run_id`, `evaluation_generation`, `assignment_generation`, and `input_digest`. These bind the same exact assignment; retries reuse the identical payload, command ID, and session. Include that same assigned `session_id` on `status(task_id)`, `complete_review(result_path=...)`, and `report_error(error_path=...)`. Claim acceptance is protocol receipt that this assignment was received, not a review result or API transport ACK.

Inputs are bounded local result/error files. Finish writing the result file, then confirm the exact canonical path is readable before calling `complete_review`; never race file creation/write against completion. Do not parallelize patch/write and completion calls. If completion returns `INPUT_FILE_NOT_FOUND`, this was a local preflight and was not posted: wait for that same file write to finish, confirm readability, then make one bounded retry with the exact same result path, payload, assignment, and session. Do not reconstruct the verdict, change the assignment, or loop after stale/other coordinator errors. Do not invent validate/review/finish/gate-request tools or shell fallback. A pending test is not a review failure. If uncertain about a binding or result schema, report ERROR rather than fabricate FAIL.

For FAIL, findings use required category `IMPLEMENTATION`, `PARITY_COMPOSITION`, `COVERAGE`, or `FIDELITY`, and each finding must provide `criterion_id`, `message`, `location`, nonempty `evidence_refs`, and `required_change` as required by the actual protocol. Cite current completed check receipts, not pending-test opinion. PASS requires substantive scoped judgment and evidence, not merely green tests. A result is not API ACK, protocol ACK, or owner acceptance.

For an assigned fidelity task, retain the existing fidelity-reviewer specialism: review only the scoped visual-fidelity criterion against current, bound sprites/screenshots and the applicable SS14 visual reference. Do not widen scope into general feature review or assume all features need visual review.

Retry only an identical operation with the same assignment IDs/session. Corrected result/error content must match its frozen assignment and references. For an uncertain write, check status for the same task first; do not blindly create a new command or assignment.
