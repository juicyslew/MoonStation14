01 · Executive decision

Change the transport boundary, not the validation contract

Recommend shared MCP service routes in the already-running coordinator, initially keeping the five author and four reviewer credential bindings. OpenCode connects over loopback HTTP. The coordinator reuses the current authenticated application operations, scheduler, store, and result owners. Local per-client stdio adapter children go away in the proposed design. Distinct fixed catalog profiles (at minimum author and reviewer) must retain separate SDK cache ownership; this is not one mutable catalog for all callers.

This is a sound architecture concept, but the observed 1.5 GiB working-set total does not justify assuming the implementation is successful—or that memory savings are already proven. Functional success and an acceptable idle-resource budget are separate acceptance criteria.

Schema

A tool name, description, and argument shape. Data; not a process.

Role

Author or reviewer responsibility, enforced by assignment and authorization.

Binding

OpenCode configuration: transport, credential, and tool namespace.

Connection

A protocol channel/session. Many channels can be served by one process.

Process

An OS runtime. Current local command transport starts a Python child; a binding does not inherently need one.

03 · Why the original design

Separate adapters were a reasonable seam—just not a free one

The distinction between what the design documents, what the architecture plausibly benefits from, and what acceptance missed matters. We should not invent a historical intention from a convenient implementation detail.

Evidence classWhat we can sayWhat we cannot conclude
Documented mechanismOpenCode uses a local command with the official MCP SDK over stdio. Each adapter translates MCP to the coordinator’s ordinary REST API, validates tool arguments, reads bounded files, and forwards authenticated session information. Per-role bindings make credentials/namespaces straightforward; local file reads resolve relative to configured repository context.This does not prove a separate process per role was a deliberate security requirement, nor that distinct runtimes are required by MCP.
Reasonable inferenceA thin adapter is easy to configure and keeps protocol dependencies and an adapter failure outside the coordinator process. A child process/event loop provides a distinct adapter failure and restart boundary.These are plausible architectural benefits, not documented historical rationale or measured fault-isolation guarantees.
Missed acceptanceThe installation design did not set a sufficiently explicit process-count or idle-memory budget. Thirty-two observed instances multiplied Python, SDK/dependency, and application-module loading.Do not call the count a proven leak, or assume nine bindings imply nine instances.
Plain language: stdio means private pipes between a host and a child process. HTTP means messages to an endpoint, proposed here on loopback only. The proposal does not claim HTTP is unsupported today, or that the SDK requires stdio, or that process separation is necessary for security. Feasibility source inspection found OpenCode remote-MCP support and Python MCP SDK 1.26.0 session-manager capability; that is not proof of a working mounted endpoint, private-header loading, or runtime savings.
04 · Explicit trade-off

What we gain—and what we give up

Moving MCP handling into the coordinator removes a runtime boundary. That is the main architectural loss, not a change to review quality or role count. Current adapters already call one coordinator, so the current system does not have nine independent workflow engines or endpoints.

DimensionCurrent local stdio adaptersProposed shared endpoint
Idle process replicationPython + SDK/application modules repeated per resident adapter instance.One shared endpoint; proposed zero long-lived Python stdio MCP adapter children. Savings remain unmeasured.
Adapter failure/restartOne adapter can fail or restart without restarting other adapters or coordinator.A shared MCP endpoint failure can affect all MCP clients at once. Its bug, memory growth, or blocked event loop can interfere with coordinator checks/review dispatch.
Identity stateProcess-local configuration naturally associates a child with its credential/repository.Must derive identity per request from validated credential and trusted mapping. No mutable global “current role”; session IDs are not credentials; worktree path is trusted configuration, not caller authority.
LifecycleHost starts a child; stdio EOF/disconnect provides a simple child lifecycle signal.SDK session/lifespan and bounded client cleanup/concurrency need correct implementation and verification.
Dependencies / event loopSeparate MCP SDK/event loop is an integration and release boundary.MCP SDK shares coordinator process resources. Blocking handlers or memory/CPU growth can affect unrelated coordinator work; no automatic isolation/retry guarantee.
Role separationSeparate configured credentials/namespaces.Initially keep the same five author + four reviewer identities and permission checks. Logical role separation can remain without process separation.
NetworkLocal child pipes.Loopback-only HTTP; no internet/cloud requirement. Loading private authorization headers from private token references remains unverified.

Gain: less replicated idle runtime, fewer child lifecycle surprises, and a reusable catalog. Cost: loss of adapter-level fault containment and process-local simplicity, plus new HTTP authentication, SDK lifespan, cleanup, concurrency, and event-loop responsibilities.

Alternative: retain stdio but investigate and bound duplicate instances and trim imports. This is a lighter near-term mitigation, but even nine current adapters are expected to retain substantial idle memory. CLI/native execution with an explicitly started coordinator can approach near-zero idle Python cost, at the expense of discoverability, convenience, and startup latency. Neither alternative needs a second validation engine.

05 · Functional contract stays put

Checks first. Reviews only after coded PASS.

Transport consolidation must not change the existing gate. The coordinator remains the admission, ordering, state, and result authority. Read-only discovery/status does not start validation or consume idle model inference.

Preserve three fresh review roles—implementation, parity, coverage—and optional fidelity review according to scope. Keep global serialization, validation receipts, existing task/session checks, and one durable ledger. Do not infer that connected bindings mean idle models or active review work.

06 · Feasibility / stop conditions

Credible direction; not integration-proven

This is not ready for cutover. A read-only audit of project code, installed Python MCP SDK 1.26.0, and the installed OpenCode executable found a credible route to remove local adapter children while serving MCP inside the existing coordinator. Source findings establish available mechanisms and specific hazards; they do not establish that the combined host, SDK, credentials, catalogs, permissions, and lifecycle work end to end.

Verified source finding: catalog cache trap. The SDK low-level server keeps its tool cache keyed by tool name; a tools-list operation can replace that cache, and calls use it for schema validation. Author and reviewer catalogs both have a status tool with different arguments. A single mutable server switching catalogs per credential can therefore invalidate another caller's schema under ordinary interleaving. Stateless HTTP does not repair this shared object state. The minimum safe direction is separate fixed author and reviewer catalog profiles, each with its own server/cache and correctly owned manager lifecycle, inside the same coordinator process. Distinct routes such as /mcp/author and /mcp/reviewer are acceptable. Retain any genuinely needed author-mode variant; do not invent nine new processes or collapse nine credentials into one. Reviewer roles may share identical catalog implementation without sharing authorization.

Unverified: private credential configuration. Embedded OpenCode file-backed config loading shows file substitution, but the audit did not prove that scoped PUT /api/experimental/mcp/:server applies that expansion. A file reference might be sent literally instead of a bearer token. Treat this as unknown, not confirmed broken. Before building the full bridge, run an isolated compatibility fixture with disposable credentials; verify endpoint receipt, persistence/reload, and absence of secrets from public config, receipts, logs, errors, and evidence. Stop if safe scoped loading cannot be demonstrated; do not add a credential-broker daemon as a workaround.

Compatibility is pinned to what is installed. SDK 1.26.0 uses the older initialization-based protocol, unlike newer 2026 documentation. Existing bindings pin protocol: legacy; retain supported legacy settings and codemode: false until tested. Do not copy latest wire semantics or assume automatic mode is compatible. The installed host must discover and call the fixture using the installed SDK.

Proof before expansion: exercise interleaved profile discovery and conflicting-schema calls; prove namespace, per-identity permissions, request-local identity and session isolation; reject bad credentials, wrong sessions/tasks/generations and cross-principal reuse. Verify authenticated loopback handling, bounded payloads, blocking-work offload, responsive status during slow work, and manager startup/shutdown/reconnect cleanup. Confirm equivalent REST/MCP operations, safe file handling, and lost-receipt recovery without duplicate effects. Measure reconnection/resource bounds and verify no adapter children; nine bindings must retain their names and credentials. Any uncertainty on these stops cutover, not merely documentation.

Evidence was source inspection only: no live transport, credential, provider turn, production task, or proposed runtime was exercised. Existing 192-check installation evidence certifies the old arrangement, not this design. The ordered fixture plan, source locators, and audit qualifications are in MCP-FEASIBILITY-REVIEW.md.

07 · Decision boundaries

Targets are proposals; open questions stay open

Proposed, unmeasured resource targets: zero long-lived Python stdio adapter instances; at most 200 MiB combined private commit for long-lived Python components including shared MCP; at most 250 MiB incremental idle private commit including host-attributable delta. These are engineering goals, not owner-approved limits or predictions.
  • Why did 32 instances remain resident? Lifecycle cause is unresolved; investigate before any process cleanup.
  • Can private credential references become remote HTTP headers safely? Installed OpenCode source capability is not proof of scoped runtime loading. No committed bearer values, public receipts, or logs.
  • Can the official SDK lifespan manage concurrent sessions and bounded disconnect/reconnect cleanup? Verify with a fixture.
  • Does an in-process MCP handler preserve async responsiveness, authorization, payload bounds, and exact existing behavior? Reuse shared application operations; do not perform blocking self-HTTP calls.
  • What is the actual idle memory/CPU delta? Measure host baseline and connection-attributable increment separately, repeated reconnect/replacement stability, then active validation separately. No future RAM bar is presented as measured.

Recommendation is not implementation approval. Any bounded runtime replacement requires explicit authorization after functional, identity-isolation, lifecycle, and resource evidence. No owner acceptance is implied by this proposal.

Bottom line: shared-process MCP can standardize invocation and remove replicated adapter runtimes while preserving nine identities, but source-confirmed catalog/cache hazards and unverified credential, authorization, and lifecycle integration remain material stop conditions. Adapter-level fault isolation is also reduced; memory benefit is unmeasured. This is a credible direction, not cutover-ready.
