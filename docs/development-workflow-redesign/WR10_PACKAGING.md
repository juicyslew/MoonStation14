# WR10 packaging and staged publication

This is a WR10 source architecture note, not an activation instruction. The old observer remains the sole live owner until WR12. Keep changes in the new inactive package namespace; do not edit published workflow instructions in this task.

## Authority and package boundary

The implementation authority is `tooling/agent_workflow/`: `workflow_coordinator.py` owns local service assembly, `workflow_coordinator_mcp.py` supplies thin role-bound tools, `workflow_store.py` owns durable lifecycle state, and the existing execution/review/result-delivery owners do their respective work. `workflow_runtime.py` remains the canonical runtime filename. Runtime protocol schemas are under `docs/development-workflow-redesign/contracts/`. See [DESIGN](DESIGN.md), [WR04](WR04_COORDINATOR.md), [WR06](WR06_REVIEWS.md), [WR07](WR07_DELIVERY.md), [WR08](WR08_RECOVERY.md), and [WR09](WR09_BOARD.md) for detailed contracts; these role documents deliberately summarize rather than duplicate them.

All workflow state, artifacts, configuration, secrets and inference-independent execution stay local; only AI inference uses the provider. Admission, scheduling, task dispatch, cancellation, verdict aggregation, delivery/recovery and owner decisions are coordinator-owned. A reviewer or author never assumes scheduler authority.

`package-docs.json` in the staged package is the explicit source-to-future-installed-target index. Its `version: 1` and `files` entries use MAIN-relative source paths and installed-root-relative targets. It is an index contract, not proof of publication. Examples are disabled placeholders, have no credentials or real session identifiers, and are not runnable production configuration. Private context/auth files and databases/artifacts must live outside worktrees and package output. See role/config examples and [runtime guide](package/README.runtime.md).

The existing coordinator loader expects `database`, `artifact_dir`, `opencode_server`, `bindings`, with optional `reviewers` and `owners`. Binding secrets are external token files. Reviewer mappings bind role to `session_id`, `worktree`, `agent`, `token_file`, and `caller`; owner entries bind token file/caller/worktree and optionally session ID. Submission context has exactly `repo`, `authenticated_author`, `policy`, `artifacts`, `publication_receipt_path`, and `publication_receipt_sha256` (see `workflow_submission._context`). Do not put those credentials or live context in checked-in examples.

Role-specific OpenCode server namespace is required because one worktree may host the author and all four configured reviewer sessions: `ms14_workflow` for author, then `ms14_workflow_review_implementation`, `_parity`, `_coverage`, and `_fidelity`. Each uses its role's existing fixed token. SDK tool names remain `claim_task`, `complete_review`, `report_error`, `status`; permission keys use `<server_key>_<tool>`. Prompt role selects the namespace; this is not a new SDK selector/protocol. Never overwrite a shared fixed-token server or automatically create/rebind sessions. Preserve configured models and grant only explicitly existing agent-bound role permissions.

Dependencies belong in separate `.venv-workflow-coordinator`; preserve `.venv-workflow-mcp`. Pins: `mcp==1.26.0`, `starlette==1.8.0`, `uvicorn==0.54.0`, `anyio==4.15.1`, `jsonschema==4.26.0`; httpx 0.28.1 is currently transitive and must not be represented as direct unless code decides otherwise.

## Publication boundary

The actual stage-only publisher interface is `publish_workflow.ps1 -CoordinatorPackage -PackageStage <absolute-stage> -PreviousReceipt <receipt> [-BindingPlan <private-absolute-json>]`; it rejects `-Apply` and other publication/activation modes. Allowed stages are exactly MAIN's WR10 build stage or a unique private OpenCode temp child. Stages are immutable/fail-stale; do not overwrite failed stages. Binding plan is optional and does not imply complete target bindings or cutover. Its exact version-1 target/role contract, installer default plan and `-VerifyOnly -PythonPath` metadata check are documented in the package [CLI guide](package/CLI.md) and grounded in current source. `-Install` is deliberately refused in WR10. The intended source name stays `workflow_runtime.py` in the installed layout (no duplicate implementation or compatibility runtime). Existing legacy publication remains default and unchanged. WR10 source and static package-fixture checks do not mean the active/published installer or configuration was changed or applied; no live publisher/installer action, service, scheduler, or configuration mutation occurred. Unknown/unowned differences stop publication; never overwrite or clean them speculatively.

## Future cutover/recovery constraints

WR12 must obtain a fresh live baseline; WR01 evidence is historical, not permission to overwrite. Hold intake and explicitly drain/resolve active identities before any ownership transition. Never disconnect tools while active work depends on them or run two schedulers. Preserve SQLite using its proper backup mechanism (including WAL state), artifact evidence and receipts; do not blindly copy a hot database. Publication must be receipt-owned and hash-verified; unknown ownership stops.

Rollback may restore only files proven publisher-owned by the current receipt, and only when their current hashes still match the published bytes. It does not rewind SQLite, verdicts or owner decisions, replay old validation, or resubmit authors. Provider pause is not inferred from HTTP health. Unknown cleanup keeps a scoped hold while leaving the board usable; resolve explicitly rather than deleting a clock/marker. Owner UI/manual actions must be taken from activated source and tested in WR12; do not invent endpoints or controls.
