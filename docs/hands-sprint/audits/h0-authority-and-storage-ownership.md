# H0 — authority and storage ownership audit / handoff

**Status: read-only audit; not implementation approval.** No runtime behavior, upstream parity, exhaustive packet-hook coverage, or connected acceptance is claimed here. The Creative/non-Creative inventory policy is decided in the [hands sprint Instructions](../Instructions.md) and [inventory program Instructions](../../hands-inventory-program/Instructions.md); this audit does not claim that a safe implementation has been established.

## Findings: actor, body, and lease authority

- `GhostMobHarnessControl.activeHarness(ServerPlayer)` (`src/main/java/com/juicyslew/moonstation14/ms14/player_body_control/server/GhostMobHarnessControl.java:929`) is a read-only snapshot lookup, not a general actor resolver. It requires the exact connected, non-`FakePlayer` session object; a committed session; a living carrier; current `SPECTATOR` mode; not riding; a live/eligible current harness; and a registry mind whose id, harness id, and epoch match the session. For character sessions it further verifies the exact stored body and `eligibleCharacter`; for ghost sessions it returns the ghost harness. It does not itself call `BodyControlRegistry.authorizes` and is documented not to revoke ownership.
- `activeCharacterBody` (`GhostMobHarnessControl.java:954`) filters that snapshot to `MobHarnessKind.CHARACTER`; ghost sessions return empty. `ActiveCharacterPolicy.activeCharacterBody` is only a forwarder (`.../ActiveCharacterPolicy.java:26`). Pending character offers are not active character bodies: the session remains ghost-kind until the handoff transfer and subsequent readiness commit (`GhostMobHarnessControl.java:433-461`, `:385-396`). Thus active-body eligibility is narrower than “player has some session” and should be the starting admission test for body-owned features, with explicit policy for lifecycle-owned bodies outside this experimental controller.
- The debug controller starts its carrier in `SPECTATOR` (saving its prior `GameType`) and commits only after the ready handshake (`GhostMobHarnessControl.java:269-304`, `:385-396`). Character and ghost eligibility both require `SPECTATOR` (`:639-649`); `activeHarness` repeats this requirement (`:933-935`). Thus Creative vanilla inventory and committed harness control are mutually exclusive under the inspected harness: actual Creative uses vanilla inventory, while an eligible non-Creative body uses body-owned hands/equipment/item-owned storage and no vanilla Survival inventory. If another system changes the carrier to Creative, the session may remain recorded/committed transiently, but `eligible`/`activeHarness` cease to authorize it. Session end restores the prior game type only when the carrier is still `SPECTATOR` (`:965-974`). This is **not** a safe mode transition implementation: it does not define inventory parking, transition ordering, or recovery of contents. Audit and test those mechanics; do not assume safety or reopen the decided policy. If a safe no-loss handoff cannot be established, stop for engineering/owner review rather than weakening the policy. Do not reinterpret the carrier’s required `SPECTATOR` mode as permission to access Creative inventory during committed body control.
- `BodyControlRegistry.authorizes(sessionId, harnessId, epoch, eligibility)` (`src/main/java/com/juicyslew/moonstation14/ms14/player_body_control/BodyControlRegistry.java:814-833`) validates connected mind, exact epoch and harness binding, owner index, registered target, and caller-supplied target eligibility. Invalid experimental (non-lifecycle-owned) targets are detached and epoch-advanced; invalid lifecycle-owned targets simply return false. It is synchronized pure in-memory ownership state and does not authenticate a packet or inspect the world; caller must supply authenticated identity and current target evidence (`:11-14`). It is harness/mind authority, not item or inventory ownership.
- `GhostMobHarnessControl.eligible` combines player/session identity, connected/alive state, spectator mode, same-level/current target checks, and `registry.authorizes` with a live ghost or `eligibleCharacter` predicate (`:639-660`). Character eligibility checks configured marker, UUID/entity identity in the `ServerLevel`, alive/not removed/not passenger, movement-ownership marker, and `GroundedHarnessLease.isOwnedBodyEligible` (`:651-660`). The acquired `GroundedHarnessLease` is movement ownership; do not assume it is an inventory lease.
- `CharacterIdentitySystem` enrolls only supported `ServerPlayer`/`Mob` actors through the centralized enrollment adapter and refuses replacement of an existing identity (`src/main/java/com/juicyslew/moonstation14/ms14/character/CharacterIdentitySystem.java:35-67`). `resolve` reads an already-present, bound attachment against the current server catalog without materializing data (`:69-87`). This is character-profile identity, not proof of current player control. `ActiveCharacterPolicy.resolveActor` explicitly returns empty for an experimental carrier before falling back to character identity (`.../ActiveCharacterPolicy.java:15-24`). On possessed-body calls, resolve/use the body identity; never infer body authority from the carrier’s profile or UUID.
- `CharacterControlSystem.canAct` is only `!isStunned` (`src/main/java/com/juicyslew/moonstation14/ms14/character/CharacterControlSystem.java:140-142`). `isStunned` requires server level, a resolvable eligible character whose `canReceiveStun` policy is true, and an active status whose definition includes `STUN_ACTION_BLOCK` (`:56-74`). It is an action-status gate, not a harness/lease or vanilla-inventory eligibility check. For experimental carriers, `ActiveCharacterPolicy.resolveActor` returns empty, so the current stun predicate does not establish a blanket inventory gate for the controlled body.

## Existing action/pickup seams and inventory-path audit boundary

- `ServerPlayerStunActionMixin` (`src/main/java/com/juicyslew/moonstation14/mixin/ServerPlayerStunActionMixin.java`) calls `CharacterControlSystem.canAct`, i.e. stun policy only. Inspected handlers include player input/movement, item use/use-on, interaction, player action (drop and offhand swap get inventory resync on denial), container click, and creative-slot packet (`:33-107`). The two latter paths are also currently denied only when stunned, not because a body is eligible for hands. This source inspection does **not** establish that every vanilla inventory mutation/action route has been hooked or is gated for the proposed feature.
- `ServerPlayerStunPickupMixin` (`src/main/java/com/juicyslew/moonstation14/mixin/ServerPlayerStunPickupMixin.java:12-20`) cancels `ItemEntity.playerTouch` only for a stunned server player. It does not gate pickup for an eligible controlled body, nor prove other item insertion routes are covered.
- Before vanilla inventory disablement is implemented, route inventory must be audited beyond these two mixins: player inventory/hotbar and offhand, armor/equipment, open inventory/container menu clicks and drag/close behavior, item use and swap, drop/pickup, creative-slot packet and other Creative actions, commands/operator paths, modded insertion, death/clone/logout/reconnect, and mode changes. Verify NeoForge/Minecraft event and packet ordering against the pinned runtime. Existing mixin method names are leads, not a completeness claim. A route-by-route verified matrix and focused tests are a gate.
- Preserve unaffected actors: no new gate should change ordinary players/entities or bodies not admitted to this feature. Pending handoff, ghost-only sessions, stale/uncommitted controller state, and non-eligible bodies must fail closed for body-owned inventory without gaining a new carrier-side route. Determine explicit behavior for a supported body with no current experimental `activeCharacterBody` before coding; do not silently broaden the experiment’s admission rules.

## Ownership/parity facts to carry forward

- The umbrella resolves the scope: body owns hands and named wearable equipment slots only. Storage is owned by the storage item; grids are not intrinsic body inventory. Pockets are garment-gated: access requires the appropriate garment worn, with removal policy for nonempty contents (prefer move-with-garment when safe, otherwise reject; never spill implicitly or move contents to a body pocket). The item-location ledger is a location/transfer contract, not a second body container.
- The umbrella identifies the SS14 human inventory template at `Resources/Prototypes/InventoryTemplates/human_inventory_template.yml`: `pocket1` and `pocket2` depend on `jumpsuit`; `suitstorage` depends on `outerClothing` plus `AllowSuitStorage`; `belt` and `back` are named equipment slots. These are template dependency/access semantics, not evidence that pocket contents are physically stored in the garment. The planned garment-backed ownership model remains a deliberate design requirement to validate against pinned upstream source; do not claim local implementation or exact upstream parity from these references.
- The umbrella’s upstream targets for later pinned-revision parity inspection include `Content.Shared/Inventory/InventoryComponent.cs`, `InventoryTemplatePrototype.cs`, and `InventorySystem.Equip.cs`; hands targets are listed in the hands instructions. This H0 does not claim that those upstream files/tests were fetched or verified. Distinguish those future parity checks from the local Minecraft authority findings above.

## Admission, no-change paths, and safe first implementation boundary

**Recommended first implementation tranche after H0 approval:** a server-only, read-only eligibility/admission seam for the explicitly approved body population, returning the exact authenticated active body (and a reasoned rejection) without creating or moving items. Bind later requests to the server-resolved body plus current authority/session revision; do not accept a client body id as authority. First integrate only one verified vanilla admission/disablement route at a time after inventory-route mapping, and prove rejected requests leave all slots, cursor, drops, and item counts unchanged. Keep unrelated actor behavior unchanged. Do not begin grid storage, named wearables, UI, persistence, a carrier bridge, or Creative access in this tranche. The no-loss handling of already-populated vanilla slots must be designed before any disablement can ship.

No-change/rejection paths required at that boundary: actor not an authenticated server carrier/body; no active committed character body; ghost-only or pending offer/return; body no longer live/eligible or identity unresolved; stale/replaced harness epoch; carrier not in its required mode; stunned where the operation is an action; unsupported body capability; and any validation/transaction failure. Each must reject without mutating item state. A gate must not detach/reset a body-control lease or alter lifecycle ownership as a side effect.

Umbrella policy is resolved (not reopened here): actual Creative uses vanilla inventory. Outside Creative, an eligible body uses only body-owned hands/equipment and item-owned storage—no intrinsic body grid and no vanilla Survival inventory. A committed harness requires a Spectator carrier, so Creative and committed body control are mutually exclusive. Before enabling body authority, audit every vanilla slot/hotbar and mutation route and establish how pre-existing vanilla contents are parked separately; on return to Creative, restore those exact contents without merging/copying them into body holdings. Body-owned items remain body-owned on Creative entry. The policy is fixed, but this audit has not established safe no-loss parking/restoration or transition ordering: verify and test them, and stop for engineering/owner review if they cannot be made safe. Do not assume existing contents are empty or transitions harmless.

## Stop gates and planned implementation tests

Do not proceed from audit to runtime changes until all applicable gates pass:

1. Owner reviews the body admission population and confirms authority source, identity relation, no-change semantics, pre-existing-content handling, and scope. No changes to lifecycle/body-control ownership are implied; coordinate with those owners if required.
2. Pin and inspect relevant SS14 hand/inventory/template sources and tests; record parity and deliberate divergences. Confirm garment-dependent pocket access and item-owned container ownership rather than treating dependent slots as physical storage.
3. Complete route-by-route vanilla inventory and carrier-transition audit. Demonstrate eligible-body vanilla disablement without a second Survival owner and no changes for unaffected bodies. Inventory pre-existing contents rather than assuming empty slots; prove exact parking/restoration and no loss/duplication across entry/exit and mode transitions. Confirm that the Spectator-only committed harness and actual-Creative vanilla mode remain mutually exclusive. The policy is settled; unsafe or unproven handoff mechanics are a stop gate, not a request to decide whether Creative may use vanilla inventory.
4. For implementation, plan pure tests for admission/identity/epoch/rejection rules; targeted dedicated-server GameTests for authoritative server resolution and each changed vanilla route; conservation tests for slot/hotbar/menu/creative/drop/pickup transitions and failed operations; lifecycle tests for disconnect, ghost/lease/body change, death/body loss, reconnect, and persistence only when those policies are approved. Add authenticated two-client acceptance only under its separate gate. Unit tests, FakePlayer coverage, docs, or successful compilation alone do not establish connected acceptance.

**Fail/stop:** ambiguous body authority; inability to isolate pre-existing vanilla contents; an unverified mutation route; any route that permits eligible non-Creative vanilla ownership; mode transition that can lose/duplicate items or bypass authority; a requirement to alter another sprint’s code/lifecycle ownership without coordination; or inability to implement the decided mode policy safely. Do not claim implementation approval, connected tests, or acceptance here.
