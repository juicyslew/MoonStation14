## Proposed MS14-owned no-item entry and target contract

1. **Typed authority and scope.** Server-only, exact committed CHARACTER lease/body/epoch from `BodyActionAuthority`, re-resolved before attempt and commit; no carrier hand, proxy player or fake `ServerPlayer`. Each supported operation must have an individually audited target handler and admission contract; unknown target/operation denies. Do **not** implement a global prototype allow-list as a substitute for target-specific behavior/access. Distinguish simple contact from complex manipulation (live enabled `ComplexInteraction` plus independent status/stun); neither is target permission. No generic `Block` fallback, entity interaction, mining, item use, hand/menu/inventory, passive `stepOn`/`entityInside`, or vanilla target grant. Future optional vanilla-target adapters require individual exact-version source audit and tests, not blanket permission.
2. **Composed entry checks.** Bind the request to the actual connection, reject stale/ambiguous lease and unusable/dead/wrong-level body, and enforce operation-specific ability/status, owned hand/item requirements where applicable, target identity/state and bounded server-derived reach/face/LOS. Require world border/build limits and already-loaded target **and ray-path** chunks as engine safety, not an access policy: bound/prevalidate intersected chunks and prove the getter cannot cause loads; recheck before effect, STOP if no-load proof fails. Never trust the client hit or Spectator eye/range. SS14's ~1.5 interaction units are not a Minecraft-block reach setting.
3. **Target-specific access, not region ownership.** For each audited operation define its target-specific access decision and cancellation/handling points: e.g. door-like credential/state/access gating, lock-like toggle attempts/lock access, storage-like contained-target accessibility, or an operation-specific floor placement restriction **only if that operation is supported**. Do not call access a pure predicate without proof: upstream door/reader paths have exceptions and successful checked access can log. Absence of a particular gate is not a universal allow: default-deny missing adapter/unknown required state, while a deliberately unrestricted MS14 target can allow under its documented contract. No global spawn/claim check for MS14-controlled bodies, no assumption of third-party claim providers or mod player hooks. If a future optional external integration/vanilla target is required, audit it separately and fail closed for that target when its required gate cannot apply to the body; do not claim generic interoperability.
4. **Ordering and effects.** Resolve lease/target → run proven pure entry/geometry/state prechecks → perform only the chosen target's audited access and veto/handling sequence → revalidate mutable pure conditions before the bounded effect → report result. Access, vetoes and callbacks are potentially effectful; do not tentatively call access and then recheck it at commit unless an audited side-effect-free preview is distinct from commit, or separately audited ordering and idempotency prove repeated calls safe. Revalidate access at commit **only** under such a proven design; otherwise STOP before enabling the route. A successful access log followed by denial, or two success logs for one attempt, is not an innocuous read. `Cancelled` is a denial only at the specified attempt site; `Handled` can suppress later fallback but is not rollback or a promise of no earlier effects. No universal rollback is available for earlier callbacks/logs. No emulation of NeoForge `RightClickBlock`, `BreakEvent` or arbitrary listener cancellation using the carrier. Document expected denial and success effects, idempotency, races and failure semantics for the chosen target; a sound call is not guaranteed audible and is **not** pre-approved. Item/structural actions additionally need their own transactional ownership, timing, drops and interruption rules.
5. **First implementation gate.** No no-item target is currently selected. Select an upstream-supported operation only after its target code and side effects are audited; do not reinstate a placed-jug no-hand sip as an invented alternative. Before any packet/effect, record exact handler/state transitions, denial order, status/hand requirement, access decision and its side effects/preview-versus-commit sequencing, reach/LOS and loaded-path algorithm; acceptance tests must cover valid body, missing/disabled complex capability when required, stun, stale epoch/competing controller, wrong dimension/dead/unloaded target/path, out-of-range/occluded/changed target, access denial, cancellation/handled fallback, duplicates/replay/out-of-order/rate limits, contention, denial without unintended effect and precisely bounded success (including access logs or other observable checks). Revisit prepared-session ambiguity and experimental-registry read-only lookup. No fixture is authorized by this document; later targets require their own evidence and tests rather than another broad owner product choice.

This contract scopes an SS14-like MS14 path, **not** generic vanilla parity or an M2 pass. No source or action route is implemented here.
