## Current code: exact Player callback order (not the proposed body path)

1. Vanilla/NeoForge Player dispatch, **if it reaches the block**, is described in [M0](m0-block-action-route.md): packet/game-mode admission and `RightClickBlock` precede block callbacks for that route; Spectator gets menu-only handling instead of activation. The registered jug's `useItemOn` fetches the BE; a reagent item and reagent BE call `ReagentSystem.handleTransfer(item stack → BE, 5f)` on server and return sided success. Otherwise it returns `PASS_TO_DEFAULT_BLOCK_INTERACTION` (`JugBlock.java:56-69`). This is not a generic guarantee that an arbitrary held item or body reaches `useWithoutItem`.
2. `useWithoutItem(BlockState, Level, BlockPos, Player, hit)` fetches the BE, requires `IReagentTrait` and `ServerLevel`, then calls `StomachSystem.ingest(blockHolder.toHandleSelf(), player, serverLevel, UNITS_PER_SIP)`; on positive return it plays `GENERIC_DRINK` at `player.blockPosition()` with `SoundSource.PLAYERS` and returns `SUCCESS`, otherwise `PASS` (`JugBlock.java:72-85`; `util/Constants.java:3-5`: `UNITS_PER_SIP=5f`, `SIP_INTERVAL_TICKS=20`). The placed-block click has **no 20-tick sip interval**; that constant governs held `JugItem.onUseTick` (`JugItem.java:69-129`), which is outside this candidate. The callback itself has no lease/epoch, status, dead, mouth, loaded-ray, reach, LOS, jug identity beyond reagent BE, or target-specific veto check. Its `hitResult` is not inspected. Do not treat direct callback tests as packet or protection tests.
3. `JugBlockEntity` implements `IReagentTrait.toHandleSelf()` (`ms14/reagent/IReagentTrait.java:5-14`), so `ReagentSystem.bridgeForHolder` chooses shared `REAGENT` for this non-living BE (`ReagentSystem.java:63-70`), **not** the body's blood or stomach. `StomachSystem.java:41-57` gates ingestion on server/same-level, positive finite request and `ThirstSystem.isEligible`: the temporary entity-type tag and `!ActiveCharacterPolicy.isCarrier` (`ThirstSystem.java:33-41`). This is not a mouth/organic organ prototype, a live status gate, or proof that every controlled character is eligible. `ingest` does not itself reject dead/dying targets (`StomachSystem.java:51-57`; compare `vomit` at `:123-125`). Missing stomach state is read detached; successful ingestion creates it, rejected/full ingestion does not (`MS14Provider.java:33-70`). It validates both reagent maps against the server catalog and cent-converts them; admits at most the request, available source and free 50-unit stomach (`StomachSystem.java:59-111`). A 5-unit request can accept a smaller positive dose; source empty, full stomach, invalid reagent or sub-cent admission returns zero without that sip's writes.
4. On positive admission `ingest` stages source and stomach separately, calls `MS14Provider.updateIfChanged(sourceHolder, sourceBridge, ...)` **first**, then `updateIfChanged(target, STOMACH, ...)`, then enables `REAGENT_METABOLISM` activity and returns the admitted amount (`StomachSystem.java:107-115`). `updateIfChanged` compares the supplied *before snapshot* to the staged component, **not** a live compare-and-swap (`MS14Provider.java:164-188`). For a BE, update sets attachment, calls `setChanged` and sends block update (`:97-106,132-148`); jug `setChanged` recalculates 0–6 fill state with `setBlock` (`JugBlockEntity.java:84-100`), and its packet/update tag transports BE attachment to rendering (`:37-81`). The body attachment update also updates activity (`MS14Provider.java:108-111`); ingestion explicitly enables metabolism afterward. Later digestion, not ingestion, processes hydration/reagents (`StomachSystem.java:45-49`; `StomachGameTests.java:215-260`). The sound follows these writes only on `consumed > 0`, not guaranteed audible. **There is no atomicity proof for the two persisted source/stomach writes, no rollback if the second write or callbacks fail, no contention lock/CAS, and no end-to-end cancellation or transport.** Do not claim that cent-conserving staged arithmetic makes the whole world operation transactional. Nor does the Player callback have an audited target access/veto sequence of its own; potential earlier Player-route events are not replicated by calling it directly.

## Withdrawn route sketch — historical technical stop gates, not an implementation plan

**Cross-agent dependency — organ conversion, not yet landed in this branch:** another agent is converting the codebase toward component-based organs. Any later upstream-supported ingestion route needs explicit **live body organ/mouth/stomach capability**, not the temporary `thirst_eligible` entity-type tag. Today `StomachSystem.isEligible` still delegates to `ThirstSystem.isEligible` via that tag; no organ system or organ API is implemented here. `ComplexInteraction` alone proves neither a mouth nor a stomach and must not imply ingestion eligibility. Reconcile the actual landed organ components, lifecycle and API before specifying admission tests; do not invent a parallel organ architecture or presume that organ work automatically unlocks drinking. This audit enables no body action.

The earlier `SIP_PLACED_JUG` no-held-item sketch is **rejected as a playable proposal**, not a backlog action or basis for a handler. It depended on exact body authority, usable body, mouth/status, loaded jug BE and reagent capacity, yet supplied no SS14 evidence for drinking directly from a placed jug without an actual item. `ComplexInteraction` and the temporary thirst tag cannot supply that missing interaction or mouth capability. If the specifically chosen upstream SS14 drinking action uses a held item, require an actual body-owned item and hand; no carrier inventory substitution. Do not implement the old no-hand sequence.

The old sketch's geometry, body/target veto, access side effects, replay and paired-write failure questions remain examples of why the local callback and direct reducer cannot authorize any body action. The local jug handler has no credential/access reader or jug-specific cancellation event; that absence is **not** a universal allow or inherited NeoForge event veto. No synthetic carrier proxy, fake player, vanilla event emulation, spawn-region protection or presumed external claim integration. Any future drinking design must start from a verified upstream interaction and independently specify its actual item/hand, mouth, target, interruption and commit rules; do not carry the withdrawn no-item action forward.
