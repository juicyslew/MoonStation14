## Rules for planning and implementation

- Fail closed for ghosts, missing/stale sessions, non-capable bodies, invalid epochs, unsupported actions, and unusable/stunned bodies. The carrier is Spectator; vanilla player-only action/stun hooks do not authorize the body.
- Re-resolve the actor, current body, epoch, action capability, held item/equipment, status, world target, reach/visibility, permissions and applicable timing on the server at commit time. No client target, item, or result is authoritative. Reject stale/replayed requests, rate-limit, and make conflicts atomic.
- Prototype action capabilities and tool qualities should be optional and strictly schema-validated/data-synced. Do not import a broad upstream prototype model or silently grant defaults.
- Audit the exact NeoForge 21.1.224 / Minecraft 1.21.1 callbacks before selecting adapters. Existing CrowbarItem, StationFloorTilePryItem, JugBlock, BottleItem and JugItem callbacks use player-parameter APIs: they are fixtures for compatibility investigation, not proof that a body actor can call them safely. Do not fabricate a `ServerPlayer` as authority or silently fall back to carrier behavior.
- Record each action's actual inspected upstream SS14 evidence separately from the proposed Minecraft adaptation. Do not infer parity or claim that approximately 1.5 SS14 interaction units equal Minecraft blocks.
- Keep stages small. At each gate, record exact tests and stop for owner review if platform APIs require unrelated ownership, lifecycle, or mode changes.
