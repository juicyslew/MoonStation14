# Scoped worker workflow

This project uses bounded implementation workers and a central integration/readiness lead in `MoonStation14-agent-05`. A primary author (`orchestrate-ms14` or `3d-modeler`) automatically submits a ready candidate to the central gate; the gate runs in 05, not in the author worktree, and blocks progression until its result. It is not a daemon or passive review queue. Expensive shared-machine validation is serialized. Inadequate candidates receive `needs_changes` and actionable evidence; the author fixes and resubmits. A pass produces a concise manual-testing log and notifies the owner. Significant work/sprints require explicit owner acceptance; automation never accepts them. Authors can run cheap focused JVM/unit and compile checks. Users may select workers in their TUI; no CLI launcher or separate coordinator terminal is required. Read-only helpers report to their parent; the primary author owns submission. No unrelated-session broadcast, continuous polling, duplicate LSP/game processes, or unrequested bulk feature work is implied.

## First steps

1. Read root `AGENTS.md` and identify the task owner, scope, and applicable handoff. Read only matching readiness contracts. For art, consult the sibling [Asset Building Workspace guide](../../../Asset%20Building%20Workspace/docs/development-workflow/README.md), [current model handoff](../../../Asset%20Building%20Workspace/MODEL_HANDOFF.md), [asset registry](../../../Asset%20Building%20Workspace/asset_locations.json), the exact package README, provenance/license, manifest/binding contract, and its read-only validator. Those package records—not a gallery's newest timestamp—define current status and complete retrieval.
2. Work only in the assigned worktree and files. Do not commit, merge, release, reset, delete, or overwrite another worker's work. Do not alter asset registries/guards or workspace art unless specifically authorized.
3. Run narrow, cheap changed-behavior checks and record evidence. Submit the candidate using current authoritative [CLI.md](CLI.md)/helper help; the primary author automatically dispatches the serialized gate to 05. On `needs_changes`, address cited gaps and resubmit; do not treat the candidate as technically ready meanwhile. After a pass, give the owner the resulting manual-testing log and state remaining unverified boundaries. Do not run expensive shared-machine validation directly.

## Shared handoff utility

The authoritative command/schema reference is [CLI.md](CLI.md), supplemented by the helper's current `--help`. Use `python tooling/agent_workflow/workflow.py --help` and relevant subcommand help if the installed interface differs; never invent arguments or rely on stale examples. The default exchange is file-backed and shared by worktrees via Git's common directory, under the sibling Asset Building Workspace `work/agent_exchange`. It does not mutate Git or game sources. No automatic process supervision is implied.

The canonical CLI modules, shared workflow docs, and role contracts are published once to sibling `MoonStation14-shared`. Run `pwsh -NoProfile -File tooling/agent_workflow/publish_workflow.ps1` from MAIN for a dry-run plan. The privileged installation owner applies publication with `-Apply`; one-time `-BindWorktrees -PreviousReceipt <receipt>` also installs the thin local CLI shims, role headers, shared-folder permissions, and workflow-section links, and retires only receipt-verified duplicate modules/docs. Future publications need not rebind. Changed files are backed up and hashed in the receipt under the approved OpenCode temp directory; unknown or unreceipted edits stop rather than being overwritten or deleted. It does not alter global OpenCode config or gameplay/assets.

The intended code lifecycle is focused author checks → ready submission → automatic integration-lead gate (repeat author correction/resubmission until adequate) → manual-testing log and owner notification → explicit owner acceptance for significant work/sprints. Asset handoffs retain their request → claim → plan/deliver → independent report → owner decision lifecycle. Use [request-template.json](request-template.json) for modeling requests, following current [CLI request guidance](CLI.md). Delivery is a copied, hashed handoff—not creator ownership, art acceptance, import, or installed runtime behavior. Import remains dry-run until explicit owner acceptance and authorization; use the CLI's source/destination hash and stale-evidence safeguards. Never guess “latest” or overwrite to bypass review.

## Integration gate

The primary author's structured submission automatically dispatches the `integration-lead` review in central worktree 05 and waits for its result. Use the current CLI contract in [CLI.md](CLI.md) and helper `--help`; do not invent arguments. The gate is synchronous and bounded, not an unattended service. Only the central gate runs expensive shared validation, through the serialized workflow runner. On failure it reports specific fixes to the author; it does not ask the owner whether the author should fix. On pass it records manual steps/boundaries and notifies the owner. Users may select roles in their TUI; no CLI launcher is required.

## Role profiles

- [Coordinator guide](coordinator.md) and [integration-lead role contract](roles/integration-lead.md): serialized technical gate, correction/resubmission loop, and concise manual-test handoff. No merge/commit/release authority.
- [Source fidelity review guide](source-fidelity.md), [review report template](review-report.md), and [fidelity-reviewer role contract](roles/fidelity-reviewer.md): evidence-driven independent visual review. A readiness recommendation is not owner acceptance.

Scoped profiles declare role-specific model, reasoning effort, color, and least-privilege permissions. Workers and read-only helpers stay within their assigned worktree (and may read the shared handoff); the central integration lead may inspect a submitted candidate read-only in its author worktree. It does not implement author fixes; the author retains that responsibility. The fidelity reviewer may write only designated review-report directories; source, asset, package, manifest, and queue edits are not permitted. Tool permissions scope direct operations but do not make shell a filesystem sandbox; follow each role's constraints.

For gameplay changes, reuse existing shared service/prototype owners and obey applicable prediction/authority and feature-readiness contracts. Automated tests establish only their exercised scope; report connected-client, visual, full-suite and owner-review boundaries honestly.
