# Shared coding-gate contract

This is the single policy for the serialized integration/readiness gate. It applies only to actual mod-code changes (including runtime, prototypes, installed map data and build configuration). Pure design/prose and non-mod process/tooling work use bounded relevant checks and the existing review/publication route, not a coding candidate. Root `AGENTS.md` and applicable readiness contracts remain authoritative.

## Submission boundary

Authors own and edit their gate-plan file before submission; submission reads and freezes that plan into the candidate. Tools do not generate or maintain author plans. To change a submitted plan, create a new plan file (for example `gate-plan-r27.json`) and submit a fresh candidate/revision; never edit the frozen plan in place or assume a file edit changes an existing candidate. The plan specifies check intent/coverage and fixture data, not execution deadlines or cleanup controls. A readiness submission must be complete and owner-manually-testable: include accurate setup/check steps and expected results. Missing behavior, wiring, assets, setup or planned implementation means keep implementing; do not create artificial milestones. A technical pass means only ready for owner testing, never owner acceptance, merge or release. The author owns corrections and submits a fresh revision after `needs_changes`.


After the scoped MCP binding is enabled, an author uses one `ms14_workflow_submit` call to submit and request the gate; the observer delivers updates, so agents do not poll. Eligible current admitted submissions are automatically queued by the observer through the existing execution owner. The integration lead independently reviews code, parity and evidence; it does not decide whether the frozen checks start. It uses only role-bound `ms14_workflow_validate`, `review`, `finish` and `status` tools. Validate remains idempotent for the existing job. These tools do not expose runtime/deadline, path, retry or cleanup controls. Until a change is published and verified, do not claim it is active; the CLI reference is administrative/debug documentation, not normal agent workflow.

Use diagnostic-only submission only when a lead-owned native check is genuinely needed to implement or diagnose not-yet-ready work. It is not a readiness exception or milestone approval. Its diagnostic plan binds an immutable author snapshot, existing named lead and exact serialized checks; do not use it for routine author-cheap checks or broad validation. The CLI reference gives the schema and command.

## Independent review and execution

The lead checks candidate identity/freshness, changed code, adequate changed-behavior coverage, plan adequacy, and relevant evidence; then runs the exact adequate plan through the serialized runner without silently skipping or altering checks. For gameplay, assess applicable SS14 ancestry/defaults/runtime-consumer mapping, source references and parity/departures, shared-owner reuse, prediction/authority and readiness contracts. Bugfixes need not repeat feature prototype audits. Applicable visual work requires independent fidelity review and exact evidence bindings; hashes do not prove quality. Unknown, unavailable, stale or failed evidence is not a pass. A green command summary alone is not a verdict.

For GameTest, let a running batch finish to collect all failures. If it fails or lacks required evidence, skip later unstarted checks. Other typed FAIL/UNKNOWN may fail fast; report partial validation as failure, never approval. The worker owns fixed maximum deadlines, startup/crash handling and cleanup; do not disable safeguards or add caller timeout/wait controls. Verify exact source, plan, logs and artifact freshness; changed code has no carried-forward receipt.

`gate-validate` returns a job ID and state, not a test result. The lead must end its turn while work is pending, and MUST NOT retry checks or change the plan to force completion. One existing observer launches a finite worker from the bound claim; execution record is a sidecar to the existing candidate. API acknowledgement proves admission only, not execution. Both final readiness verdicts require a completed matching execution receipt and collected current requested scoped reviews. `NOT_RUN` or pending work cannot be finalized as `needs_changes`; a refused pending finish means await observer completion, not resubmit. The worker owns fixed deadlines and cleanup. Interrupted checks remain explicit operational blocks, not technical verdicts. Quarantine only actual unknown cleanup; agent confirmation cannot clear a live PID. Diagnostic completion is delivered with its bound receipt even on FAIL. Readiness completion resumes the exact existing lead for independent review/finalization; failed checks can support rejection, never readiness. Preserve durable state; do not add a daemon or queue.

Diagnostic completion is `diagnostic_complete`: return the bound receipt/findings to the author even when checks fail. It needs no readiness report/finalization or manual-review entry and cannot be promoted by ready/report/publication/candidate-review paths. A fresh readiness submission with implementation, checks and manual-ready steps is required for owner readiness. In readiness mode, record the independent finding using the existing report/finish flow, finalize notification, then give the owner 3–5 concise numbered manual actions (fewer for a tiny fix) with expected visible results and unverified boundaries. The lead does not implement or claim owner acceptance. Keep handoffs concise; retain full evidence in machine records.
