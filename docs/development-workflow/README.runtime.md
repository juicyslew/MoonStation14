# Scoped worker workflow

The serialized integration/readiness gate applies only to changes to actual mod code. Mod runtime, prototype, installed map data, and build-configuration changes remain in that workflow; do not use the process-work exception to bypass required mod checks. Pure design/prose/concepts work and code that changes only non-mod processes or tooling (for example workflow tools or browser atlas tooling) do not create a coding candidate or invoke the gate: run direct, bounded relevant checks, obtain independent review where appropriate, and publish the result/receipt through the process's existing route. This is owner policy, not a file-classifier or CLI migration.

For mod-code candidates, bounded implementation workers use a central integration/readiness lead in `MoonStation14-agent-05`. The gate session is rooted in 05 while checks execute in the candidate author's worktree. The request waits for a persisted candidate verdict, not OpenCode session idleness. A timeout yields pending, not pass or rejection; the author stands down awaiting completion and resubmits only if the candidate is stale. Final `gate-finish` sends a deterministic-ID short steering notice to the author for either verdict. If delivery fails, the lead may retry `gate-deliver ID --actor integration-lead`; this retries notification only, not tests. API acknowledgement does not prove the author consumed the message. Expensive shared-machine validation is serialized. Significant work/sprints require explicit owner acceptance; automation never accepts them.

## First steps

1. Read root `AGENTS.md` and identify the task owner, scope, and applicable handoff. Read only matching readiness contracts. In restricted shells use the workflow CLI as one command per shell invocation; use the provided `read` operation for JSON and `glob` for listing. Do not use `Get-Content`, `Get-ChildItem`, compound housekeeping commands, or broaden permissions after a denied operation. A denial of one incorrectly formed command does not establish that all CLI use is blocked. For art, consult the sibling [Asset Building Workspace guide](../../../Asset%20Building%20Workspace/docs/development-workflow/README.md), [current model handoff](../../../Asset%20Building%20Workspace/MODEL_HANDOFF.md), [asset registry](../../../Asset%20Building%20Workspace/asset_locations.json), the exact package README, provenance/license, manifest/binding contract, and its read-only validator. Those package records—not a gallery's newest timestamp—define current status and complete retrieval.
2. Work only in the assigned worktree and files. Do not commit, merge, release, reset, delete, or overwrite another worker's work. Do not alter asset registries/guards or workspace art unless specifically authorized.
3. For mod-code work, run narrow, cheap changed-behavior checks, record evidence, and submit using current authoritative [CLI.md](CLI.md)/helper help for dispatch to the serialized gate. For non-mod process/tooling code or pure design/prose/concepts, do not submit or dispatch a candidate: run direct bounded checks, independent review as appropriate, and publish a concise result/receipt through the existing process route. The remaining gate/correction rules apply to mod candidates: an explicit operational `blocked`/`api_unavailable` stop is not `awaiting_review`; permit only a small bounded same-session correction; do not create another reviewer, validator, or session, and do not rerun checks when a valid receipt already exists. If correction fails, report operationally blocked—never fabricate a technical verdict. Pending permission is not permission. Stale/superseded scope needs a fresh revision. On `needs_changes`, address cited gaps and resubmit. After a pass, give the owner the manual-testing log and unverified boundaries. Do not run expensive shared-machine validation directly.

## Shared handoff utility

The authoritative command/schema reference is [CLI.md](CLI.md), supplemented by the helper's current `--help`. Use `python tooling/agent_workflow/workflow.py --help` and relevant subcommand help if the installed interface differs; never invent arguments or rely on stale examples. The default exchange is file-backed and shared by worktrees via Git's common directory, under the sibling Asset Building Workspace `work/agent_exchange`. It does not mutate Git or game sources. No automatic process supervision is implied.

The canonical CLI modules, shared workflow docs, and role contracts are published once to sibling `MoonStation14-shared`. Run `pwsh -NoProfile -File tooling/agent_workflow/publish_workflow.ps1` from MAIN for a dry-run plan. The privileged installation owner applies publication with `-Apply`; one-time `-BindWorktrees -PreviousReceipt <receipt>` also installs the thin local CLI shims, role headers, shared-folder permissions, and workflow-section links, and retires only receipt-verified duplicate modules/docs. Future publications need not rebind. Changed files are backed up and hashed in the receipt under the approved OpenCode temp directory; unknown or unreceipted edits stop rather than being overwritten or deleted. It does not alter global OpenCode config or gameplay/assets.

The intended **mod-code** lifecycle is focused author checks → ready submission → automatic integration-lead gate (repeat author correction/resubmission until adequate) → manual-testing log and owner notification → explicit owner acceptance for significant work/sprints. Pure design/prose and non-mod process/tooling work instead follows direct bounded checks/review and its existing receipt/publication route, without a candidate or gate. `ready_for_owner` is a technical gate outcome, not the owner decision. A fresh ready submission creates an owner-review request; newer submissions in the same author worktree and sprint supersede older requests. Independent worktrees or sprints remain separate. Human feedback on a pending request returns responsibility to the agent for triage and removes that request from the owner attention list. This is conversation/input, not acceptance, sprint closure, completion, or test success. Automated/synthetic completion is filtered; ambiguous multiple-project feedback is not assigned, and the observer does not clear other sessions. Asset handoffs retain their request → claim → plan/deliver → independent report → owner decision lifecycle. Use [request-template.json](request-template.json) for modeling requests, following current [CLI request guidance](CLI.md). Delivery is a copied, hashed handoff—not creator ownership, art acceptance, import, or installed runtime behavior. Import remains dry-run until explicit owner acceptance and authorization; use the CLI's source/destination hash and stale-evidence safeguards. Never guess “latest” or overwrite to bypass review.

## Integration gate

The primary author's submission dispatches the integration-lead session rooted in 05; checks run in the author's worktree. The bounded request waits for a persisted candidate verdict and ignores OpenCode-idle state. Timeout is pending, not pass/rejection. Final `gate-finish` sends a deterministic-ID short notice for both verdicts; `gate-deliver ID --actor integration-lead` retries notification only. API acknowledgement is not proof of message consumption. The owner can run `./integration-status.ps1` to open the local auto-refreshed board (no HTTP server); it presents **Needs your attention** review requests separately from gate outcomes and owner decisions, alongside elapsed time, logs, stale heartbeat and notification state. Unknown health is shown as unconfirmed; telemetry is secondary, not readiness proof or acceptance. A bounded feedback observer starts after ready publication and via the status launcher; it polls bounded known origins through the existing authenticated CLI every 10 seconds, reading the user projection and inbox. It reconciles messages after each exact review-request boundary; existing handoffs require a candidate/snapshot-bound announcement timestamp, never installation time or file mtime, so feedback after announcement but before installation is still processed. It exits after idle grace. This is not a general validation daemon or new backend/build/job; the gate queue remains passive.

## Role profiles

- [Coordinator guide](coordinator.md) and [integration-lead role contract](roles/integration-lead.md): serialized technical gate, correction/resubmission loop, and concise manual-test handoff. No merge/commit/release authority.
- [Source fidelity review guide](source-fidelity.md), [review report template](review-report.md), and [fidelity-reviewer role contract](roles/fidelity-reviewer.md): evidence-driven independent visual review. A readiness recommendation is not owner acceptance.

Scoped profiles declare role-specific model, reasoning effort, color, and least-privilege permissions. Workers and read-only helpers stay within their assigned worktree (and may read the shared handoff); the central integration lead may inspect a submitted candidate read-only in its author worktree. It does not implement author fixes; the author retains that responsibility. The fidelity reviewer may write only designated review-report directories; source, asset, package, manifest, and queue edits are not permitted. Tool permissions scope direct operations but do not make shell a filesystem sandbox; follow each role's constraints.

For gameplay changes, reuse existing shared service/prototype owners and obey applicable prediction/authority and feature-readiness contracts. Automated tests establish only their exercised scope; report connected-client, visual, full-suite and owner-review boundaries honestly.

## Sprint-local evidence lifecycle

The prepared MAIN CLI requires `--sprint SPRINT_ID` on coding `submit`; the validated sprint identity is snapshot-bound. Gate receipts, scoped-review copies, and captured command logs are scoped to the author worktree at `build/agent-workflow/<sprint_id>/reports/`, which must be Git-ignored. The central worktree need not share the author's Git common directory. The lead writes nonvisual decisions with `gate-report ID --actor integration-lead --result needs_changes|ready_for_owner --finding TEXT` (repeat `--finding` for additional bounded findings). Visual ready decisions require a completed `gate-scope-review` receipt supplied as `--scoped-review review|fidelity-reviewer`; the CLI checks exact report identity and copied/original image hashes and attributes inspection to that reviewer, not the integration lead. Finalize using the returned report path. Scoped-review image copies retain their existing source/copy hash checks.

This evidence is temporary for the current actionable candidate(s), not a permanent archive of completed failures. Once a sprint is explicitly closed, inspect `sprint-cleanup --repo AUTHOR_WORKTREE --sprint SPRINT_ID` (dry-run). Apply only with an explicit nonblank `--owner-reference`; this records a cooperative closure acknowledgment, not technical pass or authenticated owner acceptance. Cleanup refuses pending admitted gates, unfinished scoped reviews, and selected quarantined process ownership. It removes only matching new-format candidate records and report/log/image files explicitly bound by those candidate receipts; unexpected files under the sprint folder are reported and preserved while empty directories are pruned. It does not remove producer-owned logs outside the managed directory, native JUnit/build artifacts, caches, run data, worlds, legacy unbound records, or asset requests. Keep any durable handoff and owner-acceptance record separately.

These are the installed workflow commands and permissions. The coordinator is a neutral directory, not a Git worktree; when invoking the CLI there, supply `--asset-workspace "../Asset Building Workspace"` to status, gate, and cleanup commands. This selects the existing shared exchange and does not create a second queue. Gate and scoped-review report paths are computed from the candidate author's worktree and returned by the CLI; use those paths for `gate-finish` rather than writing in the coordinator.
# Maintenance intake holds

An owner-maintained `gate-maintenance.json` in the exchange root pauses new coding submissions and gate requests. A held command prints JSON with `status: held` and exits successfully: continue scoped work and wait for an explicit resume; this is neither a review result nor a failure. Holds do not retry, poll, create sessions, or create candidate records. The owner may list explicit `allowed_candidate_ids` for verification candidates during a cutover. A previously prompt-admitted gate request may finish; no other request bypasses the hold. Malformed hold metadata fails closed with a diagnostic.
