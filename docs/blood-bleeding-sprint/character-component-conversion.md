# Character slip target component conversion

## Entity-aware component consumers

Gameplay component reads now use `resolveForActor(entity)` on the server (including pressure reads against an explicitly supplied catalog snapshot) and `projectForActor(entity)` for client presentation/prediction. A registered, live player-character harness with a valid saved binding and matching HUMAN identity receives the same declared components as a mapped vanilla human host without adding its entity type to `human.json`. The server verifies the binding and live entity; client projection cannot authenticate an owner or saved binding. The pure `resolveForHost(catalog, id, host)` remains host-only for fixtures and automatic enrollment. Experimental carriers remain suppressed by `ActiveCharacterPolicy`; the legacy configured-mob movement lease deliberately requires mapped-host ownership. Missing, invalid, wrong, or dangling identities do not expose components. Existing saved state is not erased when eligibility fails.

The client fog/HUD/status/movement queries are presentation or prediction only. Server-side movement, hands, physiology, and hazards continue to resolve server authority. A valid but different client catalog revision may predict different behavior until synchronization catches up; no owner authentication is inferred from client state. Validation: `gradlew.bat build --no-daemon`, `gradlew.bat compileGameTestJava --no-daemon`, and `git diff --check`; GameTest fixtures were compiled, not executed.

## Fire stacks and eye damage eligibility

Human and pig independently opt into the marker-only typed `Flammable` and `Blindable` character components. Both accept only `type` in complete definitions and inheritance fragments; no other host gains eligibility from vanilla type or an existing attachment. The server checks the current bound identity, actual host, and current prototype snapshot for each operation. `FIRE_STACK` and `EYE_DAMAGE` remain mutable saved state, not eligibility configuration. Removing a marker leaves saved state intact but inert; reconciliation drops dormant drying activity, and a stale due drying flag cannot change the retained stacks. `EyeDamageSystem.damage()` deliberately reports raw saved damage for diagnostics even when ineligible; `isBlind()` requires `Blindable` and does not project blindness from dormant damage.

These markers map to upstream `Content.Shared/Atmos/Components/FlammableComponent.cs` and `Content.Shared/Eye/Blinding/Components/BlindableComponent.cs`. Fire stack arithmetic, drying, and eye-damage threshold/floor/clamp remain shared **local approximations**; vanilla `fireImmune()` additionally denies fire eligibility (Minecraft-specific departure). There is no upstream ignition, fire-damage, or vision simulation here.

## Hunger, Thirst, and Stomach enrollment

Human (player and villager hosts) now declares three independent typed markers `{"type":"Hunger"}`, `{"type":"Thirst"}`, and `{"type":"Stomach"}`; pig declares none. Each marker accepts only `type`, including in inherited fragments. Stomach additionally requires a `Bloodstream` component in the resolved character (not Hunger or Thirst), so ingestion cannot admit contents without a body destination. The old `thirst_eligible` entity-type tag is no longer used. Server needs and stomach ingestion/vomit resolve the current bound character identity and actual host against the current catalog, suppress experimental carriers, and fail closed when the marker is absent. Saved hunger/thirst scalars and stomach contents remain readable and are not erased when a marker is removed, but become inert; attachments alone never enroll an entity. Bloodstream metabolism remains independent of stomach eligibility. On the staggered 20-tick retry, absent eligible hunger/thirst state initializes after late catalog publication without replacing an existing scalar. The client HUD checks its current client catalog snapshot, bound identity, actual host, and matching marker before showing an existing need scalar; it does not call the server-only entity resolver.

The hunger and thirst init ranges, decay, alerts, thresholds, and speed penalties, and stomach capacity remain unchanged shared **local system behavior**, not per-species prototype tuning or full upstream parity. Component count is bounded to 32 (host entity types remain bounded to 16); human currently has 19 distinct types including the separate fire and eye markers. This adds no pig need enrollment and no new hunger/thirst/stomach mechanics.

Character prototypes no longer accept top-level `slip_data` (including `null` and abstract-parent declarations). Convert old target policy explicitly to `components`; there is no migration fallback. Reagent `slip_data` remains separate source-side chemistry configuration.

| Old target field | Character component | Admission |
| --- | --- | --- |
| `standing_eligible`, `prone_eligible` | `{"type":"StandingState","standing_eligible":true,"prone_eligible":true}` | Standing is required before contact; prone governs knockdown/sliding publication. This is local eligibility policy, not standing mechanics. |
| `no_slip:true` | `{"type":"NoSlip"}` | Suppresses the slip after qualifying contact latches. Omit for `false`. |
| `can_receive_stun:true` | `{"type":"Stunnable"}` | Permits stun/action-block checks and slip admission. Omit for `false`. |
| `reactive_groups`, `reactive_methods` | `{"type":"Reactive","reactive_groups":["flammable","extinguish","acidic"],"reactive_methods":["touch"]}` | Both lists must be present, canonical, distinct, and either both empty or both populated. Omission denies Touch admission. |

Human carries StandingState true/true, Stunnable, and Reactive; Pig carries StandingState false/false and NoSlip. Pig has neither Stunnable nor Reactive. A missing component does not acquire default capability. The policies preserve the existing local Minecraft approximation rather than introducing new gameplay or asserting upstream Pig semantics.

The character component merge is keyed by `type`: inherited markers remain present, and a child can patch individual fields of an inherited StandingState or Reactive component. There is no `remove` directive; unknown fields, malformed raw fragments, duplicate entries and noncanonical reaction values are rejected. The resolved component set is encoded for network snapshots and round-trips through the strict codec. Runtime actor resolution continues to use the bound identity and matching host type; an unbound or mismatched actor does not gain these capabilities.

Validation: `gradlew.bat build --no-daemon` and `gradlew.bat compileGameTestJava --no-daemon` (compile only; no GameTest server). Residual limitation: StandingState's booleans and Pig's inert selection remain local target policy approximations, not new standing/prone simulation.

## Metabolizer capability

Move top-level `metabolizer_types` to `components:[{"type":"Metabolizer","types":["human"]}]` (pig uses `"animal"`). The root field is rejected even when `null` or declared on an abstract parent; there is no fallback. `types` is required, canonical, distinct, and may be empty. Absent component means unavailable capability; present empty `types` means available but matching no types. Inherited component patches replace `types` atomically, without a remove/tombstone directive. Runtime resolves the verified bound host and supplies the same optional set to both existing bloodstream and stomach metabolism stages. This is the **current flattened mob capability**, not upstream organ-owned Metabolizer parity; stage-specific organ ownership remains separate future work. No new organ or metabolic stage is introduced.

## Grounded movement policy

The registered player-character harness is not a `host_entity_types` entry: that field remains for automatic vanilla host enrollment. Its explicit server resolution requires a live exact registered body, a valid saved account/profile/Mind binding, a bound HUMAN identity, the current HUMAN prototype, and no host claim for the custom type. Parked bodies need no active controller. The host-only resolver remains strict for players, villagers, and pigs. The client may project a synced HUMAN identity for display/prediction, but cannot authenticate the saved binding; the server independently verifies it before movement. A missing or malformed binding, missing/wrong identity, stale entity, or dangling prototype is inert.

Automatic spawn/load and late blood/lung enrollment exclude the exact registered harness entity type before consulting the host index, even if a future reload candidate maps its host ID. Players, villagers, and pigs retain mapped-host enrollment. Only the trusted explicit binder can assign the harness identity in production; a manually staged identity without a saved binding remains inert at actor resolution. The mapped-host candidate GameTest is compile-only validation here, not a live reload or GameTestServer run.

Move the old root `movement` fields unchanged into `components:[{"type":"MovementSpeedModifier","mode":"grounded", "acceleration":20.0, "walk_speed":2.5, "sprint_speed":4.5, "ground_friction_with_input":20.0, "ground_friction_without_input":20.0, "minimum_friction_speed":0.005}]` for human (pig walk/sprint are both 4.0). The root field is rejected, including `null` and abstract declarations. Complete components require every field; inherited fragments may patch individual fields, but provided fields must be valid and the resolved policy has no defaults. No movement mechanics were added. The .4 knockdown speed factor remains one shared pinned runtime rule, not prototype data.

Server experimental movement resolves the currently bound identity against its current host-owned server catalog on each owned tick; client prediction and snapshot correction resolve the client catalog and client identity each tick, including sprint correction bounds. If either side lacks its matching decoded component, it stops custom stepping/initiates the existing handoff rather than using a human default. Human-only experimental enrollment remains unchanged. **Sync risk:** the existing movement protocol does not transmit a catalog revision or policy hash, so different *valid* server/client catalog revisions cannot be detected as mismatched without a networking change; the server remains authoritative and correction may snap until the catalogs agree. An unavailable client catalog fails closed instead of guessing values.
