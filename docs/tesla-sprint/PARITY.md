# Tesla composition and parity map

Reference checkout: `SS14-dev/space-station-14`, verified at `c9df5ef5d675b0d1d226828bddf6b78c28502d91`. Upstream paths below are relative to that checkout. This mapping does not claim complete SS14 parity.

## Resolved upstream composition

- **`BaseEnergyBall`** is a root abstract prototype (`Resources/Prototypes/Entities/Structures/Power/Generation/Tesla/energyball.yml:1-33`): clickable, kinematic/in-air physics, air movement, chasing walk, ambient sound, blue light, appearance and lightning shooter.
- **`TeslaEnergyBall → BaseEnergyBall`** (`energyball.yml:35-121`) adds hard collider radius `.55`, non-hard consumer radius `.65`, event horizon radius `.5`, Tesla energy/growth and chaotic jump. It adds sprite, spawn audio, navigation/ghost warp tags, petting popup and guides. Periodic tile/entity consumption is disabled; collision consumption remains active.
- **`TeslaMiniEnergyBall → BaseEnergyBall`** (`energyball.yml:123-156`) overrides chase targeting/speed and adds a `.35` fixture, 120-second despawn, sprite and non-power-dependent electrification. It has no energy, event horizon or jump and cannot reproduce. Both fixture mask and layer are `None`, with no inherited base fixture. Robust's collision filter (`Robust.Shared/Physics/Systems/SharedPhysicsSystem.Contacts.cs:324-328`) therefore rejects ordinary wall/field contacts.
- **`TeslaGenerator → BaseStructureDynamic → BaseStructure`** (`Tesla/generator.yml`; `Structures/base_structure.yml`) inherits transform, clickability, gravity, physics, fixtures, pullability and structure tag. Dynamic overrides anchoring/physics and adds anchoring support. Generator overrides sprite/fixture and adds the existing singularity-generator behavior with Tesla spawn identity, outline and guides.
- **`TeslaCoil` and `TeslaGroundingRod` are independent roots** (`Tesla/coil.yml`): anchored/static machinery, fixtures, sprites/appearance/visualizer, lightning sparking/target, pulling/rotation/anchoring, structural damage, examination/repair/destruction and guides. Coil additionally has animation, battery/discharger, HV node/network-battery and Tesla coil behavior. Rod inherits no battery.
- Other direct-lightning composition: `EmitterSmallConstructibleMachine → ConstructibleMachine → Machine` (LT1); APC and Airlock directly inherit LT1; Substation resolves through its verified ancestor chain to floor (no direct LT1 target composition). The emitter composition is not a general protection guarantee: connected emitter and power-box counterparts below are explicit Minecraft direct-target adaptations, not inferences from upstream inheritance. Generators, fields and walls lacking direct LT1 composition are not thereby universally immune to incidental effects.

## Local composition and live owners

`ModTeslaProfiles` registers resolved `tesla_ball` and `tesla_machine` catalogs in `PrototypeRuntime`. Typed base/main/mini profiles preserve inherited defaults and absent behaviors. `TeslaEnergyBallEntity` consumes these for energy, movement, collision, contact, firing, lifetime and audio. Collision policy resolves to `WORLD_AND_FIELDS` for main and `NONE` for mini. `TeslaLightningSystem/Selection` consume resolved source lightning and target data. `LightningTargetComponent` is registered in the character codec/schema and composed into supported mobs; observers are excluded. Machine profiles reuse that target codec.

`TeslaMachineBlockEntity` consumes finite storage/strike/supply/flash data. `PowerLiveLoop` attributes actual delivered HV supply; `PowerRuntimeNode` settles that energy, so an empty coil cannot export electricity merely by publishing an offer. The shared generator/startup owner selects resolved spawn entity/profile; one PA swept-receiver path serves both reactors. `ReactorContactConsumption` shares native death admission. `ReactorBlockConsumption` shares loaded-world block eligibility/removal/cable cleanup without replacing singularity's periodic cadence or credit rules.

## Owner-feedback corrections and Minecraft adaptations

- Minis now pass through blocks and fields while retaining loaded-span admission. Their explicit local contact-shock check is separate from physical collision response; it is an adaptation, not a claim that upstream zero-mask fixtures generate bump contacts.
- Main physical contact consumes eligible breakable blocks and explicitly reactor-consumable machinery, including coils/rods. The `.65` contact segment is evaluated after field clipping and before world-block bounce. This maps upstream colliding machine/wall entities to Minecraft blocks; it is not a periodic terrain sweep. Bedrock, connected containment generators and unapproved inventory block entities remain protected. Startup-generator removal retains its separate originating-source UUID proof. Lightning eligibility alone never authorizes block consumption.
- Living consumption retains the port's native-death/corpse policy rather than deleting linked bodies. Block machinery is fixed; upstream towing/tool anchoring is not reproduced. Huge/Ginormous block-item carry metadata is local, not an upstream Item component.
- Current energy and last admitted input kind/amount/tick are server-side runtime diagnostics, not persistent history. They cannot explain inputs from an earlier owner run. Default names use the existing examine/name path, preserving custom names.
- **PA-only vertical tolerance:** upstream `ParticlesProjectile → BaseBullet` is defined in `PA/particles.yml:1-52` and `Objects/Weapons/Guns/Projectiles/projectiles.yml:50-96`. PA replaces the inherited fixture with a non-hard `.48` AABB and overrides radiation to 25, lifetime to 3 s and `deleteOnCollide` to false. Local `base_bullet → particle_accelerator_particle` retains those values. Resolved `energy_receiver_vertical_padding: 1.0` is explicitly Minecraft-only: the reactor capture ellipsoid keeps horizontal radius (receiver plus particle half-extent), adding one block vertically. Zero padding reproduces spherical capture. Living radiation contact, generator contact, energy per hit, physical reactor contact and gravity are unchanged. Large cages are not guaranteed complete beam coverage.
- Motion adaptation: SS14 Tesla motion is 2D chasing/jump behavior; Minecraft retains 3D jumps and vertical pursuit. Its `moonstation14:base` chasing profile sets targetless vertical-velocity half-life to 1.0 s only while no valid remembered target exists; no gravity or horizontal drag is added. Upstream `ChaoticJumpSystem.Jump` spawns `EffectEmpPulse` at the old position immediately before moving (`Resources/Prototypes/Entities/Effects/emp_effects.yml`); Minecraft renders the copied eight-frame `emp_pulse` visual only, without EMP gameplay effect or advance warning. Sprite metadata preserves attribution/license; resource is `src/main/resources/assets/moonstation14/textures/ss14/effects/emp.rsi` (CC-BY-SA-3.0; tgstation source/commit metadata is retained in its metadata). This is wired; native/visual acceptance is pending.
- Shared PA particle overlap bookkeeping caches living-entity overlaps only, leaving receiver capture to the exact receiver ellipsoid; otherwise a broad physical-box overlap could pre-mark and discard a valid PA capture. The behavior is shared by Tesla and Singularity consumers and adds no PA geometry/strength/radiation/lethal-radius tuning. `ParticleAcceleratorReceiverCaptureGameTests.teslaCaptureAfterBroadBoxOnlyOverlap` and `.singularityCaptureAfterBroadBoxOnlyOverlap` assert that the broad-box-only first step does not feed, then exact contact feeds once. Both cases passed in the focused 79-test native diagnostic; the complete feature gate and owner acceptance remain separate.
- Generic persistent structural damage is implemented through a shared namespaced NeoForge BlockEntity persistent-data owner. Direct lightning applies resolved target structural damage (without armor/resistance mitigation); thresholds and steel salvage are resolved per counterpart profile. Incidental target explosions remain a separate `ServerExplosionService` effect. Destruction removes the block normally, explicitly removes cable-host storage, and emits only authored salvage (never the intact machine drop). Damaged coils and rods have resolved repair recipes (1 second, 5 fuel) using shared `TimedInteractionSystem` held-authority and `WelderFuelService`; crash-safe recovery is not claimed. Crack overlays remain undelivered. ChemMaster destruction adapts its unsupported `machineFrame` replacement to air and yields no invented frame/steel; substation destruction adapts to air and does not reproduce upstream gas/explosion secondary effects. Equipment conductivity/insulation is not modeled; Minecraft armor is not treated as SS14 insulation. Petting and ghost warp navigation are not delivered parity claims.
- Coil and grounding-rod ordinary examine now emits the SS14 `ExaminableDamage` WindowMessages sentence using the same persisted `MachineryIntegrity` damage and each resolved profile's 225/300 destruction threshold. Six profile-authored translation keys provide the six `WindowMessages` texts; nearest 20%-band rounding matches SS14 `RoundToNearestLevels` (0% intact, then boundaries 10/30/50/70/90%, clamped). It is a public ordinary-examine sentence, not detail/status UI. `TeslaDamageExamineGameTests.ordinaryExamineReportsResolvedCoilAndRodDamageBandsAndRepair` covers accepted authenticated `ExamineService.queryDiagnostic` calls through `BuiltinExamineContributors.register`/`ExamineContributorRegistry`, zero damage, all half-band boundaries for both denominators, and repair-clear refresh. No damage counter is duplicated. Crack-overlay visuals remain undelivered. Verified upstream: `Content.Server/Damage/Systems/ExaminableDamageSystem.cs` (total damage / `DestructibleSystem.DestroyedAt`, message level selection) and `Resources/Prototypes/Damage/examine_messages.yml` (`WindowMessages` count 6), pinned `c9df5ef5d675b0d1d226828bddf6b78c28502d91`; local adaptation stores message keys directly in the typed profile rather than importing SS14 localized-dataset prototype infrastructure.
- **Power-accelerator parts:** audited finished ControlBox, PowerBox, FuelChamber, EndCap, EmitterPort, Fore/Starboard parts resolve through `ParticleAcceleratorFinishedPart → ParticleAcceleratorBase`; none has LT, `Damageable`, or `Destructible`. Local `blast_damage_immune` therefore includes only the seven canonical PA blocks (these six plus the applicable canonical part), preventing incidental explosion removal without stopping wave propagation; it does not protect every machine or add these parts as direct lightning targets. Upstream: `Resources/Prototypes/Entities/Structures/Power/ParticleAccelerator/parts.yml` and `particle_accelerator.yml`.
- Containment-field generator (`ContainmentFieldGenerator → BaseStructure`), Tesla generator (`Tesla/generator.yml → BaseStructureDynamic → BaseStructure`), and singularity generator (`Singularity/generator.yml`, parentless) likewise have no upstream `Damageable`/`Destructible`; local `blast_damage_immune` also includes these three audited startup generators. References: `Resources/Prototypes/Entities/Structures/Power/containment_field_generator.yml`, `.../tesla/generator.yml`, `.../singularity/generator.yml`.
- **Eligibility (direct lightning target selection only):** local `ModTeslaProfiles.profileForBlock` explicitly maps Tesla coil/rod and supported emitter, airlock, ChemMaster, APC, and HV/MV substation counterparts to resolved machine profiles. Those machine counterparts inherit the generic target values (priority 1, probability 1, resistance 1, structural damage 1, default explosion proposal) unless their authored profile overrides them. Tesla generator, singularity generator, containment-field generator, ordinary terrain, and unlisted blocks have no target profile and cannot be selected as direct block targets. A rejected direct target may still be affected incidentally by a separate explosion or by independently implemented living-beam effects; eligibility does not authorize either effect. This is a local counterpart mapping, not a broad BlockEntity whitelist.
- Field generator profile/state mirrors upstream base max 25, bolt 3, loss threshold 6, decay 2 per 400 ticks (20 seconds); hits reset the loss delay. Thus full charge reaches 5 after 200 seconds and zero after 260 if neither endpoint is charged; either charged endpoint retains the link. This is source reserve behavior, not an engineer grace-period guarantee. Upstream: `Content.Shared/Singularity/Components/ContainmentFieldGeneratorComponent.cs` and server system `Update`/`ReceivePower`/`LosePower`.
- Upstream default Tesla lightning explosion is 25/2/5 and `CanCreateVacuum=false`. It damages terrain but prevents progression to MapAtmosphere tiles. Local generic block-to-air explosions do not model intermediate floors or this no-vacuum restriction; that is a known parity limit, not a terrain-policy change.
- `FixedSource` HV source is mapped to local `powerDeviceKind.HV_SOURCE` for the visual SMES-like adaptation, not as a battery. A precise SS14 counterpart is unverified; retain absent LT and ordinary blast vulnerability, and do not infer an SS14 immunity rule.
- Base energy-ball ambient sound inherited by Tesla main and mini is `tesla.ogg`, volume 3, range 15. Local ambient ownership stops/recreates the loop on range leave/re-entry and profile change, with existing cleanup; it adds no power gate or repeated one-shot. Attenuation means audibility is client/manual validation, not guaranteed by range.
- Lightning bolts now retain a transient per-level server beam for the resolved contact lifetime (normally 3 seconds). Its fixed segment starts one unit from source toward target, clips entity AABBs with resolved `.20` width inflation and cube endpoint padding (finite AABB treatment, not a capsule), and shocks eligible composed living targets on entry; leaving and re-entering shocks again. The selected primary living target keeps its existing immediate shock, and is seeded as already contacting only when its box intersects the segment. Beam state is runtime-only and discarded on level unload. This is a Minecraft adaptation of SS14 `Effects/lightning.yml` plus `BeamSystem` fixture contacts; equipment insulation/conductivity remains unmodeled.
- Source-shock status admission is optional: an unsupported paralyze projection (for example on a composed pig or mouse without `Stunnable`) does not cancel independently admitted typed shock damage. This preserves source-shock damage arithmetic and does not alter chemical `Electrocute` insulation or status-reducer policy. The animal regression passed in a previous diagnostic; the current revision is unvalidated.
- Owner-approved Minecraft-only visual/motion adaptation: resolved ball profiles may author `visualRadius` and optional `orbit` (absence preserves chase). Mini visual/collider radius are `.90/.65`; it uses deterministic UUID-phased 3D orbit points around its tracked main and avoids two-second impulse resets. Runtime retains a valid main owner across jumps up to its 20-block tracking limit; if invalid, bounded local target selection can reacquire. The mini has the authored 120-second age-based despawn, independent of its parent, and does not feed energy or reproduce. Main visual/collider radii are `2.0/.75`; its `.65` contact/lethal/PA radius remains unchanged. Local resolved shooter ranges are main 7 and mini 3, versus upstream 7 and 3; the base lightning `beamHalfWidth` is `.20` (default 0 for older profiles). These tuning changes are explicit Minecraft adaptations, not claims about pinned SS14 values. Upstream baseline values in the table above remain unchanged.
- Orbit-motion correction: the resolved orbit sample remains the moving target, while minis pursue it using the existing bounded response/acceleration controller. The main's instantaneous velocity is deliberately not feed-forwarded; doing so canceled positional lag during containment reversals. Minis therefore trail and catch up after bounces/jumps without changing orbit geometry, ownership, or admission limits.

SS14 media, accepted Power R6 models and attribution are indexed in `ASSETS.md`; missing open-state art is not invented. New damage-examine resolution/runtime tests are implemented but current native validation is pending. The earlier shared-explosion gate PASS (`b318`) is historical only; all current changed behavior awaits validation. Client startup does not establish in-world GPU/audio quality or owner acceptance.
# Shared explosion presentation

LightningTargetSystem queues the default explosion on a hit (intensity 25, dropoff 2, max 5, cannot create vacuum); explosive detonations also queue through `ExplosionSystem.QueueExplosion` / `Processing.Update`, with shared visuals and camera-aware sound in `SpawnExplosion`. Local `ServerExplosionService.execute` now emits one common accepted-explosion presentation for Tesla and grenade callers. It reuses the existing grenade sound policy/network/client path and bounded vanilla EXPLOSION/FLAME/LARGE_SMOKE cue at the blast voxel center. This is a Minecraft adaptation, not full SS14 AV parity: current near/far cue does not scale by explosion intensity or combine queued explosions, and no orange light or fire RSI states are implemented. Imported SS14 sounds remain unchanged. Existing local Tesla and grenade balance values are untouched (including known grenade 380 vs upstream 120 discrepancy).
