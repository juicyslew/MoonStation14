## Proposed boundary

### In scope for a first sprint, subject to owner decisions

- A bounded 3D propagation plan and the explicitly scoped player grenade implementation described in [M3 player grenade](m3-player-grenade.md); this does not establish generic item use/throw dispatch or connected-client acceptance.
- Typed damage to eligible server entities once per event, through `DamageSystem`; no player-specific handling.
- Structural station blocks are intentionally destructible by the player grenade; the current implementation reaches three known mod station structural classes, with floors/ceilings using the same breach rule as equivalent walls. Ordinary non-air blocks including vanilla dirt and stone are also blastable at local tolerance 2, subject to explicit negative-hardness/admin/special immunity. There is no production server, save migration, or current claims/world-protection blocker.
- Explicit follow-on notifications for atmosphere topology (only when enabled) and power graph host removal/invalidation.
- Integration evidence for puddle support loss and subsequent speech audibility, without implying that raw block mutation automatically triggers either behavior.

### Out of scope

No generic item/equipment/inventory or generic throw-dispatch system; modular grenades; shrapnel, physics impulse, chain reactions, gas-fire ignition, fire-stack/temp effect, or admin public command. The local registered/server-resolved `moonstation14:ex_grenade` source prototype at `data/moonstation14/moonstation14/explosive_source/ex_grenade.json` contains provisional 380/3/10 and selects `explosion_type: default`; resolution fails closed. Local `moonstation14:default` at `data/moonstation14/moonstation14/explosion/default.json` contains damage/break metadata and `temperature_kelvin: 800`, but has no implemented gas hotspot/heat deposition/fire-stack effect. The grenade currently uses an attributed 3D cocoa-pod model (`minecraft:block/cocoa_stage2`) and imported, attributed SS14 beep1/explosion1 audio at ExGrenade 0/+2/3-second timing. Modest vanilla particle flash/flame/smoke is the current local visual translation, not the SS14 `Default` overlay and not parity. The throwable throw sound remains a vanilla placeholder.

## Proposed contracts (not implementation instructions)

### Trigger and prototype (test fixture only)

The first trigger should be a trusted, server-only GameTest fixture, unavailable to player clients. It must be possible to construct a source in a GameTest without adding a public command, usable item, or live gameplay explosive. Identify event source and coordinate in server-owned context; reject client-supplied authority, invalid coordinates, unloaded source chunks, or unknown prototype IDs. Public gameplay triggers remain excluded.

Represent tuning as immutable typed prototype data loaded by existing prototype infrastructure. Candidate fields, all requiring schema and range validation: stable `id`; total intensity/budget; distance falloff slope; maximum intensity per voxel; maximum affected voxels/work; damage per intensity and typed damage kind; structural breach rule and optional decorative floor-cover damage curve. Start from the pinned SS14 radius/intensity/falloff/budget values as an explicitly labeled 2D reference set, then calibrate via measured 3D geometry; do not silently alter them or imply exact parity. Do not imply these fields define a universal block material resistance. Temperature/fire metadata exists, but local heat deposition, gas hotspot creation, and fire-stack application are not implemented. Pinned SS14 Default has no `fireStacks` (the separate FireBomb specifies `fireStacks: 2`). Avoid arbitrary executable behavior in data. Unknown IDs/fields, nonfinite values, negative budgets, inverted curves, and unsupported damage types fail closed at catalog resolution; do not substitute a dangerous default.

Translate source total intensity, falloff, cap and any optional decorative-cover curve into explicit local units and a 3D rule. Structural floor breach uses the structural rule, not the cover roll. Define probability deterministically from event seed plus stable voxel coordinates (and a specified roll index), not thread order or ambient randomness. This is reproducible local sampling, not a claim to duplicate SS14's random generator. Repeated rerolls, if retained, must have a fixed capped count and the pinned reduction rule. One event must not obtain extra work or damage by being re-entered.

### Propagation and plan boundary

Use a pure deterministic kernel over an injected world sampler. It returns an immutable side-effect plan; it does not access Minecraft state, load chunks, mutate blocks, damage entities, or notify services. Propagate only through six face neighbors in a fixed documented order. At each candidate compute intensity from the pinned rule, apply the per-voxel cap, and stop when the budget/range rule says so. Prevent revisits from multiplying energy. Distinguish eligible/open paths, structural breach outcomes, optional decorative-cover damage, airtight structure tolerance/blocking, vacuum/space policy, and unknown samples explicitly; their Minecraft mapping is a design decision, not a universal resistance scalar.

Never load chunks as a side effect of a blast or scan a radius without a hard work bound. Unloaded boundary cells stop propagation and are not queued for later phantom damage. Set hard per-event and per-tick inspection/plan caps before implementation; validate the complete bounded plan before applying any destructive effect. A cap/queue overflow must have a documented safe outcome chosen by the owner (preferred proposal: reject the event plan before side effects, report saturation, and do not silently truncate a potentially misleading partial blast). If caps are split across ticks, define immutable event ownership, ordering, expiry/cancel semantics and ensure no partial destruction occurs before validation. This is not a claim of atomicity across Minecraft world, entity, atmosphere and graph services.

### World application, ownership, and integrations

Explosions should be broadly destructive—nearly anything may be destroyed—with exceptional explicitly immune/unbreakable and world-protected/admission-denied targets. Player placement or provenance is not a reason for immunity. Structural floors breach by the same rule as equivalent walls/ceilings; an optional independent decorative cover/tile roll may damage an unbreached floor. SS14's probabilistic per-type floor peeling is not the structural floor rule here. Airtight structures' SS14 health/damage-type-derived tolerance informs the structural rule, whose exact 3D mapping remains to be decided. Current grenade behavior makes ordinary non-air blocks, including vanilla dirt and stone, blastable at local tolerance 2; explicit negative-hardness/admin/special immune targets remain protected. This is a local implementation choice, not SS14 parity. M0 must define modded floor/wall structural and decorative-layer mappings. Do not blindly equate vanilla Minecraft blast-resistance numbers with SS14 behavior. No generic block-break API is established by current evidence: implementation must use a narrow mutation/admission hook that respects loaded chunks and world protection, and revalidate current state immediately before writes.

### Owner-approved direction

The blast target policy is broadly destructive, not restricted by mod ownership or placement provenance. It may destroy eligible modded blocks once the design gate is approved; it is not required to prove block ownership first. Outcomes use distinct target-class rules rather than a universal material-resistance scalar. There is no arbitrary universal admin bypass: preserve only the precise exceptional immune/unbreakable and world-protected/admission-denied cases agreed at M0. Destructive world integration remains gated; M1 pure-kernel work is authorized.

If approved targets are changed, use a narrow server-side mutation adapter that revalidates loaded state and target eligibility immediately before each write. Record actual old/new states and issue required downstream notifications; a previously prepared plan can become stale. Do not describe cross-system application as transactional or all-or-nothing unless the code can truly provide that guarantee. No writes occur for rejected/unloaded/protected targets.

Prioritize entity damage and power/atmosphere integration. Query entities only within bounded affected loaded cells; apply one typed damage outcome per eligible entity per event using the agreed intensity rule and `DamageSystem`, not an untyped direct health edit. Atmosphere block/topology changes must call the existing topology integration only when atmosphere is enabled; respect its ownership/closure rules and never assume direct `setBlock` emits an event. Power cable removal must clean the host through `CableStorage.removeHost` and invalidate via `PowerGraphService.noteChanged` as required, not mutate the cable block alone.

Two additional acceptance checks demonstrate downstream world behavior rather than claiming generic hooks: loss of a supported puddle block should exercise the existing neighbor support-flow behavior; speech delivered after a changed occluding wall should reflect `LocalSpeechOcclusion`'s delivery-time check. No cache invalidation claim is needed for that uncached check. These integrations are not permission to destruct arbitrary supports/walls; they require an approved target fixture.

Damage, mutation, power and atmos updates have distinct failure surfaces. Define whether a stale target is skipped and how that outcome is reported. Protect against duplicate entity application and duplicate notifications when an event is retried. Atmosphere is default-off: tests must cover both disabled and an explicitly enabled, permitted fixture. Any production acceptance requiring atmosphere must also settle permission to alter closure/topology state.

## Minimum 3D verification matrix

| Case | Required observation |
|---|---|
| Flat floor and ceiling | Six-face propagation is spatially symmetric; vertical shielding is real, not a 2D projection. |
| Vertical shaft | Open loaded shaft transmits only according to the pinned 3D intensity rule. |
| Corner and thin/thick barriers | Fixed neighbor order and barrier costs produce repeatable, distinguishable outcomes. |
| Loaded chunk seam / unloaded chunk edge | Loaded seam agrees with uninterrupted geometry; unloaded boundary stops without loading or deferred phantom effects. |
| Duplicate entity / multiple reached voxels | Exactly one typed damage application per eligible entity and event. |
| Energy/work budget and queue saturation | No over-budget plan or partial destructive side effect; outcome follows owner-approved overflow rule. |
| Disabled atmosphere / enabled permitted level | Disabled service remains untouched; enabled fixture receives required topology update and expected real closure outcome. |
| Equivalent structural floor, ceiling and wall / decorative cover | Structural outcomes follow the same breach rule; cover damage is a separate optional roll and cannot count as structural breach. Protected and explicitly immune blocks remain unchanged. |
| Eligible cable / puddle support / speech occluder | Real power cleanup, puddle support reaction, and subsequent delivery-time speech occlusion respectively; placement provenance is irrelevant. |

Tests should use real GameTest world outcomes for integration and focused pure tests for arithmetic/order. A compiled test fixture is not evidence that it ran in a server. Benchmark event inspection counts, mutation counts and worst-tick time against an idle baseline; assert no full-world scan, chunk loading, starvation or unbounded deferred work.
