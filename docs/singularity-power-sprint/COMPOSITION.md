# Singularity visual composition spike

Upstream checkout: `SS14-dev/space-station-14`, pinned `c9df5ef5d675b0d1d226828bddf6b78c28502d91` (verified). `Resources/Prototypes/Entities/Structures/Power/Generation/Singularity/singularity.yml` declares a root `entity` with no parent. Its composition includes physics/movement, event horizon, gravity well, fixtures, singularity state, distortion, radiation, point light, appearance, tags, warp point, sprite and generic visualizer. This spike implements none of those gameplay systems. `Content.Shared/Singularity/EntitySystems/SharedSingularitySystem.cs` derives distortion by level; `Content.Client/Singularity/SingularityOverlay.cs` consumes at most five same-map distortion sources and supports reduced motion; `Resources/Textures/Shaders/singularity.swsl` warps the screen texture sequentially. The renderer parameters here are an explicit local visual extraction, not an upstream prototype inheritance chain.

The visual profiles preserve static sprite scales (1,1,1,1,1.5,.9) and distortion profile values (falloff sqrt(6.4,7,8,10,12,12), intensity 3645,103680,1113920,16200000,180000000,180000000), cutoff 20 world units. The source frame widths are 32,96,160,224,288,352 pixels (verified against the six imported static PNG dimensions); the shared live/preview quad half extent is `frameWidthPixels * spriteScale / (2 * 32)`. The factor 32 is pinned Robust `EyeManager.PixelsPerMeter` (used by `DrawingHandleWorld` to map sprite texels to meters), not an assumed normalization. Live renderer culling bounds include the resolved art extent with a conservative `sqrt(2)` camera-facing corner radius; entity physics bounds remain unchanged. The world lens consumes the resolved SS14 pixel cutoff as world cutoff times 32, without source-depth/focal scaling or screen admission. A shared vertex transform is a deliberate Minecraft 3D adaptation, and does not alter aim/HUD or gameplay.

## Generator composition mapping

Pinned SS14 `singularity.yml` is a root entity (no parent); its generator component defaults are consumed by `SingularityGeneratorProfile`: threshold 16, starts non-inert, failsafe enabled, distance 16 and cooldown 10 seconds, with `spawnProfile` mapped to the local gameplay prototype reference `moonstation14:singularity`. Its live consumer is the dedicated registered `singularity_generator` block/`SingularityGeneratorBlockEntity`, which resolves `ModSingularityGenerators.catalog(level).get(DEFAULT_ID)`, uses `SingularityGeneratorStartup`, and checks the freshly refreshed `FieldContainmentRuntime.closedVolumes` before accepting PA generator-charge values. Its BlockEntity type is not shared with the distinct containment `field_generator`; the startup block never enters the field index. `generatorCharge` is distinct from singularity food. Cooldown/inert rejection precedes containment and does not extend the 200-tick cooldown. The registered `ModEntities.SINGULARITY` receives the configured gameplay profile and initializes through its resolved gameplay profile, not a hardcoded energy transfer.

Deliberate Minecraft adaptation: the machine is a static anchored block rather than an SS14 physics fixture, and the planar four-ray failsafe is replaced by a current loaded-world, closed six-face 3D volume containing the generator center, with all six face distances within the resolved failsafe distance. No globally-all-fields-intact condition is imposed; a separate valid volume suffices. The placeholder iron-block model is not accepted authored generator artwork. Upstream references: `Content.Shared/Singularity/Components/SingularityGeneratorComponent.cs` and `Content.Server/Singularity/EntitySystems/SingularityGeneratorSystem.cs` at pinned revision `c9df5ef5d675b0d1d226828bddf6b78c28502d91`.

Local level profile JSON is a presentation-only catalog consumed from the client prototype manager. It does not establish event-horizon, radiation, movement, energy, or containment behavior. A local profile base, if introduced later, is a deliberate shared-default extraction only; it must not be represented as a parent of the upstream entity.

Current presentation consumers: `SingularityRenderer` renders tracked gameplay entities with the resolved animated frame, level scale and unchanged crossed-quad/fullbright billboard geometry. Its buffered source sprites use a dedicated ShaderInstance linked against native entity-cutout programs, so the core is exempt even when the buffer flushes later; native depth writes keep the opaque core in front of subsequent geometry. `SingularityVisualPreview` retains local preview anchors, reuses its source-selection and nine-ray visibility services, and feeds the live world-frame source list. The vertex mapping runs before rasterization and every world surface is issued once; it does not use a final scene-color/depth copy. Preview anchors remain presentation-only; live gameplay is not synthesized by this renderer. Connected/GPU visual acceptance remains pending.

Audio correspondence is recorded in `docs/singularity-audio-parity.md`: the root generic ambient component and the singularity component's separate default ambient stream are both represented in resolved gameplay sound data. Formation is null by default; `singularity_form.ogg` is the component loop, not an unconditional creation cue.

## Catalog visibility root cause and remaining GPU check

The live visibility root cause was an empty authoritative visual catalog: the six profiles were physically packaged under `data/moonstation14/moonstation14/singularity_visual`, while the registered `singularity_visual` type loader scans `data/moonstation14/singularity_visual`. Client bundled bootstrap temporarily hid the mismatch, then login cleared that catalog and the server sync correctly supplied its empty type. Profiles are now at the canonical loader path; the bootstrap and tests use that same location. The lifecycle regression tests actual reload → login clear → complete sync; a tagged native server fixture asserts the live server manager contains all six resolved profiles. `/ms14_singularity_visual_status` remains useful for checking tracked entities and per-entity renderer admission/invocation. GPU presentation remains unverified; run status and inspect the live sprite after the resource fix, without treating preview anchors as proof.
