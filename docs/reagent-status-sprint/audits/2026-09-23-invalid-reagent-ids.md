# Invalid reagent IDs at runtime

## Finding

No `run/logs/latest.log` or crash report was available during this investigation, so the reported command and crash stack were not reproduced. The confirmed failure boundary was color lookup: `ReagentComponent.getBlendedColor(..., catalog)` required every positive reagent key and threw for a key missing from the resolved catalog. Bottle, jug, puddle, and related tint callbacks may invoke that lookup during rendering.

## Controlled behavior

- Tint lookup now warns once per missing ID and catalog context, excludes that ID from the blend, and returns `-1` (no tint) when no known positive reagent remains. Warning caches are bounded; valid color weighting is unchanged.
- Persisted item/component codecs intentionally remain permissive about catalog membership. Unknown IDs round-trip intact so item data can be repaired rather than silently discarded. Prototype schema/reference auditing remains the strict load-time boundary for malformed reagent prototypes.
- Server-side bottle/jug use, jug placement, ingestion, transfers, spills, and puddle flow validate positive stored IDs against the server's resolved reagent catalog before consuming a source, creating a puddle, throwing a jug, or adding material to a destination. Both sides of transfers (including pre-existing puddle/jug destinations and stomach state) are checked. Invalid holders are left unchanged and an error identifies the ID and action context. Client use does not reject based on an unsynchronized catalog.
- `StomachSystem.vomit` now checks for unknown positive reagent IDs before clearing either a detached stomach or the live digestion solution, and before applying hunger/thirst penalties or the vomiting slowdown. `StomachGameTests.invalidStomachVomitFailsWithoutClearingOrApplyingPenalties` covers unknown-only and mixed known/unknown detached stomach contents, confirming failure preserves the mixture and applies no penalties/status. The live digestion branch uses the same guard but is not covered by this focused test. For ordinary valid contents, spill placement remains non-atomic: if placement fails after source clearing, the detached spill solution can be lost.
- `InvalidReagentGameTests` parses (but deliberately does not execute) a `/give` command carrying a syntactically valid unknown reagent key, verifies bottle-use rejection without source mutation or stomach materialization, verifies mixed water/unknown rejection is atomic, confirms valid water use still starts, verifies unknown jug placement rejection, and exercises an invalid 40-unit puddle through the public server ticker to confirm it is not removed or mutated. The command parser may accept unknown IDs; rejection is at item use, not syntax parsing.
- A stream round-trip test covers an unknown reagent resource key through both fixed-point component and attachment codecs with `RegistryAccess.EMPTY`. It succeeds, showing the registry-key stream codec preserves the unknown key without registry entries; it does not by itself establish any separate pre-sync `PrototypeRuntime` catalog state. Bottle/jug held-use ticks also revalidate the current source on the server and stop using if it became invalid after use began, leaving stored contents unchanged. The invalid-source mid-use GameTest covers both items.
- Existing puddle flow validates its source before ticking/removal and validates all existing candidate neighbor holders before creating replacement puddles, transferring material, or invoking reactions. An invalid source/destination therefore skips that flow tick; contents remain persisted for repair.
- Tint fallback is covered at the catalog/color helper level. The dedicated server GameTest does not instantiate a client renderer, so an actual client-facing command display/render crash has not been excluded by an end-to-end client test.

## Limits

This does not establish the exact cause of the user's crash: the exact original crash log and crash report are still missing, and these changes do not add a catalog-membership requirement to arbitrary third-party mutation APIs. If a client-facing command display still crashes despite the tint fallback, provide the full `latest.log` and crash report plus the exact command/ID; do not infer the crash path from parser acceptance. Other call sites outside the guarded use/transfer/ingestion/puddle paths may still require investigation.
