# Thirst owner (2026-09-23)

The owner stores custom thirst in `[0, 600]`. `moonstation14:thirst_eligible` is a temporary explicit entity-type tag containing players and villagers; join-time initialization draws from `[310, 449)` and preserves existing attachments, reconciling derived state for persisted attachments on re-enrollment. This is an interim player-as-body boundary, not character-prototype enrollment. On a tick where an entity carrying the derived THIRST activity loses tag eligibility, the scheduler flag, thirst alerts, and thirst speed modifier are removed together while the authoritative attachment is retained. This cleanup is keyed by the active THIRST flag to avoid repeated projection mutations. Character-prototype enrollment and a deliberate transformation policy remain prerequisites.

The 20-tick derived activity applies one upstream-inspired second of decay per due invocation, with no catch-up. Thresholds are: `0` DEAD, `(0, 150]` PARCHED, `(150, 300]` THIRSTY, `(300, 450]` OKAY, `(450, 600]` OVERHYDRATED. Zero means only the upstream `Dead` thirst threshold; it does not kill or damage the entity. There is no automatic damage at zero.

The server owner reconciles dedicated persistent `thirsty`/`parched` alerts and one deterministic transient 0.75 movement-speed modifier for PARCHED and DEAD. Only thirst-owned alerts/modifiers are removed on recovery or eligibility loss. Alerts are categorized under `moonstation14:thirst`; a missing owned alert prototype makes applying that alert a controlled projection failure (and is logged), while removals remain possible without its prototype. Existing alert category replacement can also fail if some other currently attached alert's prototype is missing; the alert subsystem then declines the mutation, so the owner cannot guarantee cleanup in that catalog-corruption case. In every case thirst remains authoritative. Entities without `MOVEMENT_SPEED` retain scalar thirst but cannot receive the speed projection. No jetpack owner/API exists locally, so the upstream jetpack-flight exemption is not implemented. No per-tick projection writes are expected when state already matches.

`SatiateThirst` is implemented for targets already tagged eligible and already carrying thirst state. It applies `factor * scale` (codec default factor `1.5`) with bounds clamping and rejects non-finite/overflow arithmetic without mutation. It does not initialize missing state. Vanilla `FoodData` is not projected or mutated.

## Explicit deferred boundaries

Stomach/ingestion has a separate bounded owner, using the same temporary eligibility tag as a character surrogate. Vomit applies the upstream `-40` through the thirst owner when thirst state is already initialized, even if the eligible character's stomach is empty; it does not initialize thirst state or claim stomach capability based on thirst alone. Character-prototype enrollment and jetpack flight exemption remain unsupported. Death/clone transport still follows the existing default attachment policy; there is no thirst-specific clone/death cleanup or persistence transport contract asserted here. No hunger or damage semantics are inferred from thirst. The effect support matrix is 20 functional/partial registrations and 14 explicitly unsupported registrations.
