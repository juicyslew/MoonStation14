## Safe opt-in

1. Back up the world and use the same matching rebuilt modded client and server build for every comparison. First launch and confirm the default configuration (`experimentalVerticalSliceMovement = false`) retains vanilla movement.
2. Stop the server. In the running server installation's `config/moonstation14-common.toml`, set:

   ```toml
   experimentalVerticalSliceMovement = true
   ```

3. Confirm the player is in survival or adventure before testing: custom movement eligibility excludes creative/spectator modes. If `force-gamemode=true` and the configured mode is creative, change the connected player to survival before testing. Start/restart the server with opt-in enabled and connect a real authenticated player using the matching modded client. The setting is read and latched at server startup; it is **not** a live toggle. Do not edit it expecting an active server to change modes.
4. Check matching server and client debug logs for INFO messages corresponding to Begin/Commit and, where applicable, resume/handoff. Record exact messages, timestamps, session ID if available, exact client/server builds, effective per-session game mode, startup config, and outcome. Missing or unexpected transition messages are a stop condition; do not infer custom ownership from a config value alone.

Do not use FakePlayer or another packet fixture as a substitute for this test. A successful server GameTest or build is not connected-client evidence.

## Smoke sequence

Use a backed-up test area and observe both movement and logs. Exercise each case deliberately; stop if ownership appears ambiguous or the player becomes stuck:

- In survival on ordinary ground, walk forward, backward, left and right; then test diagonal movement, sprint and jump.
- Compare a jump before and after a one-block obstacle: ordinary jumping is reported working, but the owner could not clear one block. Record obstacle geometry and whether collision/step behavior differs from the expected vanilla-height jump; automated jump fixtures are not a connected retest.
- Compare continuous contact/sliding across adjacent qualifying SpaceLube sources against contacts separated by a genuine gap. Do not assume every puddle launches: pinned SS14 does not multiply velocity again while already sliding, even though a super-slippery `SlipEvent` can be admitted. Record each source's initial/current amount, contact order, Sliding/knockdown state, launch/re-slip count, and observed speed. Check the server diagnostic `[movement server] admitted slip launch changed horizontal speed` and correlate it with actual source contacts. The old three-launch local fixture was a bug, not upstream parity; see the [correction audit](2026-09-24-re-slip-parity.md). A fresh admission after sliding genuinely ends may relaunch using retained momentum without voluntary input; do not treat that as proof of the owner's reported incident or claim that fixtures prove connected chain traversal.
- For the nine-jug scenario, record each 200-unit jug's exact starting amount if inspectable, and actual per-tile puddle amounts during traversal; nine jugs do not imply a fixed amount in each puddle. Record `Stunned`, `Slipped`, and `Knocked Down` HUD states, and capture first- and third-person video both grounded and airborne. Exercise forward/strafe input, reversal, and yaw/render facing while tracking velocity turns; note when movement factor returns to neutral on loss of lube contact. Correlate observations with each approximately five-second `[movement server] surface` summary (lube/neutral tick counts, min/max factor, pre-friction blocked-projection ticks, lube-to-neutral transitions, maximum speed) and client correction summary (projected/hard corrections and duplicate ACKs). These summaries contain no raw coordinates and are diagnostics, not a cause or acceptance verdict. Record whether an admitted `SlipEvent` coincides with a velocity launch, sound, both, or neither.
- Confirm each source's actual amount during the run rather than assuming a jug distribution yields a particular quantity per puddle. The current contact query examines only the collision-resolved endpoint AABB (at most 16 overlapped cells, normally about 2×2×3), not the path between endpoints. Very fast path-crossing slips are an accepted limitation; do not interpret a missed crossing as evidence of a swept contact check.
- In the continuous case, verify there is no second launch or repeated Touch merely because a second puddle is contacted while sliding. In the separated case, verify sliding clears on loss of the last qualifying contact and observe whether momentum admits a new slip while knockdown is still active. Confirm that stun suppresses voluntary steering only for its duration: test steering after approximately 10 ticks while knockdown/sliding persists. Camera policy is now stun-only; compare turning during stun with turning after stun expires while sliding/knockdown persists, accounting for client status-sync delay.
- Compare ordinary-ground stopping/coasting and steering with expected SS14 feel. The corrected pinned-source calculation is HUMAN friction 20 (base 2.5 multiplied by tile friction 8), so the default 20 Hz neutral-floor retention factor clamps to zero. During qualifying SpaceLube contact, factor 0.05 makes effective friction and acceleration 1; it does not persist after contact. Record stop distance/coast and steering on normal blocks versus active lube contact, plus contact/factor status at abrupt turns. SS14's projected-velocity acceleration can produce “snaking” at large direction changes, but it does not prove the cause of any local turning report. Walk/sprint speeds are 2.5/4.5 blocks per second (1 block = 1 SS14 tile), intentionally slower than vanilla Minecraft. Do not infer feel acceptance from these constants; disable the experiment if behavior is problematic.
- Check the right-side HUD for Stunned (synced action-block), Slipped (synced Sliding marker), and Knocked Down (existing synced status), which can overlap; report missing, stale, or unexpected overlap. Also inspect body-facing during directional travel: its latest implementation is visual-only and must not be mistaken for head/gameplay yaw or server rotation.
- While walking and sprinting, check leg animation for expected movement and any stutter. The motor now runs in client `LivingEntity.travel` on the input tick; the tick hook sends a cached frame once, and animation is calculated after an accepted move. Under high latency, observe snapshot corrections, jitter/rubberbanding, and whether newer predicted displacement is retained. Correction preserves bounded grounded displacement arithmetically rather than fully replaying movement; it can still hard-snap otherwise. Record latency, correction, and observed outcome; this is experimental, not a proven fix.
- Test camera turning during stun, then after the 0.5-second stun ends while sliding/knockdown may persist up to 1.5 seconds. The current policy is stun-only, with possible client status-sync delay; do not infer a general vanilla or creative camera lock. Verify ordinary rotation remains as expected after stun and after leaving contact.
- Walk into a solid wall and verify collision prevents penetration or an apparent teleport.
- Test crouch, stun, and retained slip/external momentum. Check that stun suppresses voluntary movement without freezing physical response.
- Enter water, climbing, a vehicle/passenger state, and creative/flying movement; verify the intended vanilla fallback and return-to-supported-mode handoff.
- Test an explicit teleport, a dimension change, and disconnect/rejoin. Check for a single owner throughout, valid teleport acknowledgement, and no stale movement/jump on return.
- Repeat ordinary movement under high latency if practical. Watch for freeze, repeated correction/rubberbanding, stale input, or unexpected disconnect; record conditions and logs rather than tuning the result.

The handshake code supports an unsupported-mode DisableAck -> vanilla teleport-ID acceptance -> ResumeVanilla -> ResumeAck handoff, but this fallback is **not connected-proved**. Passing an individual mode check does not establish the whole eligibility matrix or race-free ordering. The 2026-09-24 second client-hosted session had no custom Begin/Commit or movement diagnostics; it is not a custom-motor regression. ## Stop and recovery

Stop the smoke on a freeze, unexpected teleport, apparent simultaneous movement ownership, missing transition acknowledgement, timeout, or disconnect. If stuck or disconnected, set `experimentalVerticalSliceMovement = false` in the server configuration and restart the server; there is no hot change. Preserve logs and report the last action and observed state. Do not repeatedly reconnect with the experiment enabled after a handoff failure.

The implementation has a 100-tick experimental timeout fail-safe that disconnects, and sends one snapshot per custom-owned tick. This is not a guarantee against all failure modes. Current known risks/limitations include:

- Vanilla `LocalPlayer` still sends position packets while the server rejects them during committed custom ownership; lag-related correction/rubberbanding is possible.
- Runtime mode-order and handoff behavior has not been validated on a connected session.
- Connected collision regression on 2026-09-24: the strict post-`Entity.move` bounds check disconnected an authenticated client. Ordinary walking/jumping without a crash in the limited post-fix smoke did not reproduce that exception, but does not establish broad collision/step behavior or clear the remaining connected checks. See the [regression audit](2026-09-24-connected-collision-regression.md).
- Snapshot correction preserves bounded unacknowledged grounded displacement arithmetically; it is not full deterministic pending-input replay. The 64-entry history bound is experimental and unmeasured. A Villager AI adapter is missing.
- The unsupported-mode fallback is code-present but not connected-proved.
- No connected evidence exists for the three-puddle lane or the M4 numeric tick bound; that bound remains unaccepted.
