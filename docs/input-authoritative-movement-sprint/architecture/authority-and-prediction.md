## Reference model and local boundary

At SS14 `c9df5ef5d675b0d1d226828bddf6b78c28502d91`, `Content.Shared/Movement/Systems/SharedMoverController.cs` describes shared player/NPC movement and server-only NPC simulation. It consumes mover wish, computes friction and acceleration, applies the physics velocity, and uses the common movement implementation. The RobustToolbox submodule is pinned to `3136118b5338ef2d9580178caf5c723e65eb76e7`; its `Robust.Shared/Input/InputCmdMessage.cs`, client `InputSystem` / `ClientGameStateManager`, and server `InputSystem` provide tick/subtick input commands, server dispatch, pending input tracking and prediction-oriented replay. Treat these as architectural references, not a literal port or proof the Minecraft networking hooks are equivalent.

NeoForge 21.1.224 is configured for Minecraft 1.21.1. Its cached source artifact is `build/moddev/artifacts/neoforge-21.1.224-sources.jar`. The reviewed sources show `ServerboundPlayerInputPacket` carries directional axes and jump/sneak flags, with sprint carried separately; this packet does not itself supply a simulation tick or server acknowledgement. `ServerboundMovePlayerPacket` carries client position/rotation and `ServerGamePacketListenerImpl.handleMovePlayer` processes that proposal. `LocalPlayer` has its own client movement prediction path. `PlayerList.placeNewPlayer` uses the explicit teleport ID/ack path; respawn and dimension changes are separate clientbound transitions, with respawn followed by a teleport, not a general serverbound respawn acknowledgement. Neither transition is a normal motor update.

Local code currently bridges slip to `ServerPlayerAcceptedMoveMixin` after vanilla `setKnownMovement`, then calls `SlipSystem.onAcceptedPlayerMovement` swept sampling. That sample is a bounded contact adapter over movement Minecraft already accepted; it does not make the underlying movement input-authoritative. `ServerPlayerStunActionMixin` cancels `handleMovePlayer` while stunned and invokes vanilla teleport correction; extending that correction into a per-tick motor protocol risks repeated teleport traffic and conflicts with vanilla prediction. `LivingEntitySlidingFrictionMixin` applies common `LivingEntity.travel` logic on both logical sides, but client code-path presence is not a connected-client agreement proof. `SlidingAttachment` is synced and volatile; it is not suitable as a per-tick state stream. `CharacterControlSystem` resolves shared identity/status policy and must not become a controller-specific movement authority. `ModEventHooks` owns existing join/clone boundaries that can inform, but do not by themselves solve, mode handoff.

## Protocol responsibilities (proposed)

1. Client command expresses bounded wish/buttons and a monotonically sequenced input tick/epoch, never a desired position, velocity, slip, status or damage result. Server validates its session, mode, ordering, range, rate and queue bounds, then chooses the command for its tick. AI adapter makes the same internal command from a Villager wish without network input.
2. Both sides call the same pure command-to-motor transition and Minecraft collision contract. Server's world state/collision remains decisive. State includes enough authoritative data to replay movement (position, velocity, relevant grounded/mode flags and acknowledged input sequence); keep implementation minimal and prove which values can be derived safely.
3. Server snapshots acknowledge the last consumed sequence and convey the authoritative motor state. Client drops acknowledged commands, restores that state and deterministically replays remaining commands. Divergence is corrected from the snapshot, not by trusting reported displacement. Slip sampling must observe only server-simulated accepted movement.
4. An epoch changes on disable/re-enable, reconnect, clone/death, dimension/teleport, and supported/vanilla mode boundary. Drain or invalidate old commands, clear one-shot edges, seed from authoritative state, and establish exactly one active movement owner. Preserve vanilla rotation and explicit teleport acknowledgements separately from vanilla respawn/dimension transition handling.
5. Enforce finite values and explicit limits on command rate, sequence window, buffered ticks, catch-up/replay work and snapshot traffic. Tune limits only from measured 20/50-player 20Hz workloads. Cleanup per-player transient state on disconnect and lifecycle changes; never persist it as an `MS14Provider` attachment.

## Unresolved proof obligations

- Establish exact injection/network hooks for receiving an added input packet and returning snapshots without a conflict with vanilla login/configuration/play protocol. Validate a real authenticated connection end-to-end; the prior FakePlayer packet fixture had a null/no-active channel and untrusted natural tick behavior.
- Prove the custom protocol can keep vanilla `ServerboundMovePlayerPacket` from relocating an enrolled human while retaining legitimate rotation, teleport, respawn, and fallback semantics. If no precise gate exists, do not ship parallel authority; return to owner with evidence.
- Establish deterministic-enough shared collision behavior, snapshot timing, missing-input policy, server-thread dispatch, ordering under jitter/reorder, and safe bounded resource usage. Client replay is prediction only, never an authority or a source of slip/Touch assertions.
- Prove mode switch/vehicle/flight exclusions cannot briefly accept both input streams or consume stale jump/movement input. A server authority transition must be explicit and observable.
- Demonstrate with an actual connected player that stun removes voluntary directional wish without canceling the motor tick, and that a wall still blocks external slip momentum while input is suppressed.

No result in the previous [slip/stun closure](../../slip-stun-sprint/closure.md) closes these obligations. In particular, 109/109 server GameTests, `FakePlayer`, and common-mixin source inspection do not demonstrate server/client movement agreement.
