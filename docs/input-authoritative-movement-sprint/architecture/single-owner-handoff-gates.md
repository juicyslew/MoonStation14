# Single-owner handoff gates

**Status: design-time source findings and acceptance-risk record; experimental implementation is now authorized and present.** The owner authorized a default-off connected vertical slice after this original stop-gate review. The code includes Begin-Ack-Commit and an unsupported-mode DisableAck/vanilla teleport-ID acceptance/ResumeVanilla/ResumeAck handoff, but these have not been proved with an authenticated connected client. The safety condition remains: at every instant, exactly one movement authority should be active; live mode transitions and teleport behavior still need owner smoke verification. See the [experimental connected-smoke checklist](../audits/experimental-connected-smoke.md).

## Source facts and unresolved hook

Source references below are the pinned Minecraft 1.21.1 / NeoForge 21.1.224 artifact paths and line ranges recorded in the [M0 source audit](../audits/m0-authority-and-protocol-proof.md): `build/moddev/artifacts/neoforge-21.1.224-sources.jar`.

- `net/minecraft/server/network/ServerGamePacketListenerImpl.java:256-268` (`tick`) runs `resetPosition()`, then `player.doTick()`, then restores `firstGoodX/Y/Z` with `absMoveTo` when the player moved from the recorded tick start. The same source audit identifies `:331-338` as `resetPosition` recording `firstGood`/`lastGood`. This means retaining native travel while rejecting position packets is not established by simply disabling that rollback; preventing restore alone risks double movement.
- `ServerGamePacketListenerImpl.java:872-1001` (`handleMovePlayer`) is not merely a position assignment. The inspected path includes rotation/position processing and vanilla fall/floating checks, movement validation, chunk handling, known-movement and statistics bookkeeping. The M0 audit records that bypassing this route can lose those semantics. No exact replacement/interception point has been source-proved here.
- `handlePlayerInput` at `ServerGamePacketListenerImpl.java:376-383` calls `ServerPlayer.setPlayerInput`; the setter only assigns input for a passenger. Thus it is not the ordinary grounded movement input driver. `ServerboundPlayerInputPacket` also has no movement sequence/tick/ack; sprint is separate (M0 audit, source references there).
- Explicit teleport acknowledgement is separate: server teleport ID/ack handling is `ServerGamePacketListenerImpl.java:501-526`, with client handling in `net/minecraft/client/multiplayer/ClientPacketListener.java:733-734`. Preserve that existing path. Respawn/dimension transitions are distinct vanilla transitions, not general movement acknowledgements.

These references characterize vanilla paths; they do **not** prove an exact custom tick hook, packet ordering, compatibility with existing hooks/mixins, or safe transitions. In particular, this audit cannot prove client behavior, wire/order behavior, selector eligibility changes during a tick, collision-adapter correctness, or how the hook composes with the current stun, accepted-move/slip, and travel-friction hooks. If an exact hook cannot be demonstrated against the pinned source and reviewed in context, it remains unproved—not an M2-ready seam.

## Proposed owner-state/mode matrix (not runtime-proven)

| Mode/state | Sole movement owner | Entry/exit rule | Evidence status |
|---|---|---|---|
| Excluded, unbound, or not eligible (including fly/creative/spectator, passenger/vehicle, elytra, swimming, climbing, and unmodeled modes) | Vanilla only | Remain vanilla until a custom enrollment transition is fully acknowledged; on exit, remain custom until vanilla handoff is fully acknowledged | Boundary is proposed; live eligibility selector and transitions are unproved |
| Eligible bound `moonstation14:human`, normal grounded walking | Custom sequenced input + authoritative server simulation/snapshot; client prediction is never authority | Enter only after the custom session transition is acknowledged and the server has assigned custom sole ownership; vanilla proposed-position movement must not also apply | Architecture/scope approved; no adapter, protocol, hook, or runtime proof |
| Eligibility becomes undefined or changes unexpectedly before acknowledgement | No automatic owner change; STOP unless a safe single-owner policy for the current mode is proven | Do not assume the previous owner can safely continue (for example, after entering passenger or fall-flying mode); reject movement that cannot be safely assigned pending owner review | Stop policy; selector timing and safe per-mode behavior are unproved |
| Teleport, respawn, dimension change, disconnect/clone/death | Existing transition/teleport/lifecycle owner until separately completed | Invalidate or drain old input epoch and one-shot edges, establish authoritative state, then perform an acknowledged owner transition; preserve explicit vanilla teleport ID/ack | Vanilla paths exist; custom integration/ack ordering is unproved |

## Required transition contract (proposal only)

Define a **session epoch** plus explicit begin/end transition acknowledgement, not an epoch-only switch. “Owner” here means the movement stream currently authorized by protocol state; it does not mean the entity controller or imply a runtime integration exists. For a handoff from owner A to owner B, A is the only stream accepted and applied while the transition is pending. B's input is buffered without application, or rejected fail-closed. At a server-authoritative atomic commit boundary—only after the mode, epoch, and acknowledgement boundary are validated—the server stops A, clears queued old-epoch input and one-shot edges (including jump), seeds B from the authoritative boundary state, and enables B. A input arriving after commit is rejected; B input from before commit is never applied retroactively. There is no interval in which neither owner is selected followed by speculative activation, nor any overlap of applied streams. The reverse handoff follows the same sequence. If acknowledgement is absent or stale, do not commit or apply B. If eligibility becomes ambiguous or changes unexpectedly before acknowledgement, mark an explicit STOP unless a safe single-owner policy for that mode is proven; do not assume retaining A is safe for modes such as passenger or fall-flying. This is a design constraint, not proof that the existing Minecraft hooks can enforce it. Client/server packet arrival and ordering, including client behavior on a mismatch, remain unproved.

The vanilla fallback is **exclusive by mode**: vanilla movement owns excluded/unbound modes; custom movement owns only successfully enrolled supported mode. It is not an alternate stream accepted alongside custom input and never a temporary overlap during handoff. Vanilla rotation and explicit teleport ID/ack handling must remain compatible without restoring client position authority for a custom-owned actor. Respawn/dimension behavior remains its separate vanilla transition path unless a reviewed design proves otherwise.

## Original M2 stop gate and current acceptance checks

The following was the original implementation stop gate; the owner has since authorized the bounded experiment. These items are still proof/acceptance obligations and must not be treated as satisfied merely because candidate hooks now exist:

1. Exact server tick/hook ordering and how the `resetPosition`/`doTick`/`absMoveTo` rollback is handled without freezing or double-moving.
2. Exact enrolled-mode vanilla position gate while preserving required rotation, vanilla validation/bookkeeping semantics (or an explicit reviewed replacement), and teleport ID/ack behavior.
3. The begin/end acknowledged session-epoch transition and eligibility/mode matrix guarantee exactly one owner across tick boundaries, including ambiguous/pending eligibility and lifecycle transitions.
4. Compatibility analysis of current movement/stun/slip/friction hooks and an established real connected-client smoke path.

Source inspection and automated server tests cannot prove packet ordering under live networking, client prediction/behavior, eligibility changes midtick, hook/mixin compatibility in a running mod, or Minecraft collision adapter correctness. No authenticated connected-client proof exists. M2/M3 acceptance remains OPEN until the owner reports the connected smoke and verifies single-owner mode/teleport behavior; do not claim the experiment is playable or accepted beforehand.
