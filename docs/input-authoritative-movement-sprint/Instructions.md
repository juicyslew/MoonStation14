## Desired authority and gameplay contract

- Character identity and movement policy are bound to the character, not its controller. A connected player and a real Minecraft Villager use the same existing `moonstation14:human` prototype and shared motor policy. Separate adapters translate network button intent and AI wishes into the same normalized motor command; controller identity is authorization/diagnostic context only. A Villager is a Minecraft AI host for the same local human profile, not a claim that it is an SS14 `MobHuman`.
- For enrolled, supported characters, the server owns position, velocity, collision resolution, external impulses, slip admission/effects, status and reactive Touch outcomes. The client sends intent (direction/buttons/jump/sneak/sprint as supported), never a position, velocity, collision result, “I slipped” assertion, or reagent/damage result. Reject or disregard vanilla client-proposed movement for these enrolled characters; do not give a second movement path authority.
- The shared motor consumes a tick-scoped command and advances state using the same documented movement constants/operations on server and client: walk/sprint wish, acceleration, gravity, friction/retention, external impulse, and Minecraft collision resolution. Preserve external momentum when voluntary input is zero. During stun, suppress voluntary wish only; existing slip launch velocity, gravity, collision response, and friction continue. Do not zero velocity or freeze all physics merely because the player is stunned.
- Send authoritative snapshots with an acknowledged input sequence/tick. The client restores that state and replays newer pending inputs using the shared motor. Status and character identity remain synchronized by their existing owners; movement sync must not become a per-tick `MS14Provider` attachment or duplicate status/provider traffic. Per-tick motor state is separate, transient, bounded high-frequency protocol state.
- The initial enrollment is only bound `moonstation14:human` on normal grounded walking. Unbound characters, spectator/creative-fly, passengers/vehicles, elytra, swimming, climbing, and any other unmodeled movement mode retain vanilla handling until explicitly designed. At every boundary, a safe handoff has exactly one authority: disable and drain/reset the old input stream, discard stale sequence epochs/one-shot jump state, establish authoritative state, then enable the other path. No per-tick teleport synchronization. Preserve vanilla rotation handling and explicit teleport acknowledgements; handle respawn and dimension changes as vanilla transitions, not as general movement acknowledgements.

## Shared motor and server-validation rules

The pure motor is state-in/state-out: finite position/velocity/ground flags plus a tick command and explicit environmental inputs produce next state and collision intent. Separate command translation from simulation so the player adapter and Villager AI adapter are independently testable but cannot diverge into separate physical policies. The AI may provide wishes from its navigation/controller; it does not bypass collisions or directly set final character position. Use vanilla world collision routines on both sides where feasible; document and reconcile unavoidable server/client environmental divergence from snapshots.

Input handling is intent-only and server validated. Scope a per-player bounded queue by player and mode/session epoch; cap input frequency, queue depth, accepted sequence/tick window and any catch-up work. Reject stale, duplicate, malformed, nonfinite, out-of-range, and implausibly future commands; define missing-input behavior (hold safe continuous buttons only within a bounded policy, never repeat one-shot actions). Bound memory and clean up on disconnect, clone/death, dimension change, and mode exit. Snapshot/ack cadence and input coalescing must be measured, not assumed. Apply server-side velocity, collision, game-mode and movement-mode checks; a packet cannot ask for an arbitrary displacement that can trigger slip/contact. Player slip detection currently checks the authoritative collision-resolved endpoint AABB only (not the path); very fast endpoint-crossing contacts may be missed. Only the current slip system can admit slip, stun, status, chemistry, or Touch.

Keep existing identity/status source prototypes and `MS14Provider`/`MS14Bridges` ownership. Do not move `CharacterData`, status/reagent definitions, slip systems, or provider state into the motor; do not rewrite their systems or source JSON as a hidden movement dependency. The `MS14Provider` lifecycle rules remain authoritative for attachments: absent reads do not materialize, persistent/synchronized state stays with its existing owner, and changes finalize through their provider (`../reagent-status-sprint/architecture/entity-attachment-lifecycle.md`).

## Bounded chain-slide acceptance scenario

Prove a real, authenticated connected player—not only FakePlayer, test seam, or Villager—runs continuously over a straight lane of **three separately qualifying Space Lube puddles** and traverses the entire lane within an explicitly bounded number of server ticks. During M1 pure-motor simulation/fixture design, choose and record a **numeric maximum-tick bound**, exact lane dimensions, starting speed and input, and slip/knockdown states, derived from the measured/pinned movement policy. Complete and freeze that record before M4 integration or any manual trial; M4 must assert traversal in no more than the recorded bound. Revise the frozen bound only with owner-approved evidence—never tune it upward in response to a failed trial. Do not invent or hardcode a tick value in this design before that evidence exists. Use the current local puddle behavior as fixture evidence: overflow is 50 units, maximum is 1,000 units, and slip activation requires **more than 15 units per tile**. Prepare each puddle with 20 units Space Lube (and reset/refill between repeated trials); confirm each independently remains above the threshold during the intended crossing. Do not silently change source quantities, thresholds, or reagent definitions to make the test pass.

Assert actual server-recorded slip events and Touch effects according to the pinned latch, super-slippery, and already-sliding gates. **Do not require exactly three SlipEvents** just because there are three tiles: upstream gates can suppress another event while already sliding. Assert no repeated Touch while the player is already sliding, and account for each source's actual current solution when a Touch split occurs. Also prove responsive server collision against a wall/solid obstacle while directional wish is suppressed by stun: player-originated input cannot penetrate/teleport through it, yet existing external slip momentum/gravity/friction continue to resolve. Record the actual slip count, per-puddle contact, Touch count/dose, state snapshots/acks, and tick duration. Run the corresponding AI wish adapter with the same prototype/motor policy on a real Villager; it is a separate proof and does not substitute for the connected player.

### M2 — bounded server owner and adapters (**experimental implementation; acceptance open**)

Add per-tick authoritative server motor, bounded per-player input queue/protocol adapter, and separate Villager AI wish adapter through vanilla collision. Gate enrolled player vanilla position packets precisely; retain vanilla routes for excluded movement modes, rotation, teleport and vehicle fallback. Add state epoch/handoff with no double owner and no one-shot stale input. Integrate authoritative displacement with player endpoint-AABB slip checks (not swept path); never feed client-proposed destination into contact. Test protocol limits, disconnect, clone/death/load, dedicated-server classloading, collision, mode transitions and security. No client prediction yet beyond a narrowly justified handshake if required.

### M3 — client prediction and snapshot reconciliation (**experimental implementation; acceptance open**)

Implement supported human client intent sampling, prediction with the shared kernel, authoritative snapshot/ack, pending-input replay and correction. Maintain existing synced character identity and status availability; movement snapshots must not emit status/provider traffic. Test adverse latency/jitter/reorder/loss within a documented protocol policy, reconnect, teleport/respawn, dimension change and every supported-to-vanilla mode handoff. No per-tick teleport sync. Connected owner smoke is mandatory before acceptance.

### M4 — integrated slip/stun/Touch and chain lane

Use actual logged-in player and real Villager with the same `moonstation14:human` policy. Preserve slip, status, reagent, and Touch providers/source prototypes untouched. Verify the three-puddle scenario and collision-under-stun requirement above, source qualification, authoritative slip counting according to upstream latch/super-slippery/already-sliding gates, current-solution Touch amount, and no repeated Touch while already sliding. Record what actually happened; do not force three slips or alter existing provider/system ownership to satisfy a numeric count.

### M5 — security, performance, validation and owner handoff

Review attack surface, mode handoffs, lifecycle cleanup, fallback behavior, packet/state schema compatibility, logs, documentation and measured performance. Benchmark evidence at **20 and 50 simulated supported players around 20Hz** with reproducible workload, hardware/runtime notes, motor/collision CPU, allocation and queue memory, input/snapshot packet counts/bytes, and latency/correction distributions. Set the per-player buffer cap, snapshot cadence, packet budget and CPU guard only from measurements and protocol analysis; do not invent hard-coded “safe” guesses. Verify no status/prototype/provider packet spam. Report limits, raw evidence, connected-client owner checklist and any blocked gates.
