# Integration status board

Run `./integration-status.ps1` to render and open the read-only board at `work/agent_exchange/integration-status.html`. Use `-NoOpen` to render without launching a browser. The responsive board has four columns, in order: **Working**, **Waiting on Validation**, **Active Validation**, and **Ready for Manual testing**. It displays one card per canonical agent worktree; related projects and child work appear inside that agent's card. Only `owner_attention.collect(...).awaiting_owner` supplies active manual-review state; old technical passes or prior manual-review history cannot recreate one. Ordinary owner feedback moves the card back to agent work through the observer; there is no manual clear or sign-off action on this board. Give feedback to the agent in the normal conversation. A technical pass is not owner acceptance.

Core coding slots **01–04** alert once per confirmed idle episode; simultaneous alerts are grouped. Waiting for validation or manual testing is not idle. Main remains a non-core card. Integration slot 05 is a coordinator, not an owner-triaged card, and is not shown as a card. The single hidden observer checks current OpenCode execution, including child sessions, every ten seconds and remains running to monitor idle cores. API failures mean **unknown**, not idle. Arbitrary detached external jobs outside tracked validation are not execution evidence.

Ready and idle notification balloons open the integration-status page when clicked. The hidden click listener exits on click or after two minutes; persistent Action Center activation is not guaranteed. Real Windows display and click-through require a manual check; syntax and mocked transport tests do not establish them.

The renderer is read-only: it does not contact OpenCode, dispatch gates, or make decisions. `agent_status.py` owns the canonical worktree projection and `agent-status.json` supplies authenticated execution observations. Author CLI labels are not profile identities. A candidate-bound running check or currently executing integration-lead review is **Active Validation**. A live queued runner is **Waiting on Validation**, including when its lead is waiting for the serialized validation mutex. Review cards never invent check counts or PIDs. Stale or unavailable observation is visibly unknown, not a verified empty queue.

Candidate-bound `progress/` and `gate-health/` sidecars are operational evidence, not verdicts. Only the persisted candidate outcome establishes technical completion. Poll timestamps do not prove execution. Old legacy results may supply explicitly unconfirmed context inside an agent card, but cannot recreate manual readiness. Owner response, explicit owner acceptance, and author-completion delivery remain separate.

Progress updates preserve `stage_started_at` while the phase is unchanged. Heartbeats must not rewrite command arguments, log paths, runner/child PIDs, or real-check evidence; only actual phase/check transitions update those fields. Old superseded requests are not current queue heads; owner attention selection remains owned by `owner_attention.current_work`.
