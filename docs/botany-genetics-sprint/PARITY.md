## Genetics, generation, and transmission

`Content.Server/Botany/SeedPrototype.cs` defines `SeedData`; `SeedPrototype` derives from it. Prototype values are shared defaults. Mutable instance data is separate from `PlantHolderComponent` age, health, soil, pests, mutation level/modifier and readiness. `EnsureUniqueSeed` clones before metabolism/mutation only when `Unique` is false. `Unique` is a copy-on-write hint, not an ownership registry.

Verified sharing boundaries: `GenerateProduct` marks genetics shared when yield exceeds one or harvest repeats; extraction marks shared when packet count exceeds one; sampling marks shared. Planting, packet spawning and swab capture do not themselves mark shared. A repeat tray therefore clones away from previously harvested fruit on its next genetic change. Pollen captured while `Unique=true` can observe later in-place parent changes; automatically snapshotting every transfer would change that behavior. Preserve this through a concrete server/reference and item-codec boundary without mutating Minecraft component values behind existing revision/network owners. Source: `BotanySystem.Seed.cs:102–116,150–179`; `SeedExtractorSystem.cs:43–52`; `PlantHolderSystem.cs:194–205,306–309,982–988`; `BotanySwabSystem.cs:63–76`. Architecture mapping is in progress; no persistent shared-reference framework is presumed necessary.

`Clone()` copies chemical/gas dictionaries (value-type entries), product/target lists and mutation list. Mutation objects themselves are shared prototype records. Species change replaces identity/output/visual/stage metadata but retains many genetic stats, tolerances, gas maps, potency, harvest mode and mutations. It merges target chemistry and removes old inherent chemicals absent from the target; acquired non-inherent chemicals are different.

`BotanySystem.Produce.cs` resolves instance seed before prototype ID, clears initial solution contents, and generates chemistry from that instance. Amount is `Min + potency / PotencyDivisor` only when both divisor and potency are positive, clamped to Min..Max; generated capacity follows the upstream consumer. Do not sum prototype initial food contents with grown chemistry. Juice extraction is separate from grinding `food`.

Generation also **ensures the named solution at zero initial capacity**, creating its manager if necessary (`BotanySystem.Produce.cs:23–38`, solution-container `EnsureSolution`). Therefore an admin-spawned Log/Papercane without a declared `food` solution differs from generated produce: generation creates an existing empty solution even when seed chemistry is empty. Chemical mutation may populate it. `SharedReagentGrinderSystem.CanGrind:379–387` tests named-solution existence, not positive volume; completion destroys a non-stack source even at zero volume. Local `grindable` must represent Extractable capability with separate current-source resolution, not imply a fresh solution exists. Current follow-up extends Factory's zero-initial-source path, shares generated-capacity resolution across both produce adapters, and consumes eligible empty sources through the ordinary grinder plan. Lazy initialization reuses `PrototypeEdibleItem.initializeSource` on a copy for query/processing; existing empty state must never refill, absent fresh composition must remain absent. Focused/native validation status is tracked in `CURRENT.md`; these changes are not yet whole-sprint readiness or live non-edible catalog acceptance.
