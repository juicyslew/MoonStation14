# Machine visual state bindings

## Verified upstream mapping

Verified against SS14 `c9df5ef5d675b0d1d226828bddf6b78c28502d91`: `KitchenReagentGrinder` has only `BeakerAttached` false/true, set on beaker-slot insertion/removal; `GenericVisualizer` selects `grinder_empty` / `grinder_beaker_attached`. The grinder has no busy, running, or power-light appearance state. Grinding remains its existing 70-tick behavior and is not gated mid-cycle by power. `SeedExtractor` uses the existing power receiver predicate for an unlit LED overlay: off is static, powered is an eight-frame animation at 0.1 seconds per frame (0.8-second cycle); extraction has no active animation interval.

## Local state owners and assets

- Grinder `ReagentGrinderBlock.BEAKER_ATTACHED` is a client-visible blockstate projection of its actual shared `MachineItemSlot` beaker slot. `ReagentGrinderBlockEntity.slotTransferCommitted` updates it only after successful committed beaker transfers; initialization reconciles restored/default contents. Chamber transfers do not alter it. Blockstate selectors bind false/true to the already-installed `block/machines/grinder/grinder_empty` and `grinder_beaker_attached` models.
- Extractor `SeedExtractorBlock.POWERED` is projected by `SeedExtractorBlockEntity.projectPowerVisual` during the existing `PowerRuntime` processing-meter solve cycle. It calls the existing `isPowered()` admission predicate; no second solver, watt comparison, or activity state is introduced. Default is off. Selectors bind false to existing `seedextractor_off` and true to existing `seedextractor_unlit`, whose `.mcmeta` retains the installed eight-frame/two-tick timing.
- No prototype fields, authored geometry, UVs, textures, or provenance were changed. Existing model render metadata and grinder blockstate bindings were updated.

## Known parity and validation boundaries

The powered extractor variant now applies the established APC model `neoforge_data` convention only to the isolated `seed_display_inset` north/south faces: block/sky light 15 and ambient occlusion false; only that element is unshaded. Cabinet and bezel remain shaded, and this adds render brightness only (no world-light emission). Existing animated atlas/PNG and eight-frame/two-tick metadata are unchanged. This is a renderer binding adaptation, not new artwork; no GPU visual review is claimed. Grinder busy jitter now consumes the actual `GrinderProgram.active()` projection in `ReagentGrinderBlock.WORKING`: successful start sets it, the existing server completion/tick reconciliation clears it, and initialization reconciles restored state. This is independent of beaker attachment and power after start. The renderer temporarily suppresses the chunk model and directly tessellates the current baked blockstate model once for each actual model render type, supplying current block-entity model data, packed overlay and world lighting; idle rendering remains the ordinary chunk model. Client blockstate `onPlace` transitions advance an ephemeral BE visual epoch, resetting per-BE motion even if no idle render occurred between jobs; no cosmetic state is saved or separately networked. Each BE has its own monotonic render clock and same-job catch-up is bounded by the 3.5-second program duration. The motion helper adapts SS14's client-only amplitude .09 world units, independent .0225-.09/.0225-.03 axes, .01s linear keyframes and exact sign-match OR/random-axis flip behavior to Minecraft model XZ. This source condition can permit repeated quadrants; it is not an all-quadrants-no-repeat rule. Java client cosmetic randomness is separate from server/gameplay RNG. False/true working selectors reuse the exact two installed beaker models. No new artwork or running skin was introduced. JVM coverage is `GrinderJitterMotionTest`; authored native assertions are in `GrinderRegisteredPlayerGameTests.registeredPlayerActivatesGrinderAndControlsSession` (authenticated start, denied busy action, normal completion) and `ReagentGrinderSuppliedPowerGameTests.suppliedApcPowerIsLostDuringTimedGrinding` (power-loss continuation). Native tests are compile-only, not executed; GPU model-pass/translucency fidelity, visual subtlety, and actual client rendering remain unverified pending manual review.
