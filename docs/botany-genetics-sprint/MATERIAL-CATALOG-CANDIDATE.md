The grinder consumer (`Content.Shared/Kitchen/EntitySystems/SharedReagentGrinderSystem.cs`, `CanGrind` and `FinishGrinding`) requires a resolvable named solution, not positive contents. `BotanySystem.GenerateProduct` calls `EnsureSolution(food, 0)`; that creates the named solution when absent. The `grindable` profile flag represents extractable capability, not whether a fresh prototype has a source solution. `BotanySystem.GenerateProduct` calls `EnsureSolution(food, 0)` for every generated product, then clears contents and adds seed chemistry. `EnsureSolution` creates the manager/named solution if absent, so generated Log/Papercane instances may have an existing empty (or chemistry-mutated) solution although their fresh prototypes have no local `source_solution`. Upstream grinder admission checks named-solution existence, not positive volume, and completion destroys a non-stack source even at zero contents (`SharedReagentGrinderSystem.cs` `CanGrind`, `FinishGrinding`). Thus all five source-extractable products set grindable true; consumers must independently check actual current solution presence. Do not persist false grindability merely because a fresh Log lacks that solution, and do not invent an initial food solution. CottonBol/PyrottonBol retain initial 10u food sources (Fiber 10u; Fiber 5u + Phlogiston 5u); both override Edible special digestion. Those food-owned initial contents live only in `IngestionProfile`; genetics-produced chemistry is separate. Candidate ingestion inherits local `food_base` and resolves force-feed delay to 60 ticks from upstream Edible behavior; local codec default 40 is not source parity. No stomach whitelist or trash is added.

ProduceBase and FoodProduceBase both contain `PotencyVisuals` without YAML overrides in these chains. The pinned component defaults are MinimumScale=1 and MaximumScale=2 (`Content.Client/Botany/Components/PotencyVisualsComponent.cs:6–10`); the candidate uses those values in local `produce_base`. None of the five has a juiceSolution Extractable override, so no static juice output is invented.

The reused `ItemProcessingProfile.Log.validate()` resolves IDs through `BuiltInRegistries.ITEM`; this test deliberately codec-decodes metadata only and does not claim that unbootstrapped game registries validated candidate output references.

## Reuse and validation boundary

Authored files are under `src/test/resources/botany-catalog-candidate/{produce_profile,ingestion_profile,extractable_profile,item_processing_profile}`. Following the shared extraction migration, the old `grindable` boolean is removed: all five extraction profiles inherit `grindable_solution_name: food` from `extractable_base`, while Produce retains seed/source/visual composition. This capability still requires a present current solution; it does not fabricate fresh Log chemistry. `MaterialProductCatalogCandidateTest` stages the existing typed catalogs without publication and independently asserts extraction capability. Log metadata is codec-checked against exact intended IDs, not run through registry validation. A future registry-backed check must use the real mod item bootstrap or native registry fixture; do not substitute synthetic/vanilla outputs to imply success.
