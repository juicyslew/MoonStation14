# Generic produce slicing composition

## Upstream mapping

Audited SS14 revision: `c9df5ef5d675b0d1d226828bddf6b78c28502d91`.

In `Resources/Prototypes/Entities/Objects/Consumable/Food/produce.yml`, `FoodProduceBase` inherits `FoodInjectableBase` (`food_base.yml` → `FoodBase` → `EdibleBase` → `BaseItem`) and supplies solution manager, Produce, potency visuals and extraction defaults. Individual fruit/vegetable entities inherit it and mark categories using `Fruit` / `Vegetable` tags; these are tags, not inheritance parents. `ProduceSliceBase` inherits `FoodInjectableBase`, sets the `food` solution capacity to 3 units with Nutriment 2, and adds slice visuals/extraction/Tag defaults. Concrete slices inherit this base.

Slices do not inherit Produce/seed identity or PotencyVisuals. Pineapple slice retains the base food3u/Nutriment2 and separately juices to 2u JuicePineapple; watermelon slice overrides food to 5u/Nutriment2+Vitamin1+Water2 and juices to 4u JuiceWatermelon. Static juice is not added to initial food. Onion/onion-red slices have food capacity5u/Nutriment2+Allicin1+Vitamin1 and no static juice. FoodPumpkin has Knife Butcherable outputs, **not** SliceableFood; no pumpkin slice should be invented. These source compositions do not establish output registration/assets or live slicing validation.

`SliceableFoodComponent` (`Content.Server/Nutrition/Components/SliceableFoodComponent.cs`) declares nullable `Slice`, default `TotalCount=5` (`count`), `SliceTime=1f`, `SpawnOffset=.5f`, and a default chop sound. `SliceableFoodSystem` starts a knife-use do-after with break-on-damage/move and hand requirements; completion obtains the source Edible solution, requests `solution.Volume / TotalCount`, creates each separate output, splits source contents, replaces each slice's solution contents subject to its available capacity, then deletes the source. Spawn placement is near the source with random velocity when not contained. Upstream `SpawnOffset` is declared but not consumed by the inspected system.

The local item-processing composition models the consumed output, count, and delay fields only. Upstream `SpawnOffset=.5` is declared but unused by `SliceableFoodSystem.Slice`; it is intentionally not represented locally. Fruit/vegetable inheritance and tags remain in upstream prototypes; local item processing profiles are generic and no production slicing profiles/placeholders are added here.

## Local resolved composition and domain contract

`ItemProcessingProfile.sliceableFood` is optional and inherits through the existing item-processing prototype merge/default behavior. Its `output` is required when present; defaults are count 5 and delay 1 second. Upstream's unused SpawnOffset is not a local field. Intrinsic item-processing validation checks output registration and numeric bounds. `ModItemProcessingProfiles.validateResolvedSliceOutputs` then checks output `IReagentTrait` support and its positive-capacity FOOD edible solution against the exact candidate ingestion catalog. `PrototypeManager` invokes this candidate-wide check after resolving all staged catalogs and on decoded encoded-snapshot publication, before atomic publication. This avoids reads from a potentially stale global server catalog. The profile is a data prerequisite, not a runtime slicing implementation.

`SlicingPlan.prepare` accepts the **current** source solution contents in integer cents, a count and resolved output capacity in cents. It calculates one request as `floor(initial total/count)`. For each output in turn, it extracts that full request from the **remaining** source using canonical `ReagentUnits.split`, subtracts the complete extracted map, and only then splits/caps that extracted map to output capacity. Capacity overflow is lost and never returned to the source or redistributed. Each result describes one independently created output entity; no genetic carrier data is copied. The source is expected to be deleted by the future runtime consumer, so source contents not represented in outputs are lost: 101 cents / 5 yields five 20-cent outputs (1 cent lost); 103 / 5 yields five 20-cent outputs (3 lost). Sequential extraction preserves species totals (for A=2,B=1,count=3, the outputs are A1, A1, B1); repeatedly splitting an unchanged source would incorrectly duplicate A.

### Deliberate rounding departure

SS14 `SliceableFoodSystem.TrySliceFood` repeatedly calls `SplitSolution` on the remaining solution with the fixed volume request. Its proportional `Solution.Contents` iteration order and sequential division/remainder behavior can differ from this repository's stable canonical resource-location split. Parent-approved local policy is to use `ReagentUnits` and its deterministic canonical split; no ordered reagent storage or shared chemistry behavior is changed to emulate upstream map-order rounding. This is an explicit, tested Minecraft/domain departure, not claimed exact reagent-by-reagent parity.

## Implemented runtime notes

`LooseFoodSlicingService` admits an authenticated nominated `USE_TARGET` only with resolved sliceable-food composition, a live active hand carrying the independent `Knife` utensil capability, and supported FOOD source/output ingestion compositions. The current ingestion API has no source solution-name field; the supported local single-solution food adaptation requires the source trait's `solutionName` to be `default`, matching the source solution materialized by current `PrototypeEdibleItem` (`IReagentTrait.solutionName` default, source data from resolved `IngestionProfile.Edible.SourceSolution`). Other named reagent containers are deliberately not sliceable under this composition.

Timed completion reads the source's then-current reagent attachment, resolves the output's current source-solution capacity, and calls `SlicingPlan.prepare` for one independent child map per output. Fresh count-one stacks receive only those reagent maps; no source genetics/components are copied. Only the source edible profile's trash list is appended once (child edible trash is not propagated). `FreshWorldOutputBatch.publishAtSourcePosition` stages all outputs before source discard and uses its existing collision-safe .25-block placement adaptation. On post-commit callback, slice children (not configured trash) receive randomized horizontal velocity: SS14 `NextVector2(2.0,2.5)` m/s maps to .1–.125 Minecraft blocks/tick, with a level-owned random angle/speed. Profile/hand/target/source proofs are revalidated until batch commit. Failure before publication denies without source mutation; the batch owns compensation and uncertain-commit recovery.

Successful publication plays SS14 `Content.Server/Nutrition/Components/SliceableFoodComponent.cs`'s default `/Audio/Items/Culinary/chop.ogg` at -2 dB.
