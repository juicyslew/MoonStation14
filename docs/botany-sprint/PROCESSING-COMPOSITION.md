# Botany produce and processing composition audit

Pinned upstream checkout verified at `c9df5ef5d675b0d1d226828bddf6b78c28502d91`.

## Produce

The five logical produce IDs are `wheat_bushel`, `tomato`, `potato`, `poppy`, and `aloe`, matching the seed catalog's `wheat`, `tomato`, `potato`, `poppy`, and `aloe` identities. Upstream `BaseProduce` supplies seed association, potency visuals, extractable metadata and a named grind solution. Four ordinary food leaves inherit `FoodProduceBase -> FoodInjectableBase -> FoodBase -> EdibleBase -> BaseItem`; wheat inherits `ProduceBaseRuminant -> ProduceBase -> BaseItem`. The local `ProduceProfile` owns only seed association and grindability. Contents, capacity and food timings belong to existing `IngestionProfile.SourceSolution` / `Edible`; no parallel food-source catalog is introduced.

Verified initial leaf solutions/capacities (hundredths of units): wheat bushel Flour 1000; tomato Nutriment 700, Vitamin 300, Water 400 (1400); potato Nutriment 1000, Vitamin 400 (1400); poppy Nutriment 200, Bicaridine 2000 (2200); aloe Aloe 1000, Dermaline 1000 (2000). Ordinary food leaves use 500-cent dose, 20-tick eating, 60-tick force-feed delay. Wheat's `requiresSpecialDigestion`/ruminant composition is unsupported locally: it is not ordinary human/mouse food. Tomato juice is a separate JUICE solution and is intentionally not an added grind recipe. Wheat's flour output is grindable but its food source is not edible. Poppy-head clothing and other unsupported component behavior are deferred.

The upstream item component parent chain gives all five produce items nonstacking behavior and small source footprint. On harvest, generated chemistry replaces (does not merge with) the initial food contents, while solution capacity starts at the resolved initial source capacity and increases by the sum of generated reagent amounts. This follows `BotanySystem.Produce.cs` (`EnsureSolution(..., 0)`, `RemoveAllSolution`, then per-chemical `MaxVolume += amount`); `Solution.RemoveAllSolution` clears contents without resetting capacity. Local construction reuses the resolved `ProduceEdibleItem.getCapacity(stack, null)` source owner. Thus wheat at potency 5 has 650 generated cents and 1650 capacity (1000 initial); tomato at potency 10 has 441 generated cents and 1841 capacity (1400 initial). Do not clone initial food into harvest contents or restore depleted source on grind/eat.

## Machine inheritance and behavior

`SeedExtractor` inherits `BaseMachinePowered -> BaseMachine -> BaseStructure` (plus `ConstructibleMachine`); `ReagentGrinder` inherits the powered/base/structure chain through `SmallConstructibleMachine`. Upstream component defaults: both receivers override base 1000 W with 0 W; grinder active draw is 750 W, inactive 0 W, start delay 3.5 s / 70 ticks, chamber capacity 6, and its beaker admission is the existing `BeakerFitsInDispenser` capability. The extractor operates immediately on a valid produce+seed target, consumes one produce and returns 1–3 packets; it has no grinder chamber or timed processing. Local machine profiles expose only supported policy values, not a fictional APC component or unsupported YAML component mirror. Machine operational consumers are intentionally deferred.

## Live-integration notes (upstream behavior and local wiring)

The local seed-extractor foundation now registers a native block and block entity, resolves `seed_extractor` from the server machine-profile catalog, and initializes/persists placement identity on the first server tick. It deliberately has no chamber, UI, held-item actions, consumption, packets, or processing pipeline. Zero-load profiles follow the upstream receiver rule (`!PowerDisabled && received == load`), so default-enabled zero-load profiles are available without an APC/energy source. The local disabled/wire-toggle state is deferred; positive configured wattage fails closed until shared positive-allocation integration exists. The cube texture model is only a native fallback, not commissioned geometry or visual acceptance.

The pinned source establishes that `SeedExtractorSystem.OnInteractUsing` checks power, consumes one eligible produce, and resolves the seed from the produce's `Produce.Seed` instance before falling back to its `SeedId` prototype. It creates 1–3 seed packets inclusive at the extractor's coordinates, then calls `TryPickupAnyHand(user)`; packets the user cannot pick up remain in the world. These are source findings, not claims about local runtime behavior.

The grinder's upstream chamber holds six items. Insertion does not start processing: the user explicitly starts Grind through the UI. Admission requires power, a fitting beaker, and all inputs grindable; removal/ejection is forbidden while busy. Completion takes 70 ticks and does not recheck power. Basic grinding is the current scope; Juice is deferred. Its zero-load receiver is not evidence of energized APC supply: `PowerNetSystem.IsPoweredCalculate` returns `!PowerDisabled && (!NeedsPower || CloseToPercent(ReceivingPower, Load))`, so zero received power satisfies a zero load when power is not disabled. Do not invent a 1 W load or require energized network for zero-load admission; local integration needs a receiver-disabled policy consistent with the existing boundary. The separate 750 W active meter does not imply that an already-started grind stops on power loss. Local processing audio is one-shot to the exact machine/start tick, ending at tick 70 or matching server STOP; stale STOP is ignored, and power loss does not abort. The resolved role helper uses `beakerInsertSound`, `beakerEjectSound`, and `chamberEjectSound`: chamber insertion is silent; successful chamber ejection plays `machine_switch` at -2 dB once per nonempty batch. Beaker insert/eject and revolver-mag insert/eject use inherited defaults (0 dB, pitch 1). Parent machine components `BaseMachinePowered` and `SmallConstructibleMachine` supply insert/eject defaults; neither overrides them. The upstream `ItemSlotsComponent` full-chain audit corrects the earlier incomplete YAML-only conclusion that slot sounds were absent. Camera-body recipients get processing and native slot cues. These are existing CHEM_MASTER assets with unknown provenance; human audibility remains unverified. Feedback-5 focused role tests pass, while its serialized technical gate is pending.

Local factory/native produce-capacity checks remain 1650/650 and 1841/441; no numerical changes are indicated. The five native checks passing does not implement live machine behavior: machine consumers remain deferred. Produce provenance remains unknown.
