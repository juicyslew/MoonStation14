The owner-directed bounded smoke is closed with residual turning-while-moving jitter deferred, but no authenticated latest-session Begin/Commit evidence was supplied; see the [bounded handoff](audits/2026-09-27-ghost-owner-bounded-handoff.md) and [look and transfer notes](audits/2026-09-27-render-frame-ghost-look-and-transfer-notes.md). The generic grounded Mob preparation remains a bounded foundation, not live Mind-to-Villager/Pig control.

- **Mind:** a distinct control-session identity bound to the authenticated player/session owner ID. Keep Mind ID separate from the authenticated session owner ID. The target is exactly one active Mob Harness during active play; no temporary harness-less ghost state. The only no-harness exception is server-owned lobby status, which is not modeled yet. See the [single-route architecture decision](architecture/single-mind-harness-movement-route.md).
- **Mob Harness:** every entity controlled by a Mind, including the ghost, is an explicitly registered/eligible harness. Track a `MobHarnessKind` (at minimum `GHOST` and `CHARACTER`) and maintain an exclusive registry: one active harness per Mind and one Mind per active harness. A harness transfer replaces the Mind's active harness; it does not create a default vacant ghost-Mind state.
- **Minecraft transport seam (desired model):** retain the Minecraft `ServerPlayer` as an invisible spectator/session carrier as needed for authenticated vanilla connection transport and view, with no character status. Current runtime does not yet meet that identity separation: `CharacterIdentitySystem.enrollSupportedActor` binds HUMAN to `ServerPlayer` on join, and the ghost debug command does not remove or override that attachment. The spectator carrier remains an actual player entity; its visibility to other spectators is unverified. It is not the ghost Mob Harness and must not be treated as controllable. The ghost is a separate, server-spawned non-`ServerPlayer` entity, independently movable and viewable. Register and render it through the approved mod bus; do not copy upstream SS14 audio assets.
- **Creation and transfer:** the current experiment creates a ghost harness only on explicit `/ms14 mindghost start`; `BodyControlRegistry` currently creates a Mind only with an eligible registered ghost and has no lobby state. This command experiment does not provide the target active-play lifecycle: `GhostMobHarnessControl` has only one authenticated-client experiment and the carrier `ServerPlayer` still has a HUMAN attachment. Do not claim on-join creation, NPC transfer, lobby behavior, carrier identity separation, or acceptance. The legacy ServerPlayer movement route is transitional and is scheduled for gated retirement, not a permanent second path. See the ordered migration in the [architecture decision](architecture/single-mind-harness-movement-route.md).
- **Future possession lifecycle (design constraint, not implemented):** entering ghost mode must release the currently controlled character Mob Harness into the world, create/register a ghost Mob Harness, and atomically transfer the same Mind to it. Possessing a configured body must only remove/despawn the former ghost after successful Mind unbind; a failed transfer must leave the ghost intact and active (no half-transfer). Returning to ghost mode creates a new ghost as the active harness while leaving the body in-world, with exclusive Mind ownership and no conflicting AI control. Vanilla spectator clicking a mob is not this operation. The existing `/ms14 mindghost start|stop` are temporary recovery/debug semantics only; once real transfers exist, the user-facing operations must be enter-ghost and spawn-body/enter-body or an explicitly validated click, with no “stop ghost mode” that strands a live Mind.
- **Eligibility and scope:** configured Mob Harness eligibility applies to any supported `LivingEntity`; do not claim that every entity is supported or that SS14 restricts its entities to Minecraft `LivingEntity`. The ghost harness is also living/controllable in this local model. The first NPC fixture is a configured human Villager. Movement/look only initially; no actions, inventory, attack, or arbitrary interaction authorization.
- **Authority and safety:** the server owns Mind-to-harness bindings and validates authenticated input. For the ghost, the client may predict the shared deterministic motor only for its locally owned camera ghost; the server applies accepted intent and remains authoritative for world position, external effects, and status. Never take a packet-selected target or client position claim. Ghost collision parity is not implemented (`noPhysics` bypasses ordinary and entity collision). Keep the ghost feature default-off; the legacy route remains transitional pending the gated single-route replacement, not a permanent parallel path. This is not a blanket client-authority rule. See the [prediction audit](audits/2026-09-26-ghost-shared-motor-prediction.md).

### M2 — ghost entity and real input/movement (bounded owner smoke closed; broader acceptance pending)

Shared experimental integration now exists behind the COMMON NeoForge boolean `experimentalMindGhostControl` (default `false`) and the op-level-2 `/ms14 mindghost start|stop` command. Starting also remains rejected while the legacy `experimentalVerticalSliceMovement` gate is enabled; retain that conservative conflict gate, and retain the legacy flag default-off as a transitional path rather than removing it. The command creates a separate non-player ghost harness and server-owned Mind; the carrier remains a spectator. The implementation is experimental, guarded by a default-off config boolean, and explicitly command-triggered; neither configuration nor login automatically starts ghost control.
