## Delivered foundation (source-derived)

- `src/main/java/com/juicyslew/moonstation14/ms14/player_body_control/movement/HumanHarnessMotor.java` is a pure per-tick adapter around the same `CharacterMovementMotor` configured with `CharacterMovementPolicy.HUMAN`. It accepts bounded quantized local wishes and yaw, normalizes diagonal input, and passes jump/sprint and the supplied movement state/environment/stun status to the shared motor. The caller owns tick timing, gravity, collision/support, and movement factors; the adapter creates no world or controller integration.
- `src/gametest/java/com/juicyslew/moonstation14/gametest/HumanHarnessMovementGameTests.java` registers a GameTest using an enrolled real Villager resolving as HUMAN, grounded on stone. It checks 20 forward ticks and a grounded jump while invoking one `Entity.move` collision resolution per test tick. The fixture injects `dt=.05`, gravity `32`, jump `8.4`, drag `.98`, zero surface velocity, zero external impulse, and neutral surface/voluntary factors of `1`; it is deliberately no-AI.
- `GhostControlPayloads` Begin/Snapshot use protocol version 2 and include server-authored shared `MobHarnessKind` and harness ID. Snapshot also carries velocity, on-ground, surface, voluntary, and stunned context. Bound validation permits surface factors through 64 and voluntary factors through 8 (as well as the existing bounded fields). Ghost-default overloads preserve ghost call sites. The ghost-only networking/controller/client rejects CHARACTER Begin and Snapshot rather than enabling character control. Client/server peers must both use version 2.

## M3a single travel owner proof

- `src/main/java/com/juicyslew/moonstation14/ms14/player_body_control/character/MindControlledVillager.java` is the new character interface. `VillagerMindHarnessOwnerMixin` supplies a synced Boolean marker defaulting to false. `LivingEntityMindHarnessTravelMixin` cancels vanilla travel only for marker-true Villagers, on both logical sides; `Mob.noAI` alone does not claim travel ownership.
- `HumanHarnessLease.tryAcquire(Villager)` is the new server-side single-owner preparation. It succeeds only for a live server Villager enrolled as HUMAN with the explicitly configured persistent marker `moonstation14:configured_mind_harness`, and only when it is not a passenger and has no current synced owner marker. It stops navigation, records the exact prior `noAI`, sets `noAI` true, and sets the synced owner marker true. Its idempotent `AutoCloseable` release attempts to restore the prior `noAI` value and clear the marker, but restoration is currently best-effort and exceptions may be swallowed (open stop gate below). The persistent configured marker is an explicit eligibility opt-in, not a blanket rule for every Villager. The lease does not transfer a Mind, register an op command, establish inventory/status ownership, or require a connected player.
- `HumanHarnessWorldStep` is a stateless server adapter. It validates a live server Villager with the marker and a resolved HUMAN identity, then calls `HumanHarnessMotor` and real `Entity.move` once. Its server step uses gravity `32`, jump `8.4`, drag `.98`, `SlidingFrictionSystem.factor`, shared HUMAN knockdown `.4`, and stun; it publishes velocity. There is no input subscription, controller, Mind binding, or client prediction yet.
- `HumanHarnessTravelOwnershipGameTests` proves a marked Villager does not vanilla-travel between adapter steps, an unmarked `NoAI` Villager still vanilla-travels, and clearing the marker resumes vanilla travel. `HumanHarnessLeaseGameTests` covers marked and unmarked acquisition, duplicate acquisition rejection, and restoration of prior AI state. These are server GameTest fixtures, not proof of client tracking/synced-marker delivery. `HumanHarnessMovementGameTests` remains a separate synchronous motor/collision fixture; none proves live possession or connected control. `HumanHarnessWorldStep` remains a stateless server adapter and is not scheduled automatically.

### Follow-up fail-closed guard

This closes that adapter precondition gap only; it does not establish live actor control. Dedicated-run output did not list the new HUMAN test, so its latest execution is not confirmed by that run.

- `HumanHarnessLease.close` currently handles restoration best-effort and swallows restoration exceptions. Harden this before live actor targeting; otherwise cleanup may leave the owner marker or `noAI` state behind.

- If lease/ownership rejection occurs after `Entity.move` has partially changed position, terminate the attempted step; do not retry it.
- There is no connected HUMAN route or owner, actor-targeted Mind/AI ownership remains pending, and client tracking/synced-marker delivery is unverified. Do not claim live handoff, connected control, or lube/slip parity. Ghost bounded feel remains done with minor visual turning jitter deferred.
