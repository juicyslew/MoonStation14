The faithful part of this proposal is **design intent**: keep authenticated user/account, mind/control binding, and character body conceptually distinct; spawn/select a body and attach control; and permit control only for a server-configured eligible NPC set. It intentionally differs in **transport**: SS14 sessions use `AttachedEntity` as their control target, while this Minecraft design keeps the `ServerPlayer` spectator carrier as the player/session entity and needs a custom bounded input relay to move a separate harness. SS14 lobby sessions can lack an attached entity and can lack a mind at times; an in-round ghost, by contrast, is an actual observer entity. SS14 does not establish a persistent Minecraft-like spectator `ServerPlayer` carrier separate from its attached entity. Death, ghosting, and role takeover follow different `Visit`/`TransferTo`/new-mind branches, so neither universal body eligibility nor guaranteed ghost return is claimed here. This feature remains independently default-off; no feature or command exists yet.

In spectator-carrier architecture there is no old physical player body to displace, so this teleport can be acceptable as view positioning after an explicit same-level and acknowledgement policy is proven. **It changes view/position only; it does not route input to the target.** Do not claim it alone possesses the harness.
- `ServerPlayer.tick`:524-534: the carrier follows its camera target and resets camera when that target is dead. This is relevant to view lifecycle and requires explicit behavior for invalid/dead harness targets.
- `ServerPlayer.java:1589-1610`: `setGameMode` resets camera when leaving spectator. A ghost mode lifecycle must avoid accidental gamemode transitions or explicitly restore its view policy.
- `ServerPlayer.java:1724-1732` and `net/minecraft/world/entity/player/Player.java:256-261`: spectator behavior includes no-physics/invisibility-related behavior and restrictions. The `ServerPlayer` spectator carrier still exists as a world entity; `setCamera` teleports/follows that ghost carrier and does not remove it. It is not a playable character body. These facts do **not** prove every client never sees the skin/avatar: co-location, tracking/visibility, and spectator-to-spectator skin behavior need connected proof. No universal invisibility claim is justified by these excerpts.
- `net/minecraft/client/player/LocalPlayer.java:266-315` sends position only when the controlled camera is `LocalPlayer` (`isControlledCamera`:700-702). Local input processing still ticks through `aiStep`:723-745. Thus camera targeting away from the carrier does not itself drive the harness; the initial slice needs a bounded custom intent path to control its target.
- `net/minecraft/server/network/ServerGamePacketListenerImpl.java:872-1001`: vanilla movement handling operates on `this.player` (the `ServerPlayer`), not a camera target or arbitrary harness. Existing vanilla movement packets do not automatically become NPC input.
- Vanilla spectator item/attack paths do not provide the intended harness action routing. The initial design can be scoped to movement/look only and deny action/inventory access while possessed until a separate design exists.

## Proposed bounded design (not implementation approval)

Use a server-side mapping from authenticated carrier/session to harness UUID. Enforce one controller per body and one body per controller; allow the mapping to be vacant while the carrier is a ghost. Every request is authenticated against the server-owned binding: never trust a body chosen in a client packet, and reject spoofed ownership, stale epoch/sequence, replay, duplicate control, or invalid/unconfigured entities. A bounded sequenced/epoch input relay drives movement/look only. The server pauses/arbitrates harness AI, runs collision movement on the target, and acknowledges accepted intent/displacement. The new movement adapter must feed accepted harness displacement into contact/slip admission exactly once when eligible; existing status owners are not derived solely from movement. Treat this as a conditional trigger, not an SS14 guarantee for a ghost. Do not use a per-tick teleport motor.

Return to ghost—not to an original human player body—and clear once on harness death/removal, leave/logout, carrier death/clone transition, dimension change, teleport, or stale epoch. Define server-thread ownership, idempotent cleanup, camera restoration, and fail-closed behavior before coding. While possessed, deny actions, inventory, item, and attack access; a camera switch is not permission to use the carrier's inventory or actions.

Project identity currently enrolls all players and Villagers, so the opt-in must be narrowly scoped. Do not globally strip player character identity, alter normal gamemode behavior, or disturb existing FakePlayer/vanilla flows. Any ghost-only identity prevention/migration, lifecycle hook, movement relay, AI arbitration, target collision, camera policy, command registration, or config change requires a future precise owner-approved shared-file list.
