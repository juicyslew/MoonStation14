# M2b: Ghost-control wire foundation audit

**Status: experimental ghost owner-control is guarded by a default-off COMMON NeoForge boolean and requires an operator command; connected-owner smoke is pending.** The original payload-only foundation and its historical validation are recorded below. See the [sprint instructions](../../../instructions-player-body-control-sprint.md), the [M2a ghost harness audit](m2a-ghost-mob-harness-foundation.md), the [M0c Mind and Mob Harness contract](m0c-mind-and-mob-harness-contract.md), and the [experimental owner smoke checklist](experimental-ghost-owner-smoke.md). The feature does not start on join and is not full M2 acceptance or SS14 parity.

## Delivered wire foundation

- `src/main/java/com/juicyslew/moonstation14/ms14/player_body_control/network/GhostControlPayloads.java` defines validated Begin, Ready, Commit, Intent, and Stop payloads. Client payloads do not contain a position or a body/harness target.
- `src/main/java/com/juicyslew/moonstation14/ms14/player_body_control/network/GhostControlNetworking.java` provides standalone NeoForge payload registration. Its dispatch seam targets the MAIN thread and checks for a connected, non-fake `ServerPlayer` when dispatching.
- No packet handlers are installed. There is no client input sampler, server input consumer, Mind lifecycle/controller integration, executed camera handshake, or gameplay command. No owner-connected player controls the ghost, and no NPC transfer exists.

The packet schema avoids client-selected position and target authority, but these constraints do not establish authenticated Mind ownership in runtime: the server-side lifecycle/controller and handler that would bind and consume intent do not exist. Do not describe the wire registrations alone as control or as an enabled feature.

## Validation and limitations

Focused codec and networking JUnit tests passed. `gradlew build --no-daemon` passed. After network registration, the latest dedicated-server GameTest run completed **119/119** tests; see the [M2a audit](m2a-ghost-mob-harness-foundation.md) for its exact harness additions and the retained 117/117 historical result. A full JUnit `--rerun-tasks` run was not performed after network registration. These checks are interim automated validation and do not prove connected-client behavior.

The ghost renderer remains an invisible placeholder. Its `noPhysics` movement bypasses ordinary and entity collision, including stone walls; SS14 `GhostImpassable` wall/fixture behavior is not supported. No full SS14 parity is claimed.

## Latest experimental control implementation and validation

The implementation has advanced beyond the payload-only state described in the historical sections above:

- `GhostMobHarnessControl` registers op-level-2 `/ms14 mindghost start|stop` on the game bus. Start rejects when the legacy `experimentalVerticalSliceMovement` gate is enabled, avoiding a pending legacy session. There is no config/startup ghost creation or on-join control.
- A start saves the player's previous GameType, spawns a separate non-player invisible ghost Mob Harness, creates its Mind binding, and makes the `ServerPlayer` carrier a spectator. The server sends Begin; the client waits for the tracked ghost entity and sends Ready; the server sets camera and sends Commit. The client then sends bounded intent, which the server applies to the ghost at most once per tick.
- The server logs the commit correlation (player/epoch/entity ID/ghost UUID) and the first accepted displacement. Stop, a 100-tick timeout, and logout perform cleanup. `GhostControlClient` is `Dist.CLIENT`. Network payload handling is on the main thread; this is a server-scoped in-memory session, not persistence or reconnect recovery.
- The existing ordinary player entity remains present while opted in, and the carrier may still have the legacy HUMAN attachment: `CharacterIdentitySystem.enrollSupportedActor` enrolls `ServerPlayer` on join, while this ghost debug command does not remove or override that enrollment. Thus this experiment is not yet the desired no-dedicated-player-character model; identity/enrollment must be separated before that model is met. The carrier's visibility to other spectators is unverified. No NPC body transfer, action/inventory authorization, or on-join ghost behavior is implemented. The renderer remains invisible; ghost `Entity.move` is invoked with `noPhysics`, so it bypasses ordinary/entity collision and does not implement SS14 `GhostImpassable` wall/fixture behavior.

Latest reported validation after the config change: `gradlew test --rerun-tasks --no-daemon` and `gradlew build --no-daemon` both succeeded; the focused `MindGhostStartupGate` JUnit test passed. The dedicated GameTest log at `build/gametest-run/logs/latest.log` records 120 tests started on line 36 and `120 GAME TESTS COMPLETE` / `All 120 required tests passed` on lines 253–254. These are automated checks only. GameTest command/node registration does not prove execution of the actual operator command, and no connected-client owner test has been run. The command remains op-only and is unavailable when either its default-off startup gate is false or the legacy gate is on.

The next bounded evidence gate is the safe owner-run procedure in [experimental-ghost-owner-smoke.md](experimental-ghost-owner-smoke.md). It requires a backed-up world and matching rebuilt client/server; in the correct running installation's `config/moonstation14-common.toml`, set `experimentalMindGhostControl = true` and `experimentalVerticalSliceMovement = false`, then restart so the server samples the default-off gate. Use one real op-level-2 player in Survival or already-Spectator mode. The repository's `run/config/moonstation14-common.toml` is a local gitignored runtime config, not a versioned config template. Skip if it is not safe to disable the legacy experiment. Verify the committed Ready handshake and first nonzero accepted displacement, ghost camera and movement ownership, skin visibility from owner and second spectator, lag/chat observations, and stop restoration. Do not use character status or HUD as proof of the desired identity model: the carrier may retain its legacy HUMAN attachment until identity/enrollment is separated. Abort on missing Begin/Commit, restore failure, unexpected UI, or disconnect. Freeze should be addressed with operator stop or server stop/restart; changing the config does not hot-toggle the running gate and active sessions persist until stopped or restart. Do not expand this to cross-dimension, teleport, respawn, higher-role, or NPC tests, and do not edit atmos configuration.

Do not describe the smoke as acceptance of the full ghost system. NPC transfer and on-join ghost creation, each with a separate opt-in gate, remain deferred. Other outstanding gaps include invisible rendering, all-wall collision bypass, lack of action/inventory authorization, and the absence of connected-client evidence for lifecycle transitions beyond this limited start/move/stop scenario.
