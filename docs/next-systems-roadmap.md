# Next systems roadmap

This is a proposal for after the current sprint closes, not authorization to start another implementation sprint. Favor foundational ownership boundaries over adding isolated content. Keep the existing movement feature disabled by default and preserve its owner-acceptance limits.

## Order and gates

1. **Separate player/session, character, and body; make this the first architectural gate.** `CharacterIdentitySystem` currently enrolls a `ServerPlayer` or `Villager` to the `moonstation14:human` prototype. `CharacterData` is immutable data-only eligibility/policy, not a mind, player account, or character-creation model. Define stable ownership and lifecycle for account/session → selected character → spawned body, including logout, death/respawn, and round transitions, before those features multiply identity assumptions. **MVP/gate:** one authenticated player selects one persistent profile, spawns a body, and a tested respawn/reconnect path cannot duplicate or silently reassign its identity. Keep NPC enrollment explicitly separate. SS14's `Content.Shared/Mind/SharedMindSystem.cs` is a useful conceptual reference, not a Minecraft API to port.

2. **In parallel, run a bounded atmospherics feasibility spike: highest technical unknown.** There is no full atmos solver; the deferred-effect ledger identifies fire's missing oxygen/atmosphere and temperature/heat-capacity owners. Scope a room/chunk representation, boundary/leak behavior, persistence across chunk unload/reload, and measured server cost before promising simulation fidelity. **MVP/gate:** a tiny sealed test room conserves a deliberately simple gas/pressure quantity through a door change and chunk save/reload, with an explicit tick/memory budget and graceful unloaded-boundary policy. Do not make fire depend on a broad solver until this passes.

3. **Round/lobby and character setup, in small modules.** Once the identity lifecycle is established, add a fixed-map round state machine (lobby → setup → play → end), then one role and spawn path, then player role preferences and character profile/creation/persistence. Keep those concerns independently testable rather than building a single “round framework” mega-sprint. Reuse datapack hosting only after verifying reload, validation, persistence, and server integration for each kind of data; it is not automatically a substitute for account/profile storage. **MVP/gate:** deterministic start/end on one predetermined map with one eligible role, correct spawn, and profile/preference surviving reconnect; test invalid preferences and round cleanup. SS14's `Content.Server/GameTicking/GameTicker.Lobby.cs`, `GameTicker.Spawning.cs`, and `Content.Shared/Preferences/PlayerPreferences.cs` are conceptual references for lifecycle and data ownership.

4. **Inventory, hands, equipment, then a generic interaction/action contract.** Minecraft already supplies inventory and `InteractionHand`; Jug, Bottle, and Puddle behavior currently lives in hardcoded interaction callbacks. First specify custom equipment-slot ownership and equip/unequip constraints only if content needs them. Then centralize actions behind a server-validated contract: discover available actions and perform an action with actor, target, held item, range, permissions, and stale-state checks. A client radial/context menu is an optional second presentation of that contract, never authority. **MVP/gate:** two distinct item/target actions share the contract, including rejection tests for out-of-range, unauthorized, and stale requests; existing vanilla interaction remains a safe fallback. SS14's `Content.Shared/Hands/EntitySystems/SharedHandsSystem.Interactions.cs`, `Content.Shared/Inventory/InventorySystem.Equip.cs`, and `Content.Shared/Verbs/SharedVerbSystem.cs` are conceptual analogues, not copyable APIs.

5. **Gravity only after movement authority is settled.** The experimental `ms14/movement/*` path owns supported grounded bound humans; handoff to vanilla movement mode is not proved. Gravity changes could multiply that uncertainty. **MVP/gate:** first prove authority handoff and regression behavior for supported and unsupported actors; only then prototype one bounded zone with entry/exit, fall, and reconnect tests. If authority/handoff fails its gate, leave gravity to vanilla behavior. SS14's `Content.Shared/Gravity/SharedGravitySystem.cs` is a conceptual reference.

## Next-sprint recommendation

Do one deliberately narrow sprint on the **player/session–character–body lifecycle and its respawn/reconnect test gate**, with a written interface that round/lobby can later consume. In parallel, time-box the atmospherics feasibility spike as investigation, not a second implementation commitment. Identity and lifecycle are prerequisites for coherent rounds and future ownership; atmos is the largest technical unknown and deserves early evidence, but should not expand the sprint into a solver. After the owner reviews the gates and accepts scope, choose the next implementation. Content additions such as items/blocks can continue to leverage existing Minecraft hosting without pretending they establish these missing systems.

- Upstream SS14 paths cited above are design analogies only. Minecraft APIs, persistence, and integration must be verified locally before choosing an implementation.
