## Honest telemetry boundary and separately reviewed follow-up

Today `ApcMenu` synchronizes breaker, revision, battery charge, trip latch and visual state, but **numeric external input and output are not synchronized**. `ApcScreen` labels external supply and load unavailable. `PowerLiveLoop.Result` computes per-APC `apcInputWatts` and `apcOutputWatts`, but `PowerRuntime` caches **only output** samples for overload protection, with sample tick, graph-known flag and topology-generation validity checks. That cache is not an authorized numeric client display contract; an absent/unknown/stale sample must not become 0 W. The current data cannot honestly support numeric output or SS14 Low/Good input labels without authoritative freshness, topology validity and dedicated synchronization to each open menu.

Proposed bounded slice, **not delivered or authorized by this note**: review a server-owned, per-APC output meter (actual delivered W against the 20 kW protection threshold) and separate MV input status, explicitly carrying known/fresh/unknown state and units. The protection rule trips only when actual output is **strictly greater than 20,000 W** for its required duration; 20,000 W is not itself a trip, and the bar must not imply an automatic trip exactly at its endpoint. Source output from a fresh solve and do not treat cached solver zero as observed zero on an unknown graph. Invalidate on topology epoch changes, unloaded/replaced APCs, disabled simulation and elapsed-sample expiry; coordinate client updates for multiple viewers and reopening with bounded menu/packet cost. On an opened breaker or trip, do not continue showing a stale pre-open output sample as live delivery: clear/invalidate it or show a newly validated zero only with explicit server authority. Decide status thresholds for MV input separately rather than guessing SS14 Low/Good from battery percentage or the output meter. Review implementation, tests, rights and connected screenshots separately before displaying this telemetry.
