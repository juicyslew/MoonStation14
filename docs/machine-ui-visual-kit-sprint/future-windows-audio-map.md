# Future machine windows, APC audio, and station-map viewport

**Status: design notes only.** Nothing here implements or authorizes a new protocol, window manager, audio prediction, or map service. The [current kit handoff](implementation-handoff.md) remains the implementation/acceptance record; visual-state animation is being handled separately and is **not** declared completed here.

## What APC telemetry can actually say today

`PowerLiveLoop.Result` computes per-APC `apcInputWatts` and `apcOutputWatts` during a server solve. `PowerRuntime` retains an output sample for protection, with solve tick, graph-known and topology-generation checks; the protection observation accepts it only when known, on the current topology, and no older than the 20-tick solve interval. The separately evolving visual-state work does not make either numeric meter a client display contract. `ApcMenu` currently synchronizes breaker, revision, battery charge and trip latch, **not numeric input or output**. The menu's external supply/load labels therefore remain unavailable; unknown or expired data is not observed 0 W. An APC can have an output rating/protection threshold of **20,000 W** without delivering 20,000 W: a meter would show measured delivered output, not rating, input, demand, or an inferred SS14 external-power Low/Good state. Protection requires output strictly above 20,000 W for the required duration; equality does not trip.

If a separately approved telemetry slice is built, define server-owned per-APC samples, units, known/unknown/fresh status, topology epoch, revision and viewer update contract. Invalidate on topology changes, elapsed age, simulation disable, chunk unload or APC replacement, and breaker open/trip; never keep pre-open delivery labeled live. A validated new zero is different from an unknown value. Bound update fanout and verify multi-viewer reopening and recovery. Input status needs its own authoritative semantics, not a color derived from battery percentage or the output meter. See [owner feedback](owner-feedback-and-next-slice.md) for the proposed meter boundary.

## Several machine windows are not several vanilla menus

Today a player has **one active vanilla Minecraft `Screen`/`containerMenu`**. `ApcMenuService` opens a per-viewer APC menu/session and validates toggle requests against that player's current container ID, session, loaded block entity, distance/access and breaker revision. Multiple viewers can open the same APC and see updates; this does **not** mean one player can keep multiple independent live machine menus open simultaneously. The client-side reusable window chrome and gallery do not change that rule.

A future bounded client window manager could display several machine panels at once only after defining a server protocol for **independent, keyed subscriptions/sessions** (player, dimension, device identity and window key), each with its own authorization, lifecycle, snapshot revision, freshness and resync/rejection path. Keep inventory identity and item movement on a separate authoritative, validated transaction path: source/target, count, permission, session and observed revision must be rechecked server-side. At most one vanilla inventory menu remains active; never pretend an inactive panel still owns a vanilla menu or can transfer items through a purely client-side slot grid. Define close/reopen, out-of-order replies, replacement, unload, range/access loss and disconnection cleanup per key. Cap open windows, visible widgets, subscribed devices, payloads and update rates; coalesce unchanged snapshots, measure render/tick/network allocations under multiple viewers and avoid polling unloaded chunks or retaining stale state. This is a distinct server-owner proposal, not an extension implicitly provided by the visual kit.

## Switch audio: upstream precedent versus optional prediction

At pinned upstream SS14 `Content.Server/Power/EntitySystems/ApcSystem.cs`, `OnToggleMainBreaker` checks the attempt and access before calling `ApcToggleBreaker`; that method changes the breaker and calls `_audio.PlayPvs(apc.OnReceiveMessageSound, uid, AudioParams.Default.WithVolume(-2f))`. The overload path also calls `ApcToggleBreaker`. This APC path plays on the **confirmed server change**; do not call it predicted APC audio merely because SS14 uses predicted audio in other paths. Locally, `PowerDeviceBlockEntity` plays the same SS14 switch clip server-side for accepted manual changes and timed trips, not rejected requests. The kit suppresses the vanilla button click, not that server sound; connected-client single-click listening after the fix remains pending. The imported clip's file-specific license is unresolved; see [audio milestone](../apc-overload-sprint/audio-milestone.md).

Optional future lower-latency feedback for the initiating clicker would require a deliberate paired protocol, **not a second unconditional sound**: play locally once only when an actionable toggle request is actually sent; correlate its session/request ID with the accepted change; exclude **only that initiating actor** from the accepted server sound broadcast if local playback already occurred. All neighboring players must still hear the accepted change, and automatic overload trips must retain their server broadcast to everyone. Never suppress a trip or another player's change, and never suppress the actor's server sound if no local prediction was played. A rejection, timeout or lost request cannot unplay a locally predicted clip: document that audible false positive and test it, along with duplicate/late responses, close/reopen and two-client overlap, before choosing this tradeoff. No audio implementation is made here.

## From sample points to a destructible station map

`BoundedViewportModel` and `SampleViewportWidget` currently show a bounded collection of supplied 2D points with local pan/zoom. The gallery's sample points are **not** a station map, floor plan, topology inference or world scan. An editable 3D station needs a new authorized world-data adapter that projects server-known block/chunk snapshots into a selected horizontal view with explicit elevations and dimension, chunk/snapshot revisions and visible/unknown/unloaded states. Offer selectable vertical layers or a deliberately bounded stacked view with height/occlusion rules; floors can be removed, holes opened and structures added at arbitrary levels. Do not assume an immutable floor or fill missing/unloaded cells as intact tiles. Geometry, room names, connections and power topology must not be fabricated from a static picture or the sample point model.

Specify who may receive map data and at what range/visibility; authorize any editing separately as server-validated world transactions (position, expected block/chunk revision, rights and conflict response), never client-only map mutations. Clip to a bounded viewport; request only needed chunks/layers, cap cells/markers, use LOD or aggregation by zoom, send deltas with revision checks, and discard stale or unloaded snapshots. Measure render, allocation and bandwidth costs before promising a live multi-window map. A read-only unknown/partial view is preferable to false station certainty; this viewport concept does not implement world edits.
