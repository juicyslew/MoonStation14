# Player Body Control — Sprint Instructions

## Status and scope

**Current architecture: an authenticated player's control session is a Mind; every controllable entity, including the ghost, is a Mob Harness.** The prior proposal that treated the Minecraft `ServerPlayer` spectator carrier as the ghost while allowing a vacant Mind is superseded. See the [M0c Mind and Mob Harness contract](docs/player-body-control-sprint/audits/m0c-mind-and-mob-harness-contract.md). The [M0b spectator-carrier proof](docs/player-body-control-sprint/audits/m0b-spectator-ghost-harness-proof.md) is retained as historical evidence only; its carrier-as-ghost premise is superseded. M1's isolated pure model/tests are delivered; see the [M1 implementation audit](docs/player-body-control-sprint/audits/m1-pure-mind-mob-harness-registry.md).

This sprint remains separately default-off behind a COMMON NeoForge config boolean and is entered only through an operator command; it does not start ghost control on join. The `experimentalMindGhostControl` config defaults to `false`; the operator command is registered but refuses to start while the server-startup-sampled gate is false. M1's pure model is delivered. M2a's separate ghost Mob and dedicated-server harness are registered, with the latest reported GameTest run passing **120/120**. M2b now has an experimental Mind/ghost owner-control slice: `/ms14 mindghost start|stop` creates a separate ghost Mob Harness, binds a server-owned Mind, performs Begin/Ready/Commit camera setup, and relays bounded client intent for server-applied movement. This implementation has automated validation but **no connected-owner runtime proof**. See the [M2a foundation audit](docs/player-body-control-sprint/audits/m2a-ghost-mob-harness-foundation.md), the [M2b ghost-control wire and latest status audit](docs/player-body-control-sprint/audits/m2b-ghost-control-wire.md), and the [experimental ghost owner smoke checklist](docs/player-body-control-sprint/audits/experimental-ghost-owner-smoke.md). This is not M2 acceptance or full SS14 parity: the ghost remains an invisible placeholder, and its `noPhysics` movement bypasses ordinary and entity collision rather than matching SS14 ghost/fixture collision behavior. NPC body transfer and on-join ghost creation remain deferred and require separate opt-in design and proof.

## Architecture and invariants

- **Mind:** a distinct control-session identity bound to the authenticated player/session owner ID. Keep Mind ID separate from the authenticated session owner ID. A Mind normally has exactly one active Mob Harness; temporary detachment is allowed only for lifecycle/failure handling, not as the default ghost state.
- **Mob Harness:** every entity controlled by a Mind, including the ghost, is an explicitly registered/eligible harness. Track a `MobHarnessKind` (at minimum `GHOST` and `CHARACTER`) and maintain an exclusive registry: one active harness per Mind and one Mind per active harness. A harness transfer replaces the Mind's active harness; it does not create a default vacant ghost-Mind state.
- **Minecraft transport seam (desired model):** retain the Minecraft `ServerPlayer` as an invisible spectator/session carrier as needed for authenticated vanilla connection transport and view, with no character status. Current runtime does not yet meet that identity separation: `CharacterIdentitySystem.enrollSupportedActor` binds HUMAN to `ServerPlayer` on join, and the ghost debug command does not remove or override that attachment. The spectator carrier remains an actual player entity; its visibility to other spectators is unverified. It is not the ghost Mob Harness and must not be treated as controllable. The ghost is a separate, server-spawned non-`ServerPlayer` entity, independently movable and viewable. Register and render it through the approved mod bus; do not copy upstream SS14 audio assets.
- **Creation and transfer:** the current experiment creates a ghost harness only on explicit `/ms14 mindghost start`; it does not create one on join. On-join creation and transfer to a configured NPC remain deferred and need separately reviewed opt-in gates. Current client input is routed through the server-owned Mind binding to the attached ghost harness; cleanup is provided for stop, timeout, and logout, but broader lifecycle recovery still needs proof.
- **Eligibility and scope:** configured Mob Harness eligibility applies to any supported `LivingEntity`; do not claim that every entity is supported or that SS14 restricts its entities to Minecraft `LivingEntity`. The ghost harness is also living/controllable in this local model. The first NPC fixture is a configured human Villager. Movement/look only initially; no actions, inventory, attack, or arbitrary interaction authorization.
- **Authority and safety:** the server owns Mind-to-harness bindings and validates authenticated input. For the ghost, the server applies bounded accepted `Entity.move`; wall/fixture collision parity is not implemented (`noPhysics` bypasses ordinary and entity collision). Never take a packet-selected target. Enforce exclusive ownership, bounded input, and lifecycle cleanup. A camera/view change alone is not control. Keep this feature default-off and separate from legacy movement behavior.

## Milestones and authorization

### M1 — isolated pure Mind/Mob Harness model and tests (authorized)

**Delivered:** isolated pure Java model and JUnit tests under `src/main/java/com/juicyslew/moonstation14/ms14/player_body_control/**` and matching test package. It models a Mind ID distinct from the authenticated owner UUID, `GHOST`/`CHARACTER` harness kinds, atomic creation already attached to a registered eligible ghost, exclusive binding, transfer, failure-detach/ghost recovery, eligibility rechecks, unregister revocation, and registry-global monotonic epochs. The focused suite contains 11 tests. See the [M1 implementation audit](docs/player-body-control-sprint/audits/m1-pure-mind-mob-harness-registry.md) for verified details and limitations. **M1 alone** is in-memory policy only: no world references, networking, server/client integration, actual ghost entity/packet, or command. No live hooks, movement, configuration, entity registration/prototypes, or shared-file integration is authorized at M1. M2 remains gated—not indefinitely cancelled—on a genuine ghost Mob Harness first and separate exact approval for shared integration.

### M2 — ghost entity and real input/movement (experimental owner smoke pending)

Shared experimental integration now exists behind the COMMON NeoForge boolean `experimentalMindGhostControl` (default `false`) and the op-level-2 `/ms14 mindghost start|stop` command. The command is registered even when disabled, but `/ms14 mindghost start` refuses while the server-startup-sampled gate is false without changing the ghost, Mind, or game mode. The server samples the gate at `ServerStartingEvent` and closes it at `ServerStoppedEvent`; there is no hot toggle. An already-active session persists until stopped or the server is restarted. Starting also remains rejected while the legacy `experimentalVerticalSliceMovement` gate is enabled. The command creates a separate non-player ghost harness and server-owned Mind; the carrier remains a spectator. The owner smoke checklist is the next evidence gate; until an actual connected owner safely completes it, do not claim runtime control proof. NPC transfer and on-join ghost creation are deferred and require separately reviewed opt-ins. A camera-only transition is not proof of movement.

The implementation is experimental, guarded by a default-off config boolean, and explicitly command-triggered; neither configuration nor login automatically starts ghost control. Do not expand it to NPC transfer or on-join creation under this smoke task. Stop before touching shared files: `Config`, `MoonStation14`, `ModDataAttachments` and other shared files overlap concurrent atmospherics work. Coordinate before any follow-up edits to those files.

### M3 — connected owner visibility and transition proof (smoke pending)

Connected-client evidence is still required. The [experimental owner smoke checklist](docs/player-body-control-sprint/audits/experimental-ghost-owner-smoke.md) covers only safe initial ghost control and recovery; it does not prove avatar visibility for all clients, collision fidelity, Mind transfer/return, or cleanup across every lifecycle transition. No FakePlayer or camera-only proof substitutes for connected evidence.
